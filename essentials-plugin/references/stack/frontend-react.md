# Frontend integration — embedded or standalone

How a React / TypeScript frontend attaches to an Essentials backend. Expands **S8** of
`stack-contract.md`; everything in S1–S11 still applies to the backend underneath.

There are exactly two deployment modes. They share a build pipeline and differ in almost
everything else, and the difference is invisible in development — which is why choosing
explicitly matters more here than anywhere else in the contract.

## The choice in one table

| | **Embedded** | **Standalone** |
|---|---|---|
| Deployment unit | one fat JAR | two: JAR + static host/CDN |
| Origin at runtime | same | different |
| CORS | **not needed** — do not configure it | **required**, and must name real origins |
| Deep-link routing (`/orders/42`) | backend SPA fallback filter | static host's SPA rewrite |
| API base URL | relative (`/api/...`), nothing to configure | must be configured **and consumed** |
| Release cadence | locked together | independent — contract skew becomes real |
| Frontend in the Maven reactor | yes | no |
| Rollback | one artifact | two, and they can disagree |
| Best for | one team, one release train, internal apps | separate frontend team, CDN/edge hosting, multiple clients |

**Default to embedded.** It removes an entire class of problems (CORS, contract skew, two-artifact
rollback) at the cost of coupling release cadence. Choose standalone when a real constraint forces
it — a separate team, a CDN requirement, or more than one client against the same API — not
because it feels more modular.

## What both modes share: the contract-first pipeline

The frontend never hand-writes an API client and never hand-writes types. The chain is:

```
Kotlin/Java endpoints
   │  SpringDoc, at /v3/api-docs
   ▼
contracts/openapi.json          ← regenerated by `mvn verify` (S7), committed
   │  Orval
   ▼
src/shared/api/generated/       ← typed hooks (TanStack Query), never hand-edited
src/shared/api/model/           ← typed DTOs,   never hand-edited
   │  a mutator you own
   ▼
src/shared/api/custom-fetch.ts  ← auth headers, error shape, base URL
```

Rules that hold in both modes:

- **`generated/` and `model/` are build output.** Editing them is a defect: the next `orval` run
  discards it. If a shape is wrong, the endpoint is wrong — fix the backend and regenerate.
- **`custom-fetch.ts` is the one place you own** in that chain. Auth headers, error normalisation
  and base URL live there and nowhere else.
- **The spec is generated, never authored** (S7). A hand-edited `openapi.json` is a lie the
  frontend then compiles against.
- **Regeneration is part of the change, not a follow-up.** An endpoint change that does not
  regenerate the client has not landed; it has only half landed.

The generator config that produces that shape, and the dev proxy that makes `/api` same-origin
during development:

```ts
// orval.config.ts
export default defineConfig({ api: {
  input:  { target: '../contracts/openapi.json' },
  output: { mode: 'tags-split', target: './src/shared/api/generated',
            schemas: './src/shared/api/model', client: 'react-query', httpClient: 'fetch',
            clean: true, override: { mutator: {
              path: './src/shared/api/custom-fetch.ts', name: 'customFetch' } } } } })

// vite.config.ts — dev only; this is what hides a standalone deployment's CORS bugs
server: { port: 5173, proxy: { '/api': { target: 'http://localhost:8080', changeOrigin: true } } }
```

**`generated/` and `model/` must not be committed.** They are build output; `orval` runs in the
build (Mode A) or before it (Mode B). Committing them means a stale client can be shipped against a
changed API, and reviewers diff machine-written code.

**Dev-time proxying makes both modes look identical, and that is a trap.** The Vite dev server
proxies `/api` to the backend, so during development the browser sees one origin whichever mode
you are targeting. A standalone deployment's CORS and base-URL configuration is therefore
**never exercised until it is deployed**. Test standalone against a non-proxied origin before
believing it works.

## Package manager — npm, and say so if you deviate

Everything below is written for **npm** (`npm install`, `npm ci`, `npm run build`,
`frontend-maven-plugin`'s `npm`/`npx` goals). That is the default, not a requirement: pnpm and yarn
both work, but they are not drop-in, and one difference is worth stating because it stops a build
rather than degrading it.

**pnpm gates postinstall scripts.** From pnpm 10, dependency build scripts do not run until they
are approved in `onlyBuiltDependencies` (`pnpm-workspace.yaml`), and pnpm refuses to run *any*
script while an approval is outstanding — so `pnpm orval` fails before Orval is reached. Vite's
`esbuild` is the dependency that trips this. Two sanctioned resolutions:

- Approve it (`onlyBuiltDependencies: [esbuild]`). Read `install.js` before you do: its registry
  download is a *fallback* for when the platform package (`@esbuild/<platform>`) is absent, and
  pnpm installs that package on supported platforms, so on those the approved script does no
  network fetch.
- Or bypass the gate entirely by invoking the binary directly — `node_modules/.bin/orval` — and
  approve nothing.

Whichever you pick, **record it in the project's `CLAUDE.md`**: an unexplained
`onlyBuiltDependencies` entry reads as a supply-chain concession with no rationale attached, and
the next person deletes it or copies it.

## Mode A — Embedded (single fat JAR)

The frontend is built during the backend's `package` phase and copied into the JAR's static
resources. One artifact ships; the browser loads the SPA and the API from the same origin.

**Required:**

1. **Frontend joins the reactor.** `frontend-maven-plugin` installs Node, runs `npm ci`, runs
   `orval`, then `npm run build` — all bound to `prepare-package`, in that order. Orval must run
   before the build: the TypeScript compile depends on generated types. Orval reads the
   **committed** `contracts/openapi.json` (S7); the build never starts the application to fetch a
   spec. An endpoint change therefore reaches the embedded client once `mvn verify` has regenerated
   the spec and it is committed — the next `package` builds from it.

   ```xml
   <!-- frontend-maven-plugin, workingDirectory = ../frontend; versions in stack-pins.md -->
   <execution><id>install-node-and-npm</id><phase>prepare-package</phase>…</execution>
   <execution><id>npm-ci</id>        <phase>prepare-package</phase><configuration>
       <arguments>ci</arguments></configuration></execution>
   <execution><id>orval-generate</id><phase>prepare-package</phase><goals><goal>npx</goal></goals>
       <configuration><arguments>orval</arguments></configuration></execution>
   <execution><id>npm-build</id>     <phase>prepare-package</phase><configuration>
       <arguments>run build</arguments></configuration></execution>
   ```
2. **Built assets land in static resources.** `maven-resources-plugin` copies `frontend/dist` into
   `${project.build.outputDirectory}/static`, so Spring Boot serves them from the JAR.

   ```xml
   <execution><id>copy-frontend-dist</id><phase>prepare-package</phase>
     <goals><goal>copy-resources</goal></goals><configuration>
       <outputDirectory>${project.build.outputDirectory}/static</outputDirectory>
       <resources><resource><directory>${project.basedir}/../frontend/dist</directory></resource>
       </resources></configuration></execution>
   ```
3. **A SPA fallback filter.** Deep links must reach `index.html` so the client-side router can
   handle them, while API and infrastructure routes pass through. The filter forwards a request to
   `/index.html` when the path is neither an API/infrastructure prefix (`/api/`, `/v3/`,
   `/swagger-ui`, `/actuator`) nor a file with an extension. On WebFlux this is a `WebFilter` that
   rewrites the path; on WebMvc, a `OncePerRequestFilter` that forwards. The generated
   `config/SpaWebFilter` carries the form for the project's web stack.

   ```kotlin
   @Component
   class SpaWebFilter : WebFilter {
       private val apiPrefixes = listOf("/api/", "/v3/", "/swagger-ui", "/actuator")
       private val extensionPattern = Regex("\\.[a-zA-Z0-9]+$")

       override fun filter(exchange: ServerWebExchange, chain: WebFilterChain): Mono<Void> {
           val path = exchange.request.uri.path
           if (apiPrefixes.any { path.startsWith(it) }) return chain.filter(exchange)
           if (extensionPattern.containsMatchIn(path.substringAfterLast("/")))
               return chain.filter(exchange)
           return chain.filter(exchange.mutate()
               .request(exchange.request.mutate().path("/index.html").build()).build())
       }
   }
   ```

   ```kotlin
   // WebMvc: the same rule as a servlet filter that forwards
   @Component
   class SpaWebFilter : OncePerRequestFilter() {
       private val apiPrefixes = listOf("/api/", "/v3/", "/swagger-ui", "/actuator")
       private val extensionPattern = Regex("\\.[a-zA-Z0-9]+$")

       override fun doFilterInternal(request: HttpServletRequest, response: HttpServletResponse,
                                     chain: FilterChain) {
           val path = request.requestURI.removePrefix(request.contextPath)
           if (apiPrefixes.any { path.startsWith(it) } ||
               extensionPattern.containsMatchIn(path.substringAfterLast("/"))) {
               chain.doFilter(request, response); return
           }
           request.getRequestDispatcher("/index.html").forward(request, response)
       }
   }
   ```
4. **A `skip-frontend` Maven profile** (S11), so backend-only work does not run `npm ci`.

**Forbidden:**

- **Do not configure CORS.** Same origin means no preflight and no `Access-Control-*`. A CORS
  policy here is dead configuration that will be read as intent by the next person, and copied
  into a service where it *is* live.
- **Do not set an API base URL.** Relative `/api/...` is correct by construction.

**Consequences to accept:** the backend build needs Node; frontend and backend version together;
a frontend-only fix requires a backend release.

## Mode B — Standalone (separate deployment)

The frontend is its own artifact on its own host — CDN, static bucket, nginx, or a Node server —
calling the backend across an origin boundary.

**Required:**

1. **Real CORS on the backend, expressed as a `CorsConfigurationSource` bean.** Allowed origins are
   the frontend's actual origins, named explicitly. `allowCredentials = true` **cannot** be combined
   with a wildcard origin; browsers reject the pair. Scope the policy to the API paths, not `/**`.

   **Expose the source, not a standalone `CorsWebFilter`.** S9 puts Spring Security on every
   generated project, and Security's filter chain runs ahead of an ordinary `WebFilter` — so a
   bare `CorsWebFilter` bean sees the preflight `OPTIONS` only after the security chain has already
   decided about an unauthenticated, header-less request. Publishing a `CorsConfigurationSource`
   instead lets Security pick the policy up and apply it *inside* the chain, which is where it
   belongs; nothing else has to be ordered by hand.

   ```kotlin
   @Bean
   fun corsConfigurationSource(props: CorsProperties): CorsConfigurationSource {
       val config = CorsConfiguration().apply {
           allowedOrigins = props.allowedOrigins        // real origins, never "*" with credentials
           allowedMethods = listOf("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS")
           allowedHeaders = listOf("Authorization", "Content-Type", "Accept")
           allowCredentials = true
           maxAge = 3600L
       }
       return UrlBasedCorsConfigurationSource().apply { registerCorsConfiguration("/api/**", config) }
   }
   ```

   Then enable it on the chain — the bean alone is picked up, but say it explicitly so the
   dependency is visible in the one place a reader looks for the security posture:

   ```kotlin
   http.cors { }        // uses the CorsConfigurationSource bean above
   ```

   **Bind the origin list with `@ConfigurationProperties`, never `@Value`.** A YAML sequence
   becomes indexed keys (`app.cors.allowed-origins[0]`), and `@Value` resolves a single property
   placeholder — so `@Value("\${app.cors.allowed-origins}")` on a `List<String>` fails to resolve
   at startup. Either bind the list properly, or flatten it to a comma-separated scalar; the first
   is the idiom:

   ```kotlin
   @ConfigurationProperties("app.cors")
   data class CorsProperties(val allowedOrigins: List<String> = emptyList())
   ```
   ```yaml
   app:
     cors:
       allowed-origins:
         - https://app.example.com
   ```
2. **An API base URL that is configured *and consumed*.** A build-time variable (`VITE_API_BASE_URL`
   or equivalent) is read in `custom-fetch.ts` and prefixed onto the request URL. **Declaring the
   variable is not enough** — the generated client emits relative paths, which otherwise resolve
   against the *static host*:

   ```ts
   export const customFetch = async <T>(url: string, options: RequestInit = {}): Promise<T> => {
     const baseUrl = import.meta.env.VITE_API_BASE_URL ?? ''   // '' keeps a same-origin build correct
     const response = await fetch(`${baseUrl}${url}`, { ...options, headers })
     …
     return { data, status: response.status, headers: response.headers } as T
   }
   ```

   The generated `custom-fetch.ts` reads the variable **per call**, so a test can stub it, and
   returns `{ data, status, headers }` — the shape Orval's fetch client expects of a mutator. Its
   `custom-fetch.test.ts` pins the behaviour: with the variable set the request goes to
   `${VITE_API_BASE_URL}/api/…`, unset it stays relative. That test is what keeps "declared but not
   consumed" from coming back.
3. **SPA rewrite at the static host.** The backend has no part in serving the SPA, so the deep-link
   fallback moves to nginx `try_files`, a CDN rewrite rule, or the host's SPA setting. A backend
   SPA filter is dead code in this mode.
4. **A published contract.** `contracts/openapi.json` becomes an artifact the frontend build
   consumes, not just a file in a sibling directory. Version it.
5. **A cross-origin auth decision.** Bearer tokens in a header cross origins with CORS alone.
   Cookies additionally need `SameSite=None; Secure` and credentialed requests on both ends.

**Test it without the proxy.** Two generated tests hold the two halves: `CorsPreflightIT` sends a
browser preflight (`OPTIONS` with `Origin` and `Access-Control-Request-Method`) through the security
chain and expects the allow header for the first configured origin and a 403 for an unknown one;
`custom-fetch.test.ts` proves the base URL is consumed. Before a deployment, run the built SPA on a
real second origin — `npm run build && npm run preview` serves `dist/` on `http://localhost:4173`,
which the generated `app.cors.allowed-origins` lists — with `VITE_API_BASE_URL=http://localhost:8080`
at build time, against the backend on `:8080`. That is the cross-origin path the dev proxy hides.

**Now genuinely your problem:** contract skew. The two artifacts deploy independently, so a
frontend built against yesterday's spec can meet today's backend. Removing or narrowing a field
becomes a breaking change on a schedule you no longer control — expand/contract, or version the
API.

**Not required:** the SPA fallback filter, `frontend-maven-plugin`, and the static-resource copy.
Deleting them is part of choosing this mode.

## Two half-choices to check for

Neither mode fails loudly when it is half-configured. Check any project for both:

| Symptom | Why it is wrong | Mode it belongs to |
|---|---|---|
| A CORS policy allowing `localhost:5173` / `localhost:3000` in an **embedded** deployment | Same origin means it never fires. It is dead configuration that reads as intent, and gets copied into a service where it *is* live | Standalone (or dev convenience only) |
| `VITE_API_BASE_URL` declared in `.env.example` but **no source file reads `import.meta.env`** | Harmless while embedded — relative URLs are correct by construction — and a silent failure the moment someone goes standalone believing the variable works | Standalone, and only if consumed |

The second is the sharper one: the generated client emits **relative** paths, so without the base
URL prefixed in `custom-fetch.ts` they resolve against the *static host* rather than the API. The
requests 404 against your own SPA, which looks like a routing bug rather than a configuration gap.

Declaring a variable is not wiring it. Grep for `import.meta.env` before believing a standalone
build is configured — or run `scripts/stack-lint.py`, which checks both half-choices (`ESS-S8`).

## Migrating between modes

**Embedded → standalone:** wire the base URL into `custom-fetch.ts`; add real CORS; move the
deep-link fallback to the static host; remove the SPA filter, `frontend-maven-plugin` and the
resource copy from the reactor; publish the contract; decide the auth story; then test against a
non-proxied origin.

**Standalone → embedded:** the reverse, and it is the easier direction — the pieces you delete
(CORS, base URL) fail loudly if still needed, whereas the pieces you add going the other way fail
silently.

## Non-React frontends

Nothing above is React-specific except the generated client's flavour. The pipeline, both modes,
and every rule hold for any TypeScript or JavaScript frontend; Orval targets several clients, and
a different generator (or `openapi-typescript`) slots into the same position against the same
`contracts/openapi.json`.

What changes: the generated hooks' shape, and the state library the mutator integrates with. What
does not: the spec is generated, the client is generated, `custom-fetch.ts` is yours, and the mode
decides CORS, routing and base URL.

The template ships React only.
