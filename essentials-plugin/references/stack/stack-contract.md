# The Essentials application stack contract

What a Trustworks Essentials application **must** have to work, stated independently of the
language it is written in and of whether it ships a frontend.

This is the counterpart to `rules/slice-design.md`. The slice law governs how code inside a
bounded context is *arranged*; this contract governs what the *application around it* must
provide for that code to run at all. Together they are the whole shape of an Essentials service.

**Read this when:** scaffolding a new project by hand, reviewing whether an existing one is
wired correctly, porting to another language or web stack, or deciding what `/essentials:init`
should emit.

## How this document is used

Requirements are numbered **S1–S11** and cited **by number, never restated** — the same
convention `rules/slice-design.md` uses for R1–R5. A skill or command says "S3 requires the
Kotlin module on the web mapper"; it does not paste the paragraph. When this file changes, every
citer follows automatically.

Each requirement is **MUST** (the application is broken without it), **SHOULD** (the sanctioned
default; deviate deliberately and write down why), or **MAY** (a real choice with no default).

**Every claim here traces to something.** The `Proof` line on each requirement names a doc under
`references/llm/` (which traces to the Essentials source), or inlines the configuration that *is*
the fact. Nothing here is authored from memory. If you add a requirement, add its proof in the
same edit.

Note what a proof is and is not. `/essentials:init` renders its project from
`references/init-assets/project/` with `scripts/init-render.py`, and the Essentials repository's CI
renders nine answer cells from it (both languages, all three profiles, both web stacks, every
frontend mode) and builds each against the framework at HEAD with `mvn verify`: every cell compiles
and starts its context against a real database. That executes what a generated project does — the
S2.1 set per profile, S3–S5 wiring, S7's contract test, S8's CORS and fetch tests — but not every
sentence here, so the `Proof` line stays the evidence for a requirement. `scripts/stack-lint.py`
checks the half of S1–S11 that is decidable from a project's files. `tests/fixtures/worked-example/`
exists to give the slice tooling something to read, not to prove this contract.

## S1 — Baseline and version pins (MUST)

An Essentials 0.60.0 application runs on **Java 25 or newer** and **Spring Boot 4.1.x**. Spring
Boot 4.0.x and 3.x are not supported. 0.60.0 class files are built at `--release 25`, and a Java 21
runtime rejects them with `UnsupportedClassVersionError`.

Every Essentials artifact is pinned from **one** `essentials.version` property. Mixed Essentials
versions on one classpath is not a supported configuration.

Concrete versions are **not** listed here — they live in `stack-pins.md`, which is the single
place a version rots. Nothing else in this directory may name a version number.

> Proof: `references/llm/LLM.md` § Quick Facts (Java 25+, Spring Boot 4.1.x). The `--release`
> level is the Essentials root `pom.xml`'s `java.release.version`. Concrete pins: `stack-pins.md`.

## S2 — Module selection (MUST pick exactly one persistence profile)

Choose the starter that matches the persistence model. The starters are cumulative, not
additive-by-hand: do not assemble one from its parts.

| Profile | Starter | You get |
|---|---|---|
| `pg-event-sourced` | `spring-boot-starter-postgresql-event-store` | Everything in `pg-crud`, plus `EventStore`, subscriptions, `EventProcessor`s |
| `pg-crud` | `spring-boot-starter-postgresql` | JDBI, `UnitOfWork`, durable queues, fenced locks, Inbox/Outbox, `DurableLocalCommandBus` |
| `mongo` | `spring-boot-starter-mongodb` | `MongoTemplate`, durable queues, fenced locks, Inbox/Outbox |

The event-store starter includes the PostgreSQL starter transitively. Declaring both is
redundant, not harmful; declaring the *components* individually instead of the starter is how
projects end up with a half-configured context.

**Two Essentials modules the starters do not bring, which a project on these profiles declares
itself** (both at the one `essentials.version`, S1):

| Profile | Declare | Why it is not transitive | What breaks without it |
|---|---|---|---|
| `pg-event-sourced` | `eventsourced-aggregates`; on Kotlin also `kotlin-eventsourcing` | The event-store starter marks `eventsourced-aggregates` `<optional>`; no starter depends on `kotlin-eventsourcing` | The decider and aggregate APIs (`EventStreamDecider`, `AggregateRoot`, the Kotlin `Decider` DSL) do not resolve — the first command slice does not compile |
| `pg-crud`, `pg-event-sourced` | `postgresql-document-db`, when read models use the document store (S5) | No starter depends on it | `DocumentDbRepositoryFactory` does not resolve — the first view slice does not compile |

A Java project must not carry `kotlin-eventsourcing`: its decider family lives in
`eventsourced-aggregates` (`java-spring-boot.md` § Event sourcing in Java).

> Proof: `components/spring-boot-starter-postgresql-event-store/pom.xml` in the Essentials
> repository (`eventsourced-aggregates` is `<optional>true</optional>`; neither Postgres starter
> names `postgresql-document-db` or `kotlin-eventsourcing`); `references/llm/LLM-eventsourced-aggregates.md`,
> `references/llm/LLM-kotlin-eventsourcing.md`, `references/llm/LLM-postgresql-document-db.md`
> (each module's own coordinates).

### S2.1 — What the starter does **not** bring (MUST declare these yourself)

"Cumulative" describes the Essentials components. It does **not** describe the third-party
libraries they run on. Every Essentials integration declares its framework dependencies in
**`provided` scope**, which is non-transitive by design — the zero-dependency-core philosophy —
so the application names them itself. **Every one of them kills context startup**, several under a
message that never names the real cause — and **most of them compile first**. Two compile errors are
the exception, and both only when the project's own code touches the library: `jdbi3-core` where
code imports `Jdbi` (the generated `config/DocumentDbConfig` does), and `kotlin-reflect` for Java code
calling the document store's overloads (below).

| Profile | Also declare (compile scope) | What breaks without it |
|---|---|---|
| `pg-crud`, `pg-event-sourced` | `spring-boot-starter-jdbc` | No `PlatformTransactionManager`. Surfaces on WebFlux as *"Failed to deduce bean type for `…reactiveHandlersBeanPostProcessor`"* — a message that names neither the transaction manager nor the missing starter |
| `pg-crud`, `pg-event-sourced` | `org.postgresql:postgresql` (the JDBC driver) | No `DataSource`: *"Failed to load driver class org.postgresql.Driver"* (a `ClassNotFoundException`). No Essentials artifact pulls the driver |
| `pg-crud`, `pg-event-sourced` | `jdbi3-core`, `jdbi3-postgres` | `NoClassDefFoundError: org/jdbi/v3/postgres/PostgresPlugin`. Without `jdbi3-core`, code importing `Jdbi` (the generated `DocumentDbConfig`) does not compile |
| `pg-crud`, `pg-event-sourced` | `kotlin-stdlib-jdk8`, `kotlin-reflect` | `NoClassDefFoundError: kotlin/jvm/internal/Intrinsics`. **Applies to pure-Java projects too** — see below |
| `mongo` | `spring-boot-starter-data-mongodb` | Spring Data MongoDB is absent, so the Essentials Mongo auto-configuration cannot even be introspected: *"Failed to deduce bean type for `…reactiveHandlersBeanPostProcessor`"*, caused by `NoClassDefFoundError: org/springframework/data/mongodb/core/convert/MongoCustomConversions$MongoConverterConfigurationAdapter` |
| all | `tools.jackson.core:jackson-databind` (Jackson 3) | Context startup fails with `NoClassDefFoundError` for a `tools.jackson` class. A Boot 4 web starter brings it through `spring-boot-starter-jackson`, so this bites a headless application |
| all | `reactor-core` | `NoClassDefFoundError: org/reactivestreams/Publisher` while creating the Essentials `EventBus` (`essentialsEventBus`). Satisfied transitively by WebFlux; **not** on a WebMvc stack |

**The Kotlin row is the one that ambushes Java projects.** `postgresql-document-db` is written in
Kotlin, so `kotlin-stdlib` is a *runtime* requirement of every project on a Postgres profile
regardless of whether the project contains one line of Kotlin, and `kotlin-reflect` is a *compile*
requirement of Java code touching that module: `createForCompositeId`/`create` and the `Condition`
DSL expose `KClass`/`KProperty1` overloads that javac must resolve in order to select the
`Class`-based one, and without it the build fails with `cannot access kotlin.reflect.KClass`.
A Java project therefore has a load-bearing Kotlin version pin (`stack-pins.md`) and no Kotlin
compiler — do not "clean up" either dependency as unused, and do not remove the pin because there
are no `.kt` sources.

**These are compile scope in the application even though they are `provided` upstream.** `provided`
is upstream's statement that *it* does not choose the version; the application must, and it must
put them on the runtime classpath.

**Event sourcing is a choice, not the default posture.** `rules/slice-design.md` §R5 sanctions
three write styles, and one of them — a state-stored entity — needs no event store at all. Pick
`pg-event-sourced` because the domain wants an event log, not because this framework is
associated with event sourcing.

**MongoDB, Spring Boot 4:** connection properties are `spring.mongodb.*`. The Boot 3 *connection*
names (`spring.data.mongodb.uri`, `host`, `port`, `database`, the credentials, `replica-set-name`,
`ssl.*`, …) are deprecated at level `error`, which means unbound — no warning, and a silent
fallback to `mongodb://localhost/test`. `spring.data.mongodb.uuid-representation` moved to
`spring.mongodb.representation.uuid`. The Spring Data keys (`spring.data.mongodb.auto-index-creation`,
`field-naming-strategy`, `gridfs.*`, `repositories.type`, `representation.big-decimal`) are still
bound and stay as they are.

**MongoDB needs a replica set.** Essentials' Mongo durable queues and fenced locks run in Mongo
transactions, which a standalone server does not support — so the development database (a Compose
service started with `--replSet`) and the integration-test container (`MongoDBContainer` with
`.withReplicaSet()`; the Testcontainers 2.x class starts a standalone node unless asked) are both
replica sets, and the connection string names it.

> Proof: `references/llm/LLM-spring-boot-starter-modules.md` (§ Starter Selection, § Dependencies —
> the non-transitive set per starter — and § Gotchas for `spring.mongodb.*`); the moved and the
> still-bound Mongo keys are Spring Boot's own configuration metadata
> (`spring-boot-mongodb` / `spring-boot-data-mongodb`, `META-INF/spring-configuration-metadata.json`);
> the replica set: `references/llm/LLM-springdata-mongo-distributed-fenced-lock.md` and
> `references/llm/LLM-springdata-mongo-queue.md` (transactions need one);
> `references/llm/LLM-postgresql-document-db.md` (Quick Facts "Key deps"; § Java gotchas for the
> Java-must-declare-Kotlin note); `references/llm/LLM.md` § Dependency Philosophy.

## S3 — The serialization contract (MUST — and it fails silently)

This is the single most expensive area to get wrong, because every failure mode here compiles,
starts, and returns a 200.

**S3.1 — Jackson 3 only.** Essentials serializes with Jackson 3 (`tools.jackson`, the Boot 4
default) and nothing else: its Jackson modules are `types-jackson3` / `immutable-jackson3`, which
the starters bring transitively. The persisted JSON is identical to what 0.50 wrote, so existing
events, queue payloads and documents stay readable. The Jackson 2 artifacts `types-jackson` /
`immutable-jackson` are gone but published `EssentialTypesJacksonModule` under the **same FQCN**:
a leftover one on the classpath makes every persistence serializer throw `IllegalStateException`
at startup. No Essentials artifact needs Jackson 2's `com.fasterxml.jackson.core:jackson-databind`;
`com.fasterxml.jackson.annotation` (`@JsonProperty`, `@JsonCreator`) is shared by both majors and
comes with Jackson 3's databind. SpringDoc does need it: `springdoc-openapi-starter-common` brings it
through swagger-core, so a *transitive* Jackson 2 databind on the classpath is expected and harmless.
The guard is against the Jackson 2 Essentials modules above, not against databind.

**S3.2 — The persistence serializer is built by `EssentialsObjectMappers` and ignores module
beans.** The starters' `JSONSerializer` (`pg-crud`, `mongo`) and `JSONEventSerializer`
(`pg-event-sourced`) beans take no parameters and deliberately do not collect `JacksonModule` beans
from the context, because those usually target the web layer and would silently change the
persisted format. A persistence mapper that needs an extra module — `KotlinModule` on Kotlin, see
`kotlin-spring-boot.md` — comes from your own `JSONSerializer` / `JSONEventSerializer` bean built on
`EssentialsObjectMappers.createJackson3ObjectMapper(…)`, which the starter backs off from. Never
hand-assemble the persistence `ObjectMapper`: it drifts from the persisted format, and the drift
shows on replay, not on write.

**S3.3 — Two mappers, registered independently.** The PostgreSQL and MongoDB starters (and so the
event-store starter) publish `EssentialTypesJacksonModule` as a bean, and Spring Boot adds every
`JacksonModule` bean to its auto-configured **web** `JsonMapper` (`@RequestBody`/`@ResponseBody`).
That registration reaches the web mapper only, never the persistence one (S3.2). It is lost
silently in two ways: an application with no Essentials starter (expose the bean yourself), or one
that replaces Boot's `JsonMapper` with its own bean (register the module on it explicitly).

**S3.4 — Kotlin types are covered by neither mapper out of the box.** See `kotlin-spring-boot.md`; this is the one
serialization rule that is genuinely language-specific.

**S3.5 — Constructor parameter *names* are part of the JSON contract.** Jackson 3 reads them from
the bytecode and treats any constructor as an implicit properties-based creator, even when a no-arg
constructor exists; Jackson 2 registered no parameter-names module and populated fields instead. A
constructor parameter whose name differs from the JSON property it ends up in receives `null` — so
the object trips its own `requireNonNull` or comes back half-populated. This is **silent on the way
out and only fails on the way in**: an upgraded service writes happily for days, then fails on
replay. Compile with parameter names retained (see the language files), and rename the parameter or
annotate it `@JsonProperty("…")` — that annotation lives in `com.fasterxml.jackson.annotation`,
which both majors share. `ConstructorDetector.EXPLICIT_ONLY` does **not** avoid this: with no other
way to construct the type, Jackson 3 uses the sole constructor regardless.

> Proof: `references/llm/LLM-types-jackson.md` § Quick Facts and § Spring Boot 4 (web mapper);
> `references/llm/LLM-foundation.md` § JSONSerializer (the canonical mapper, the Jackson 2 jar
> guard, constructor parameter names); the Kotlin persistence serializer is in
> `kotlin-spring-boot.md`.

## S4 — The typed edge (MUST if any endpoint takes a semantic type)

`types-spring-web` **auto-configures nothing**. There is no `AutoConfiguration.imports` and no
`spring.factories` in it: the dependency alone is inert, and the `@Import` *is* the registration.
This is the trap the module is most often filed under — the jar is present, the code looks wired,
nothing works.

It ships `EssentialsWebMvcConfigurer` and `EssentialsWebFluxConfigurer`. **Import
exactly one** — whichever web stack you are on. There is deliberately no combined class: only one
of `spring-webmvc` / `spring-webflux` is ever on a classpath, so a class naming both configurer
interfaces could not load.

Neither configurer touches HTTP message codecs — they override `addFormatters` only — so adding
this module **cannot** change which Jackson major serializes bodies. Bodies are S3's problem.

**Diagnostic:** a missing converter surfaces as HTTP **500**, not 400. Spring raises
`ConversionNotSupportedException` and classes a missing converter as server misconfiguration, so
a forgotten `@Import` looks like a server bug on a well-formed request.

```kotlin
import dk.trustworks.essentials.types.spring.web.EssentialsWebFluxConfigurer
// import dk.trustworks.essentials.types.spring.web.EssentialsWebMvcConfigurer   // servlet stack

@Configuration
@Import(EssentialsWebFluxConfigurer::class)      // THIS is the registration
class EssentialsWebConfig
```

> Proof: `references/llm/LLM-types-spring-web.md` § Configuration and § Gotchas.

## S5 — Persistence, transactions, and the document store (MUST)

Writes go through the starter's `UnitOfWork` — obtained from the `UnitOfWorkFactory` the starter
configures, or ambiently via Spring's transaction integration. Do not open your own JDBI handle
or Mongo session for domain writes; the durable-queue, Inbox/Outbox and fenced-lock machinery all
participate in that unit of work, and a write outside it silently opts out of every guarantee
they provide.

**Durable queues:** every queue operation runs in its own transaction — queueing, fetching,
acknowledging, retrying and dead-lettering are separate, so a failing handler cannot roll back its
own retry count. A consumer's handler is acknowledged by the framework when it returns; when it
throws, the `RedeliveryPolicy` decides. A rollback inside the handler (`markAsRollbackOnly()`,
directly or through the command bus) does **not** undo the delivery — design handlers to be
idempotent and let the policy retry. A `queueMessage` called inside the caller's `UnitOfWork` joins
it, so the enqueue commits or rolls back with the caller's writes. There is no transactional mode to
choose: an `essentials.durable-queues.transactional-mode` left in configuration binds to nothing,
and nothing reports it.

**Read models on PostgreSQL** may use `postgresql-document-db`, which needs a
`DocumentDbRepositoryFactory` bean built from `Jdbi`, the `HandleAwareUnitOfWorkFactory` and the
`JSONSerializer`. It is Postgres-specific: on the `mongo` profile there is no such thing.

**Aggregates and policy annotations:** `@AggregateSnapshotPolicy` and
`@AggregateClosingBooksPolicy` are registered by `BeanPostProcessor`s, which observe only Spring
beans — and an aggregate root is not a Spring bean. Annotations on an aggregate class therefore
reach no registry and **nothing complains**. Declare them with an `EssentialsAggregateDeclarations`
bean.

The document-store factory is not auto-configured; build it from the three beans the starter
already provides:

```kotlin
@Bean
fun documentDbRepositoryFactory(
    jdbi: Jdbi,
    unitOfWorkFactory: HandleAwareUnitOfWorkFactory<out HandleAwareUnitOfWork>,
    jsonSerializer: JSONSerializer
): DocumentDbRepositoryFactory = DocumentDbRepositoryFactory(jdbi, unitOfWorkFactory, jsonSerializer)
```

> Proof: `references/llm/LLM-foundation.md` § UnitOfWork (Transactions);
> `references/llm/LLM-postgresql-queue.md` § Transactions (and
> `references/llm/LLM-springdata-mongo-queue.md` § Transactions);
> `references/llm/LLM-postgresql-document-db.md` § Factory Creation;
> `references/llm/LLM-eventsourced-aggregates.md` § Declaring Aggregates.

## S6 — Internal structure (MUST — governed elsewhere)

Application code is organised by **vertical slice**, never by technical layer. The four slice
kinds, the JVM directory vocabulary, the boundary rule, and the R1–R5 anti-god-class rules are
the law in **`rules/slice-design.md`**, which is standalone and depends on no other plugin.

This contract does not restate any of it. A project satisfying S1–S5 and S7–S11 but organised
into `controllers/ services/ repositories/` is a correctly *wired* application that this plugin
still considers wrong; `/essentials:slice-check` is the audit, `/essentials:slice-discover` the
brownfield path.

## S7 — API surface and the contract (SHOULD)

Endpoints are **one per command slice**, and a view slice exposes queries over the read model it
owns — again, `rules/slice-design.md`, not restated here.

The OpenAPI document is **generated from the code, never hand-written**. SpringDoc serves it at
`/v3/api-docs`; an integration test (`OpenApiContractIT` in a generated project) fetches it from the
running test context and writes the checked-in `contracts/openapi.json`, with `servers` removed (the
random test port is not part of the contract) and keys sorted (`springdoc.writer-with-order-by-keys:
true`), so the file changes only when the API does. `mvn verify` regenerates it; `mvn package` does
not. Commit it with the endpoint change. That file is the contract other components consume, and
the embedded frontend build's input — the build reads the committed file, it never starts the
application to fetch one (S8).

Generate it against a context that has its database. The beans an endpoint needs — the command
bus's durable queues, the fenced-lock manager — reach the database as they are created, so an
application started without one (a DB-less spec-export profile, or a forked app the build starts and
stops around a fetch) cannot serve `/v3/api-docs` once a slice exists. The forked-app shape fails
worse than loudly: the fetch plugin logs the error and the build stays green on the **previous**
spec. The test fails the build instead.

**The spec describes semantic types as they are written.** Out of the box springdoc publishes a
`CharSequenceType` id as an object (`bytes`, `empty`, `value`) and a Kotlin value-class property
under its mangled JVM name (`id-nb-kci0`), while the wire carries a plain string under the real
name — so every client generated from the spec types every id wrongly, and nothing fails. Register
`types-spring-web`'s `SingleValueTypeModelConverter` as a bean in the application that runs
springdoc; like the rest of that module it is not auto-configured
([ESS-111](../llm/LLM-traps.md#ess-111)).

> Proof: build configuration, in the generated `OpenApiContractIT` and `application.yml`. The
> database dependency: `DBFencedLockManager`'s constructor opens a unit of work, even with
> `essentials.schema.mode: external`; springdoc instantiates every controller to describe it.
> Semantic types in the spec: `references/llm/LLM-types-spring-web.md` § OpenAPI with springdoc.

## S8 — Frontend integration (MAY — and the two modes are a real choice)

A frontend is optional. When there is one, it is **embedded** or **standalone**, and the choice
changes the build, the deployment unit, CORS, routing, and how the API base URL is resolved.

Both modes share the contract-first pipeline of S7. The full specification — what each mode
requires, what breaks if you mix them, and the migration between them — is
**`frontend-react.md`**.

The one rule that belongs here: **pick a mode explicitly and configure only that mode's pieces.**
A project carrying both a SPA-forwarding filter and a permissive CORS policy has not chosen; it
has accumulated — see `frontend-react.md` § "Two half-choices to check for".

## S9 — Security posture (MUST decide, MUST NOT inherit)

The scaffolded security configuration permits everything. That is a deliberate starting point for
a template, not a posture — replace it before the application leaves a laptop.

Two Essentials-specific requirements:

- The **admin surfaces** (`spring-boot-starter-admin-ui`, `spring-boot-starter-admin-api`) are
  **deny-all by default** and serve nothing until the application supplies both
  `EssentialsAuthenticatedUser` and `EssentialsSecurityProvider`
  (`dk.trustworks.essentials.shared.security`). Roles are per operation
  (`essentials_queue_reader`, `essentials_lock_writer`, `essentials_admin`, …).
- **Names are an injection surface.** Table, column, index, queue and collection names are
  string-concatenated into SQL/NoSQL. The framework's validation helpers are a convention check,
  not sanitization. Hardcode names; never accept one from a request.

> Proof: `references/llm/LLM-admin-api.md` § Security; `references/llm/LLM-components.md`
> § Security (the name checks are a first pass, not sanitising).

## S10 — Testing (SHOULD)

- **Unit and integration tests are separated by the build, not by convention.** Surefire runs
  unit tests and excludes `*IT` / `*IntegrationTest`; Failsafe runs those during `verify`.
- **Integration tests use Testcontainers 2.x**, whose artifacts are `testcontainers-postgresql`,
  `testcontainers-mongodb`, `testcontainers-kafka`. The 1.x coordinates no longer resolve.
- **Context caching is the difference between a fast suite and an unusable one.** Reuse forks,
  cap the Spring context cache, and keep the number of distinct context configurations small.
- **Property-based tests** belong on domain invariants; the JVM libraries are named in the
  language files.

**The fast-suite recipe is framework documentation, and this contract does not restate it:**
`references/llm/LLM-foundation-test.md` § *Fast integration tests*. It covers the shared, reused
container, Postgres in RAM, a warm context cache, and — the part that matters for an event-sourced
application — what keeps that recipe from hanging the suite: never truncate an `*_events` table with
`RESTART IDENTITY`; rebuild read models through `onSubscriptionsReset` plus `resetAllSubscriptions()`
or seed them directly; container reuse is opt-in and, when on, means one shared store per host; a
test that disrupts the database owns its container. A project's `IntegrationTestBase` follows that section.

**Two imports in that base class moved under the pinned versions, and both fail as "the annotation
/ class does not exist" rather than as a version problem:**

- **`@AutoConfigureWebTestClient` is no longer in `org.springframework.boot.test.autoconfigure.web.reactive`.**
  Boot 4 reorganised auto-configuration into per-technology modules; it is now
  `org.springframework.boot.webtestclient.autoconfigure.AutoConfigureWebTestClient`, and it is
  **no longer applied implicitly** by `@SpringBootTest`, so a test that used to get a
  `WebTestClient` for free now has to ask. If the annotation cannot be resolved, the fallback is to
  build the client explicitly against the injected `@LocalServerPort` — correct, just more code.
- **`PostgreSQLContainer` moved package in Testcontainers 2.x.** The artifact coordinate is
  unchanged (`testcontainers-postgresql`), but the class is
  `org.testcontainers.postgresql.PostgreSQLContainer`, and it is **not generic**:
  `PostgreSQLContainer<?>` / `PostgreSQLContainer<*>` does not compile against it.
  `org.testcontainers.containers.PostgreSQLContainer` is the deprecated generic one. The same
  repackaging applies to the other 2.x modules.

Surefire excludes `**/*IT` and `**/*IntegrationTest`; Failsafe includes exactly those and binds to
`verify`. Both reuse forks and cap the Spring context cache.

> Proof: `references/llm/LLM-foundation-test.md` § Fast integration tests. The two import moves are
> upstream Spring Boot / Testcontainers facts, not Essentials ones, and are recorded here because
> the pins in `stack-pins.md` make them unavoidable.

## S11 — Build and packaging (SHOULD)

Maven multi-module: a parent POM owning version properties and imported BOMs, and a `backend`
module. Embedded-frontend builds add the frontend to the same reactor (see `frontend-react.md`).

`spring-boot-starter-parent` is the parent POM, and no transitive version is pinned by hand.
What Spring Boot already manages — Testcontainers, Mockito, AssertJ, Awaitility, Kotlin, the
MongoDB driver — is moved through the version property Boot reads (`testcontainers.version`,
`mockito.version`, …): a BOM imported under that parent is inert for anything the parent already
manages, because the parent's management wins. What Boot does not manage — JDBI, Spring Modulith —
is imported as a BOM.

A **`skip-frontend` profile** must exist on any project whose package phase builds a frontend, so
backend-only development does not pay for a Node install. Without it, `mvn spring-boot:run`
during backend work runs `npm ci` and a Vite build.

> Proof: build configuration, inlined in `frontend-react.md` § Mode A. The property names are
> Spring Boot's own (`spring-boot-dependencies` imports `testcontainers-bom`, `mockito-bom` and
> `mongodb-driver-bom` at `${testcontainers.version}`, `${mockito.version}`, `${mongodb.version}`).
> Every version is in `stack-pins.md`.

## Conformance checklist

A project satisfies this contract when every line is true. `/essentials:slice-check` audits S6;
`scripts/stack-lint.py` checks the half of S1–S5 and S7–S11 that is decidable from the project's
files (`/essentials:upgrade` Group C and `/essentials:review` run it); the rest is review.

- [ ] Java 25+, Spring Boot 4.1.x, one `essentials.version` property (S1)
- [ ] Exactly one persistence starter, matching the chosen profile (S2)
- [ ] `eventsourced-aggregates` (plus `kotlin-eventsourcing` on Kotlin) on `pg-event-sourced`, and
      `postgresql-document-db` on the Postgres profiles, declared — the starters do not bring them (S2)
- [ ] The starter's non-transitive dependencies declared: JDBC starter, driver, JDBI, Kotlin
      stdlib/reflect on Postgres profiles (S2.1) — most of these compile and then kill context startup
- [ ] Mongo connection properties use `spring.mongodb.*`, not `spring.data.mongodb.*`; the
      database and the test container are replica sets (S2)
- [ ] Jackson 3 only — no 0.50-era `types-jackson` / `immutable-jackson` jar resolved (S3.1)
- [ ] Extra persistence modules come from an own `JSONSerializer` / `JSONEventSerializer` bean built on `EssentialsObjectMappers`, never a module `@Bean` or a hand-built mapper (S3.2)
- [ ] `EssentialTypesJacksonModule` reaches the **web** mapper — via the starter's bean, or explicitly when Boot's `JsonMapper` is replaced (S3.3)
- [ ] Event/payload constructor parameter names match their JSON properties (S3.5)
- [ ] Exactly one `Essentials*WebConfigurer` `@Import`ed, matching the web stack (S4)
- [ ] Domain writes go through the starter's `UnitOfWork` (S5)
- [ ] Queue handlers are idempotent and rely on the `RedeliveryPolicy`, not a rollback, to retry; no `essentials.durable-queues.transactional-mode` left in configuration (S5)
- [ ] Aggregates using policy annotations are declared via `EssentialsAggregateDeclarations` (S5)
- [ ] Code is organised by slice; `/essentials:slice-check` passes (S6)
- [ ] `contracts/openapi.json` is generated by an integration test against a context with its
      database, and committed; the frontend build reads the committed file (S7)
- [ ] `SingleValueTypeModelConverter` registered as a bean wherever springdoc runs (S7)
- [ ] Frontend mode chosen explicitly; only that mode's pieces configured (S8)
- [ ] Security replaced from the permit-all default; admin SPIs supplied if admin is enabled (S9)
- [ ] Surefire/Failsafe split; Testcontainers 2.x artifact names **and packages** (S10)
- [ ] `@AutoConfigureWebTestClient` imported from its Boot 4 package, or the client built
      explicitly (S10)
- [ ] `skip-frontend` profile exists on frontend-bearing builds (S11)
