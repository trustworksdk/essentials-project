# `slice.yaml` — field guide

Schema: `references/slice/slice-yaml.schema.json` (toolchain-neutral, so a manifest written by an
external generator validates too). This file is the *authoring* guidance: which fields to
write for each kind, and what Essentials expects beyond the schema minimum.

Every slice directory carries a `slice.yaml` and a `CLAUDE.md`. They are generated by
`/essentials:add-slice` and audited by `/essentials:slice-check`.

---

## 1. Always present

| Field | Notes |
|---|---|
| `schemaVersion` | `"1.3"` — readers accept any `1.x`, so an older stamp stays valid and needs no restamp |
| `slice` | `<bc>.<slice-id>` — **snake_case on the JVM** (`orders.place_order`); hyphens are illegal in package dirs |
| `kind` | `command` \| `view` \| `automation` \| `translation` |
| `bc` | owning bounded context |
| `owner` | owning team; defaults to `<bc>-team` |
| `status` | `planned` \| `live` \| `deprecated` |
| `summary` | one sentence, present tense |
| `tests` | `{ unit: {present}, integration: {present}, contract: {present} }` |
| `generator` | always `essentials` when written by this plugin |
| `language` | `java` or `kotlin` |
| `forbidden` | always includes `cross-slice-internal:<bc>` |

`lastSyncedAt` is **not** written by Essentials — it stamps an external generator's sync loop, which
this plugin does not run. The schema treats it as optional for exactly this reason.

## 2. Per kind

Schema-required is the floor; Essentials writes the stricter set so the manifest is actually useful.

| Kind | Schema requires | Essentials also writes |
|---|---|---|
| command | `handles`, `writes` | `publishes`, `endpoints`, `invariants` |
| view | `serves` | `projections` (**with `from`** — see §3), `reads`, `endpoints` |
| automation | `consumes` **or** `schedule` | `dispatches`, `invariants` |
| translation | `externalSystem`; plus `consumes` + `maps` unless `direction: outbound` | `direction`, `tests.contract` |

**Every kind declares what triggers it, but not all in the same field.** A view uses
`projections[].from`; automations use `consumes` or `schedule`; translations use `consumes`. §3 has
the table and the reason this matters to anything that reads a manifest.

**Two kinds have a shape the schema deliberately does not force.** A **schedule-triggered
automation** consumes no events — the law lists the automation trigger as "event / **schedule**", so
requiring `consumes` there would contradict it and produce an information-free `consumes: []`. A
**port-style ACL** — the system calls out, nothing calls in — has no inbound message and therefore no
mapping table, and is still unambiguously a translation slice; declare `direction: outbound` and the
schema stops asking for `consumes` and `maps`. With `direction` absent, `consumes` and `maps` stay
required.

The schema deliberately does **not** require `projections` on views or `dispatches` on automations —
integration-heavy/BFF slices legitimately have neither, and the schema is toolchain-neutral and
supports those profiles. Essentials enforces the stricter set in its skills instead.

**The stricter set is lane-conditional** (`rules/slice-design.md` §R5). On the two event-sourced lanes
a command slice always writes `publishes` and a view slice always writes `projections`. On the
**service-entity** lane:

- `publishes` still applies — the slice publishes its events on the `EventBus`, so the contract is
  the same even though nothing is appended to a stream.
- `projections` is **empty**, because a view slice there queries the entity's own table instead of
  owning a projected read model. Do not demand it, and do not treat its absence as drift.
- `tier: service-entity` **and** `lane: service-entity` — the one lane where the two axes carry the
  same word, which is exactly what made them easy to conflate. See §3.
- `reads[].via` names the slice-private query interface a view reads through. Use it rather than
  inventing a new property: the field already exists for exactly this purpose.

## 3. Field semantics that get written wrong

- **Always quote `path`.** `endpoints: [{ method: GET, path: "/api/orders", auth: user }]`.

  This is the one rule in this guide that decides whether the file is **YAML at all**, so it comes
  first. Inside a flow mapping — the `{ … }` form these manifests use throughout — an unquoted scalar
  containing `{` starts a *nested mapping*, and the parser fails at the brace:

  ```yaml
  # ✗ not YAML — the parser stops at the brace and the whole file fails to load
  - { method: POST, path: /api/orders/{orderId}/cancel, auth: user }
  # ✓
  - { method: POST, path: "/api/orders/{orderId}/cancel", auth: user }
  ```

  Every path variable produces that brace, so any REST-shaped API hits it. Block form is also safe —
  `- method: POST` with `path:` on its own line is not inside a flow mapping — but **quote anyway**:
  "quote every path" is a rule that survives a later edit reflowing the entry into flow form, while
  "quote when it contains a brace" is a rule people apply right up until the day they add a path
  variable to an existing endpoint.

  The failure is silent where it matters most. Nothing in a Maven or Gradle build reads `slice.yaml`,
  so a broken manifest compiles, tests green, and ships — and only surfaces when a tool parses it,
  which is the moment it drops the slice from a map or an audit. `/essentials:slice-check` gate 1
  reports it as **Blocking** and `--fix-manifests` repairs the quoting.
- **A mapping selected by a query parameter is its own `endpoints` entry**, written
  `path: "<route>?<param>="`:

  ```yaml
  serves: [OrderStatusList, OrderStatusByStatus]
  endpoints:
    - { method: GET, path: "/api/shipping/order-status", auth: user }
    - { method: GET, path: "/api/shipping/order-status?status=", auth: user }   # @GetMapping(params = "status")
  ```

  Spring's `params = "status"` creates a **distinct mapping**, so it is a distinct endpoint and a
  distinct name in `serves` — over the *same* read model, which is §R2's "a view may expose several
  queries over the model it owns". It is not a second slice and it is not drift.

  Write the discriminators after `?`, `&`-separated, in any of three forms: `?status` (present),
  `?status=` (present, the conventional spelling), or `?status=shipped` (pinned to a value, matching
  `params = "status=shipped"`). An **optional filter** on an existing mapping —
  `@RequestParam(defaultValue = "false") boolean shipped` — is *not* a discriminator and gets no entry
  of its own; it does not select a different mapping.

  **The query string never appears in the source.** It is expressed as `params = "…"` or
  `@RequestParam`, so a manifest-to-code check that greps the declared path verbatim reports a false
  positive on every run. Readers must match the route *before* the `?`, then confirm each named
  parameter is bound in that handler — `/essentials:slice-check` gate 6 and `/essentials:slice-map`
  both do.

  Why the parameter lives in `path` rather than in a field of its own: the schema is toolchain-neutral,
  `path` is a plain string with no format constraint, and one self-describing string beats a second
  field that every consumer would have to learn. The cost is that `path` is a route *plus* an optional
  discriminator, which is why the split rule is stated here and enforced in both readers.
- **`serves` takes query names, not routes.** `serves: [ListOrders]`; the route belongs in
  `endpoints: [{ method: GET, path: "/api/orders", auth: user }]`. This is **mechanically
  enforced** — the schema rejects any `serves` entry containing `/` — because it is the easiest field
  in the manifest to get wrong and a route there is silently useless to every reader. Manifests that
  carry a hand-written comment reminding the next author of this rule are the tell that documenting
  it was not enough.
- **`auth` is a coarse class; `capability` is your permission model.** `auth` stays a closed enum
  (`anonymous | user | org-scoped | service`) precisely so it remains comparable across projects and
  across toolchains. A real permission model — named bundles, per-resource
  scopes, roles — goes in `capability` beside it, as open strings:

  ```yaml
  endpoints:
    - { method: POST, path: "/api/orders/{orderId}/cancel", auth: user, capability: [orders:cancel] }
  ```

  Collapsing four distinct permissions to `auth: user` deletes the only machine-readable record of
  who may call the endpoint. Record the class *and* the capability; neither substitutes for the other.
- **`provides` is a published read seam** — an interface this slice implements so another slice can
  ask it a question without touching its store. The interface is declared in the BC's `types/`; the
  implementation stays inside the slice:

  ```yaml
  provides:
    - name: OrderCreditStatus
      note: Answers "is this customer over their limit" without exposing the credit read model.
      consumedBy: [orders.place_order, orders.raise_limit]
  ```

  The consuming side declares the other half — `reads: [{ name: CreditStatus, via: OrderCreditStatus }]`.
  Read-only and question-shaped: see `rules/slice-design.md` § The published read seam for the four-part
  bar, including why an event is the better answer wherever one will do. `consumedBy` is advisory — a
  stale entry is drift to report, not a build failure.
- **`notes` records a deliberate limit**, in prose, as an array of strings:

  ```yaml
  notes:
    - No total count on this endpoint: counting a filtered append-only log is a second full query.
  ```

  It is for constraints that are *still true* and that a reader would otherwise have to reconstruct
  from a comment — not a changelog, not a TODO list. Human-owned: never derived, never overwritten.
- **`schedule` is the automation's other trigger.** An automation declares `consumes`, or `schedule`,
  or both:

  ```yaml
  schedule: { cron: "0 0 3 * * *", note: "Off-peak; the report it feeds is read at 08:00." }
  # or
  schedule: { fixedDelay: PT15M, initialDelay: PT1M }
  ```

  Give the `note`. A schedule with no stated reason is the one nobody dares change.
- **Both are arrays, and a view slice may legitimately have several.** A view slice owns one read
  model and may expose more than one query over it (`rules/slice-design.md` §R2) —
  `serves: [ListOrders, FilterOrdersByStatus]` with a matching `endpoints` entry each. Every exposed
  method must appear here; an endpoint missing from the manifest is drift, and `/essentials:slice-check`
  gate 11 reports it. A **command** slice always has exactly one of each.
- **`tier` and `lane` are two axes, and only one lane shares a word with a tier.** `tier` is the
  `architectureTier` — *how is the backend organised* — and `lane` is §R5's write style — *where does
  the decision live inside it*:

  | `lane` | `tier` |
  |---|---|
  | `decider` | `cqrs-es` |
  | `aggregate` | `cqrs-es` |
  | `service-entity` | `service-entity` |

  **`tier: aggregate` is wrong.** `aggregate` is a write style, not an
  `architectureTier` value; an aggregate-lane BC is event-sourced, so its tier is `cqrs-es`. The cost
  of getting it wrong is silent rather than loud: the schema's contract for an unrecognised tier is
  *behave as if it were `custom`*, so a tier-aware reader skips the slice's per-tier structure sections
  and its manifest generation entirely — a wrong `tier` is worse than an absent one. `lane` is a **closed
  enum** because §R5 sanctions exactly three write styles and a fourth would be a change to the law.
- **`writes` is the aggregate, not the table.** `writes: [Order]`.
- **`publishes` is the event type**, owned by this slice: `publishes: [OrderPlaced]`.
- **`consumes` is what triggers the slice** — events for automations, external messages for
  translations.
- **A view does not use `consumes`. Its events go on `projections[].from`.** This is the single most
  common place a manifest goes quietly out of step with its code, so it is worth stating flatly:

  | Kind | Where the inbound events are declared |
  |---|---|
  | view (event-sourced lanes) | `projections[].from` — every event type its `ViewEventProcessor` / `InTransactionEventProcessor` handles |
  | view (service-entity lane) | nowhere — there is no projector; `projections: []` is correct |
  | automation | `consumes` |
  | translation | `consumes` (external messages) |

  One field per kind, never both: a view that also lists its events under `consumes` has two copies to
  keep in step, and they will diverge. **Anything reading the manifest must union the two** rather than
  reading `consumes` alone — a reader that does not will show every correctly-generated view as
  reacting to nothing, which is precisely what keeps the mistake invisible.

  `projections[].from` is a **complete** list, not an illustrative one. Add an `@MessageHandler` for one
  more event type and the entry gains a name in the same change; that is what makes
  *"which events feed this view"* answerable without reading the projector. `consistency: eventual`
  corresponds to a `ViewEventProcessor`, `strong` to an `InTransactionEventProcessor`.

  **A projection object takes exactly five keys — `name`, `aggregateTypes`, `from`, `consistency`,
  `store` — and `from` is required.** `kind`, `handles` and `table` are the three near-synonyms an
  author reaches for instead, and each would carry the event list under a key no reader consults:

  ```yaml
  # ✗ rejected by the schema — and every reader would report this view as reacting to NOTHING
  projections:
    - name: SomeProjection
      kind: ViewEventProcessor          # not a field
      handles: [ThingCreated, ThingRenamed]   # not a field — and this is the event list
      table: some_table                 # not a field
  ```

  That is strictly worse than an absent field, because it looks maintained. Anything the five keys
  cannot carry goes in `notes`.
- **`aggregateTypes` is the STREAM, `from` is the EVENTS, and they are not interchangeable.** A
  projector subscribes to one or more `AggregateType` streams and handles some set of event types
  off them. Those are two different facts and the manifest carries both:

  ```yaml
  projections:
    - name: OrderListProjection
      aggregateTypes: [Orders]                    # the stream — PascalCase plural
      from: [OrderPlaced, OrderCancelled]         # the event types its handlers take
      consistency: eventual
      store: document-db
  ```

  `subscribesTo` is the fourth key authors reach for, and it is a *different* mistake from the three
  above: it carries a real fact under a key nothing reads. Its home is `aggregateTypes` — **never
  `from`**, where a stream name silently corrupts the event list and every reader then draws an
  inbound edge for an event that does not exist. Both are arrays of strings, so the schema cannot
  tell a swap apart; `slice-lint.py` gate 1(c) catches it from the corpus instead, by reporting an
  `aggregateTypes` value used as an event type anywhere else in the project.

  The field is optional. Absent means *unknown*, not *none* — service-entity-lane views have no
  projector at all, and manifests authored before schema 1.3 never had the field to fill in.
- **`dispatches` is what an automation sends**, i.e. command types.
- **`maps` is the translation table**: `[{ from: BillingInvoiceIssued, to: RecordPayment }]`.
- **`invariants` carry an id, text, and the component that enforces it** —
  `{ id: INV-PO-1, text: "Quantity must be positive", enforcedBy: PlaceOrderDecider }`. An invariant
  with no `enforcedBy` is a wish, not an invariant.
- **`forbidden` is machine-checkable prohibition**, not prose. `cross-slice-internal:<bc>` and
  `direct-decider:<other_slice>` are the two Essentials uses.
- **`supersedes` declares a migration twin**, and is the only sanctioned way for two slices to
  project the same events into the same shape. See §4 below.
- **An unknown root key is rejected, and `x-` is the escape hatch.** The schema is strict at the root
  so that drift is visible rather than silent. Where a project genuinely needs to carry something no
  field fits, prefix the key with `x-` (`x-team-oncall: payments`) and it validates. Reach for a real
  field first and `notes:` second — no toolchain reads an `x-` key, so one is
  documentation, not a contract.

### Validating a manifest

```bash
python3 <plugin>/scripts/slice-lint.py .            # every slice.yaml under the current directory
python3 <plugin>/scripts/slice-lint.py . --require-schema   # what CI should run
```

It parses, validates against the schema, and checks the three sole-ownership properties across
manifests. Exit 0 clean, 1 findings, 2 could not run. `/essentials:init` offers to install a project
wrapper and a pre-commit hook; wire one of them up, because nothing in a Maven or Gradle build reads
`slice.yaml` and an unparseable manifest is otherwise invisible rather than loud.

## 4. `supersedes` — the versioned view twin

When a view must project a new event but the model is too large to rebuild in an acceptable window,
`rules/slice-design.md` § Evolving a view slice allows a temporary second directory. The manifests
are what make it legible as *one slice in two versions* rather than an R4 violation:

```yaml
# excerpt — views/order_list_v2/slice.yaml, while catching up. Other fields unchanged.
slice: orders.order_list_v2
kind: view
status: planned                 # → live once caught up and consumers have swapped
supersedes: orders.order_list
```

```yaml
# excerpt — views/order_list/slice.yaml, the original, once v2 is live.
slice: orders.order_list
status: deprecated
```

Both files change again at the end: `v1`'s directory is **deleted** and `v2` drops `supersedes`
(optionally renaming back to the unsuffixed id). `/essentials:slice-check` reports the retirement as
**Should-fix** for as long as both exist, and reports an undeclared duplicate pair as **Blocking**.

Do **not** use `supersedes` for a permanent second view. If two read models are meant to coexist,
they serve different purposes and are two ordinary slices with no link between them.

## 5. Worked examples

### command

```yaml
schemaVersion: "1.3"
slice: orders.place_order
kind: command
bc: orders
owner: orders-team
status: live
summary: Place a new order for a SKU and quantity.
generator: essentials
language: kotlin

handles: [PlaceOrder]
publishes: [OrderPlaced]
writes: [Order]
reads:
  - { name: Order }
endpoints:
  - { method: POST, path: "/api/orders", auth: user }
invariants:
  - { id: INV-PO-1, text: "Quantity must be positive", enforcedBy: PlaceOrderDecider }
forbidden:
  - cross-slice-internal:orders
tests:
  unit: { present: true }
  integration: { present: false }
  contract: { present: false }
```

### view

```yaml
schemaVersion: "1.3"
slice: orders.order_list
kind: view
bc: orders
owner: orders-team
status: live
summary: List orders for the current customer.
generator: essentials
language: kotlin

serves: [ListOrders]
endpoints:
  - { method: GET, path: "/api/orders", auth: user }
reads:
  - { name: OrderListView }
projections:
  - name: OrderListProjection
    aggregateTypes: [Orders]
    from: [OrderPlaced, OrderCancelled]
    consistency: eventual
    store: document-db
forbidden:
  - cross-slice-internal:orders
tests:
  unit: { present: false }
  integration: { present: true }
  contract: { present: false }
```

### automation

```yaml
schemaVersion: "1.3"
slice: orders.fulfillment
kind: automation
bc: orders
owner: orders-team
status: live
summary: Drive an order from confirmed through payment to shipment.
generator: essentials
language: kotlin

consumes: [OrderPlaced, PaymentReceived, PaymentFailed]
dispatches: [InitiatePayment, ReserveInventory, CancelOrder]
invariants:
  - { id: INV-FF-1, text: "Payment is attempted at most three times", enforcedBy: FulfillmentProcessor }
forbidden:
  - cross-slice-internal:orders
tests:
  unit: { present: false }
  integration: { present: true }
  contract: { present: false }
```

### translation

```yaml
schemaVersion: "1.3"
slice: orders.billing
kind: translation
bc: orders
owner: orders-team
status: live
summary: Anti-corruption boundary to the Billing system.
generator: essentials
language: kotlin

externalSystem: billing
direction: both
consumes: [BillingInvoiceIssued]
maps:
  - { from: BillingInvoiceIssued, to: RecordPayment }
  - { from: OrderPlaced, to: BillingCreateInvoice }
forbidden:
  - cross-slice-internal:orders
tests:
  unit: { present: true }
  integration: { present: false }
  contract: { present: true }
```

## 6. The companion `CLAUDE.md`

15–40 lines, and it is prose for a human or an agent opening the slice cold:

```markdown
# Slice: <bc>.<slice>

**Kind:** <kind>   **Status:** <status>   **Owner:** <owner>
**Purpose:** <one sentence>

## Invariants
- <invariant> (enforced by `<component>`)

## Boundaries
**Reacts to / reads:** ...
**Publishes:** ...
**Forbidden:**
  - Never import another slice's internals — only `<bc>/events/` and `<bc>/types/`.
  - Never add this slice's logic to a shared decider/controller/event file.

## Data
**Owns (writes):** ...
**Reads:** ...

## Files
- `<file>` — <role>
```

Machine-derived fields are regenerated on refresh; hand-written prose is preserved.
