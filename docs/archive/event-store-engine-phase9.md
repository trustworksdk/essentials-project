# Event store redesign, phase 9: migration design

> **ARCHIVED (2026-11-19).** The new event store engine is built and ships as a preview in 0.62.0. The engine as built is described in [`../design/event-log.md`](../design/event-log.md); this document is kept for its decisions and gate results. Section references of the form "phase N §x" in source comments point here.

**Status:** decided 2026-11-17 (§15); built 2026-11-17, gate passed (§17, with the decisions of §18). Built on
`feature/event-store-engine-phase9` (from phase 8b, `223d36278`). When phase 9 is done, this file moves to
`docs/archive/` or is folded into the redesign's record.
**Scope:** phase 9 of `docs/archive/event-store-subscription-redesign.md` (§18, "Phases 1 onward"): the one-way move of an
application from `PostgresqlEventStore` to the event log. That means copying the events per aggregate type, optionally
importing resume points, cutting over, and verifying all of it (§12.4, D5, risk 9, §19 item 20). The phase starts with a
spike that measures how fast the copy runs and how long the stop lasts (§19 item 20).
**Gate (plan §18):** I8 passes, with its must-fail test against an import that copies the old resume point unchanged
(§9.2); every other must-fail test in §9 is seen to fail; a copy of the trading demo's data verifies equal and resumes on
the new engine without loss (§10.3, read with open question 3); the §10 measurements meet the pass lines decided there.
Every phase-2 to phase-8 IT keeps passing.

Section references (§n) are to the plan. "Phase-8 §n" and similar refer to `docs/archive/event-store-engine-phase8.md`
and its siblings. Where this draft proposes something the plan does not say, it is marked **Proposed**.

The existing engine is not changed (decided 2026-11-15). The migration only **reads** the old engine's tables: the event
tables, `durable_subscriptions`, `transient_subscriber_gaps`, `permanent_gaps` and the identity sequences. It takes one
lock on them (a `SHARE` table lock during the final pass, §3.5), which blocks writers but changes nothing. Nothing in
this design copies the old subscription model. The old resume points feed the new progress rows once, through the new
engine's own admin surface (§4).

## 1. What exists today, and what changes

### 1.1 The source: the old engine's tables

| What | Shape (`SeparateTablePerAggregateTypePersistenceStrategy.java:705-741`) | What matters for the copy |
|---|---|---|
| Event table, one per aggregate type | Name from the configuration's resolver (`<type>_events` by default). Column names are configurable (`EventStreamTableColumnNames`) | The tool cannot derive these; it must be told the table and column names (§2.2) |
| `global_order` | `bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, with no `CACHE` clause, so the cache is 1 unless an operator altered it | §3.3's wait rule relies on cache 1, so the tool checks it in pre-flight (§3.1) |
| `aggregate_id` | `text` or `uuid` (`IdentifierColumnType`, `TEXT` by default) | The new column is `text`; `uuid::text` gives the canonical lower-case form (§2.4) |
| `event_id`, `caused_by_event_id` | `text` or `uuid`, `TEXT` by default; `UNIQUE(event_id)` | The new columns are `uuid`; a text value that is not a canonical UUID cannot be copied (§2.4) |
| `correlation_id` | `text` or `uuid` | As `event_id` |
| `event_type` | `text`, holding the persisted type-or-name value (`EventJSON`) | Interned into `el_event_types` (`smallint`) |
| `event_revision` | `text` | The new column is `smallint`, so values must parse and fit |
| `timestamp` | `timestamptz` | Same type |
| `event_payload`, `event_metadata` | `json` or `jsonb` (`JSONColumnType`, **`JSONB` by default**) | §2.3: with `jsonb` there are no original bytes left to preserve |
| `tenant` | `text` | Same type |
| `durable_subscriptions` | `(subscriber_id, aggregate_type)` primary key, `resume_from_and_including_global_eventorder`, `last_updated`, `reposition_epoch` (`PostgresqlDurableSubscriptionRepository.java:171-185`). The table name is configurable | One row per subscriber and type, shared by every JVM |
| `transient_subscriber_gaps` | `(subscriber_id, aggregate_type, gap_global_event_order)` (`PostgresqlEventStreamGapHandler.java:219-224`) | Open gaps below a resume point (§4.2) |
| `permanent_gaps` | `(aggregate_type, gap_global_event_order)` | Report only (§4.4) |

### 1.2 The target: the event log's tables

| What | Where | What matters for the copy |
|---|---|---|
| `el_<type>_events` | `EventLogSchemaContributor.aggregateTypeStatements`, `:238-269` | `global_order bigint GENERATED BY DEFAULT AS IDENTITY (CACHE 1)`, so explicit values are accepted. Has `uuid` ids, `smallint` type and revision, and `json` payload and metadata. `UNIQUE(aggregate_id, event_order)`, plus an `event_id` index and a partial `caused_by_event_id` index |
| `el_<type>_heads` | same | `(aggregate_id, version)`, where `version` is the stream's highest `event_order` (`EventLogStorage.TableStatements`, `:516-527`). The copy must write it (§3.6) |
| `el_aggregate_types` | `schemaStatements`, `:147` | Written by `EventLog.registerAggregateType` |

## 2. Where the tool lives, and what it is told

### 2.1 Module

**Proposed:** a new module, `components/postgresql-event-log-migration` (package
`dk.trustworks.essentials.components.eventlog.migration`). It depends on the engine and on `foundation`, and **not** on
`postgresql-event-store` or JDBI. It uses raw pgjdbc, like the engine.

Plan §12.2 puts "the migration tooling" in the integration module. Reasons to put it in a module of its own instead:

1. **Lifecycle.** The tool is used once per application and is deleted when the old engine is. Inside the integration
   module it would stay on every adopter's classpath for good.
2. **Shape.** The copy is SQL over two schemas. It involves no serialisation, unit of work, interceptors or Spring,
   which is everything the integration module is for.
3. **Where it runs.** Operators will want to run it as a standalone process against a copy of production, without the
   application's classpath (§5). A small module with a `main` does that.
4. **Dependencies.** The tool needs nothing of the old engine except table and column names, which are plain strings
   (§2.2). Not depending on `postgresql-event-store` keeps the "only reads" promise visible in the POM.

The cost is one more module, and therefore an entry in the root `pom.xml` (E1, §13). The one piece that needs old-engine
types is the bridge that turns a `SeparateTablePerAggregateEventStreamConfiguration` into §2.2's `SourceTable`. That
bridge goes in the integration module, which already depends on `postgresql-event-store` (unit 9-F).

### 2.2 Input

```
MigrationPlan(
    DataSource source, DataSource target,            // the same database in phase 9 (open question 2)
    List<SourceTable> tables,                        // per aggregate type: old table name, the column names, and
                                                     //   the id and JSON column types read from the catalog, not trusted
    SourceSubscriptions subscriptions,               // names of the durable_subscriptions, transient and permanent gap tables
    List<ImportedSubscription> imports,              // optional (§4)
    CopySettings settings)                           // batch size, epoch wait timeout, lock timeout
```

`SourceTable` validates every name with `PostgresqlUtil.checkIsValidTableOrColumnName` before concatenating it into SQL
(root `CLAUDE.md`). The aggregate type maps to `AggregateTypeTables.of(type)`, which refuses an aggregate type too long
for the derived names.

### 2.3 Payload and metadata bytes: what "equal" means

The old default column type is `jsonb`. `jsonb` does not keep the bytes it was given: it drops whitespace, reorders keys
(shorter keys first) and keeps only the last of any duplicate keys. Whatever an old-engine reader gets back is the
column's text output (`col::text`), which is `jsonb`'s canonical rendering with `", "` and `": "` separators, not
Jackson's compact output. Those original bytes exist nowhere any more, and the old engine never returned them.

So the copy writes `old.event_payload::text` into the new `json` column. A `json` column stores its input text unchanged,
so `new.event_payload::text = old.event_payload::text` byte for byte, for `json` and `jsonb` sources alike. That is the
equality I8 and §6 check. A reader on the new engine therefore gets exactly the bytes an old-engine reader got.
Deserialisation through `EssentialsObjectMappers` does not depend on key order or whitespace, so the frozen wire format
(root `CLAUDE.md`) is untouched: the stored JSON has the same properties and values.

One visible effect: after cut-over, a table copied from `jsonb` holds old events in `jsonb` form and new events in
Jackson's compact form. Only code that hashes payload text could notice, and the release notes say so (phase 10). The
copy never re-serialises: no `::jsonb` round trip and no Jackson in the path. Mutant `PAYLOAD_VIA_JSONB` (§9.1) checks
that verification catches a re-cast.

### 2.4 Ids, revision, tenant, causation and correlation

| Column | Copy | Pre-flight refusal (§3.1) |
|---|---|---|
| `aggregate_id` | `::text`. A `uuid` source yields lower-case canonical text | None. For a `uuid` source the report warns that the adapter's `AggregateIdSerializer` must produce lower-case canonical text, or `fetchStream` will not find the stream. §10.3 checks this through the adapter |
| `event_id` | `::uuid` | Any value that is not a lower-case canonical UUID (`!~ '^[0-9a-f]{8}-…$'`). An upper-case UUID would change `EventId` equality after the move, so it is refused, not normalised |
| `correlation_id` | `::uuid`, null kept | As `event_id` (the adapter rejects non-UUID correlation ids too, `EventLogEventStore.java:344`) |
| `caused_by_event_id` | `::uuid`, null kept | **Proposed:** a non-UUID cause is copied as null and counted in the report. This matches the adapter's rule (`:380-389`) and the old engine's own rule for `uuid` columns. Open question 5 |
| `event_type` | the `el_event_types` id of the same name (§3.4) | More than 32 767 distinct names in total |
| `event_revision` | `::smallint` | A value that does not parse or does not fit in `smallint` |
| `timestamp` | unchanged (`timestamptz`) | — |
| `tenant` | unchanged text | — |
| `event_order`, `global_order` | unchanged | `global_order` identity cache ≠ 1 on the source (§3.3) |

Causation and correlation are kept as values. Nothing is re-derived, and the causation index is maintained by the
insert.

## 3. The copy

### 3.1 Pre-flight (read only, before anything is written)

For each `SourceTable`, the tool reads:

- the column types from `information_schema.columns`, which overrule what the plan says;
- the identity sequence's cache, `pg_sequences.last_value` and `max(global_order)`;
- §2.4's refusals, each as one counting statement over the table. These are full scans, run online, and each is
  reported with up to 10 sample `global_order`s.

It then checks the target: the aggregate type is not registered there, or if it is, its event table is empty or holds
only rows of an earlier run of this migration (§3.7). Pre-flight writes a report and stops on any refusal. Nothing is
created before it passes.

### 3.2 Same-database `INSERT … SELECT`, not `COPY`

Plan §19 item 20 names `COPY` through `CopyManager`. **Proposed:** when the old and new tables live in one database,
which is the normal case because the new engine runs on the application's `DataSource`, the copy is one server-side
statement per batch:

```sql
INSERT INTO el_<type>_events (global_order, event_order, timestamp, event_id, caused_by_event_id, correlation_id,
                              event_type, event_revision, aggregate_id, event_payload, event_metadata, tenant)
SELECT o.global_order, o.event_order, o.timestamp, o.event_id::uuid, <cause or null>, o.correlation_id::uuid,
       t.id, o.event_revision::smallint, o.aggregate_id::text, o.event_payload::text::json, o.event_metadata::text::json, o.tenant
FROM <old table> o JOIN el_event_types t ON t.name = o.event_type
WHERE o.global_order > ? AND o.global_order <= ?
ORDER BY o.global_order
```

No event byte crosses the network or passes through the JVM. `COPY` would move every payload out to the client and back,
and would still need a staging table for the type join. The spike (§10.1) measures both arms anyway, and `COPY` is kept
for a cross-database move if that is ever wanted (open question 2). Batches are ranges of `global_order`
(`settings.batchSize`, default 10 000 values, set by the spike). A range made up mostly of holes therefore copies few
rows; the next range follows at once.

### 3.3 Online epochs: copying only what can no longer change

Old-engine writers do not take an xid before they draw a `global_order` (risk 9). A range copied while they run can
therefore miss a row that commits later into a value below the copied maximum. Recording the holes and copying them
again later does not scale: under contention the old engine burns about 466 values per 1 000 appends (P0.0).

**Proposed rule, an epoch:**

1. Read `M = max(global_order)` of the old table, and `T0 = clock_timestamp()`.
2. Wait until no other transaction that started at or before `T0` is still running (`pg_stat_activity`,
   `xact_start <= T0`, excluding this backend). This is the wait `CREATE INDEX CONCURRENTLY` uses for old snapshots.
3. Copy `(copied_through, M]` in batches, then set `copied_through = M`.

Why it is complete: with an identity cache of 1, values are handed out in increasing order across sessions, so every
value `v ≤ M` was drawn before the row `M` was, that is, before `T0`. The transaction that drew `v` was running at `T0`
or had already ended. After step 2 every such transaction has ended. A value ≤ `M` without a row is then a permanent
hole, and no late commit can land in `(copied_through, M]`. Copied ranges are final, so they can also be verified
online (§6).

The wait is conservative: an idle-in-transaction session or a long report query also holds it up. It is bounded by
`settings.epochWaitTimeout` (default 10 min). On timeout the epoch copies nothing, and the report names the blocking
`pid`, `application_name` and `xact_start`. The operator runs epochs until the remaining delta is small. Each epoch logs
its delta and copy rate, which also tells the operator how long the stop will be.

Mutant `EPOCH_WITHOUT_WAIT` (§9.1): a writer holds a value below `M` across an epoch and commits afterwards. The mutant
loses the row and verification must catch it.

### 3.4 Event types

Before each batch the tool reads the batch range's distinct `event_type` names, a scan the batch's insert repeats while
the pages are still in cache. Names it has not cached are interned with `EventTypeRegistry.idOf` in their own committed
transaction, as engine decision 2 requires. The insert joins on `el_event_types.name`. A row whose type has no id would
fall out of the join, so the insert's row count is checked against a `count(*)` of the same range, in the same
transaction. A mismatch aborts the batch, and mutant `TYPE_JOIN_DROPS_ROW` must be caught.

### 3.5 The final pass under the stop

1. The operator stops every old-engine node (risk 9). The tool cannot tell an old-engine writer from any other client,
   so it also enforces the stop:
2. In one transaction, the tool runs `SET LOCAL lock_timeout = <settings.lockTimeout>`, then
   `LOCK TABLE <old tables> IN SHARE MODE`, for all types in one fixed order. `SHARE` conflicts with the
   `ROW EXCLUSIVE` lock that every `INSERT` takes at statement start, before it draws a value. Acquiring it therefore
   waits for every in-flight insert to end and blocks new ones. Readers are not blocked. The lock is the only thing the
   migration ever does to the old tables beyond reading, and it ends with the transaction. If the lock times out, the
   report says "writers still running" and nothing is copied.
3. Under the lock, in the same transaction: copy `(copied_through, max]`, write the heads (§3.6), reset the identity
   sequences (§3.6), verify the delta windows (§6), import resume points (§4), and set the migration state to
   `CUT_OVER` (§3.8). Then commit.
4. The application starts on the new engine.

Doing everything in one transaction keeps the cut-over atomic. A failure anywhere rolls the target back to the state
after the last epoch, and the old engine can be started again; aborting is a configuration change (§12.4). The
transaction holds the `SHARE` locks for as long as the delta takes, which is the stop the spike measures (§10.1).

A forgotten old node that is still running blocks on the lock and appends after it is released. Its events then exist
only in the old table. The command `verify --after-cutover` (§6.3) finds old-table rows above the copied maximum and
reports them loudly. Revoking `INSERT` on the old tables would prevent this, but it is a change to the old schema's
grants, so the tool only prints the `REVOKE` statements for the operator (open question 6).

### 3.6 Heads and identity sequences

- **Heads:** per type, `INSERT INTO el_<type>_heads (aggregate_id, version) SELECT aggregate_id, max(event_order) FROM
  el_<type>_events GROUP BY aggregate_id ON CONFLICT (aggregate_id) DO UPDATE SET version = EXCLUDED.version`. Online
  epochs maintain the heads per batch, over the batch's aggregates only. The final pass redoes the heads of the delta's
  aggregates. Mutant `HEADS_NOT_WRITTEN`: the first adapter append to an existing stream must fail the §9.1 test.
- **Identity:** `setval(pg_get_serial_sequence('el_<type>_events', 'global_order'), S, true)` with
  `S = greatest(old sequence last_value, max copied global_order)`, read under the `SHARE` lock. Taking the old
  sequence's `last_value`, not the highest copied row, matters: values burned at the old table's end (rollbacks,
  optimistic-concurrency losers, a sequence jump) can put an old resume point above the highest row. A new sequence that
  restarted at the highest row would hand out values below that resume point, and the subscription would skip them.
  Mutant `SEQUENCE_AT_MAX_ROW` (§9.1) must lose an event. `setval` changes neither the cache (still 1, as start-up
  checks) nor any DDL. It is issued from the migration module's storage class, and the schema rules see no DDL.
- Holes, permanent gaps and jumps are copied as what they are: absent values. The new engine needs nothing for them.
  None is held by a running writer, so the reader's watermark passes them at once (§4.9: no tombstones). The value
  space between the copied maximum and `S` is one more jump, handled by §4.8.

### 3.7 Resumability and idempotency

Copy progress lives in **`el_migration`** (§3.8): one row per aggregate type with `copied_through`, the epoch count,
the state and the source table name. Every batch updates the row in the same transaction as its insert, so a crash
loses a whole batch and its checkpoint together. A rerun starts at `copied_through`. The insert has no
`ON CONFLICT DO NOTHING`: a primary-key conflict means that someone other than this migration wrote the table, and the
run stops instead of hiding a divergence. Mutant `CHECKPOINT_OUTSIDE_BATCH` (the checkpoint commits on its own, before
the batch) loses a batch on a crash injected between the two, and verification must fail.

`synchronous_commit = off` is set per batch transaction (**Proposed**). A batch lost to a server crash is lost together
with its checkpoint and copied again. The final pass keeps the server default.

### 3.8 The migration state, and the engine's guard

Any new-engine node that runs before cut-over is dangerous. Its reader would see copied rows appear below its watermark
and treat them as retired holes. Its appends would draw values that a later epoch then collides with. **Proposed
engine change** (unit 9-B; the engine is a new module, so it is not on §13's list):

- `el_migration(aggregate_type text PRIMARY KEY, state text CHECK (state IN ('COPYING', 'CUT_OVER')), source_table
  text, copied_through bigint, epochs int, started_at, cut_over_at, report json)`. It is created by the engine's
  `EventLogSchemaContributor` with the fixed schema, so the engine owns the DDL and the migration module only writes rows.
- `EventLog.registerAggregateType` refuses a type whose `el_migration` row is in `COPYING`, with a message naming the
  migration. That one indexed read at registration is the guard. Mutant `GUARD_SKIPPED`.
- `CUT_OVER` rows are kept as the record of the move (the report holds the hashes). Rows are never deleted by the
  engine.

## 4. Importing resume points (optional)

### 4.1 Mapping

The old key `(subscriber_id, aggregate_type)` maps to a new progress row only through an explicit
`ImportedSubscription(oldSubscriberId, aggregateType, SubscriptionDefinition, List<String> instanceNames)`. The
definition supplies the exclusive flag, mode and model, which the old row does not have. A non-exclusive definition needs
the instance names that will run it, because the new model keeps one row per instance (§19 item 17). Every instance gets
the same imported point. An old subscriber with no mapping is listed in the report and not imported. Its new subscription
then starts where its `StartFrom` says.

### 4.2 The value: the open-gap hand-over

Let `R` be the old resume point. `transient_subscriber_gaps` can hold values below `R` that the subscriber has not been
given yet: transient gaps whose fill committed but was not yet delivered (§12.4). The import runs under the final pass's
lock, after every old writer has ended. At that moment every open transient gap of the subscriber is in one of two
states: it **has a row**, and the subscriber may never have seen it, or it **has none**, and it is a permanent hole. The
imported value is therefore

```
I = least(R, min{ g ∈ transient_subscriber_gaps(subscriber, type) : a row with global_order g exists })
```

This is what I8 asks for, and slightly tighter than "the lowest open gap" in §12.4: an old gap that never filled does
not force a replay. Every event in `[I, R)` is delivered again, which is at-least-once as on the old engine. The report
gives each subscription's replay length `R - I` in values and in rows, so a gap filled long ago, and the large replay it
causes, is seen before the cut-over. The new model has no per-subscription pending set: progress is one `resume_from`,
and decided §19 item 17 stores no open-page state. Replaying from `I` is therefore the only hand-over that loses nothing.

**Operator opt-in to `R` (§18).** A mapping may set `trustOldResumePoint` (YAML `trustOldResumePoint: true`). The
operator then states that the old subscriber has already handled the events that filled its open transient gaps, and
the import writes `R` instead of `I`. This trades I8 for a smaller replay, on the operator's word and not on anything
the tool can prove (§17.4). The report records the opt-in and lists the filled gaps it skips, the cut-over logs them at
WARN, and the read-back check asserts `resume_from = R` for such a mapping. Mappings without the opt-in keep `I`. The
import preview and the report show, per mapping, both `R` and the I8-safe `I` with the rows `I` replays, and the preview
flags a safe replay of more than 10 000 rows with a hint about the opt-in.

Mutant `IMPORT_RESUME_UNCHANGED` (`I = R`) is I8's named must-fail (§9.2). Mutant `IMPORT_LOWEST_GAP_UNFILTERED`
(`I` = the lowest open gap, filled or not) is *not* a correctness mutant. It is the stricter rule §12.4 states, and it
only replays more. The test asserts the replay length to show the tighter rule is in use.

### 4.3 Writing the progress row

**Proposed engine addition** (unit 9-B): `EventLogAdmin.importProgress(SubscriptionDefinition, String instanceName,
long resumeFrom, Connection)`. It runs on the caller's connection and never commits, like `reset(key, from, Connection)`.
It inserts the progress row with the definition's mode, model, exclusive flag and filter digest, and with
`resume_from = I`. `reset_epoch` is 0, and the lease columns are null, so the first `LEASE_CLAIM` takes it: its condition
is `lease_owner IS NULL OR …` (`EventLogStorage.java:129`). With an existing row it does nothing and returns that row's
`resume_from`. The tool treats an equal value as an idempotent rerun and refuses a different one. Because the row
exists, the subscription's `StartFrom` is not consulted (`PROGRESS_START` keeps the stored `resume_from`). The definition's
own mode and model are written, so the first start does not log a mode change.

The progress SQL therefore stays in `EventLogStorage`, and the migration module never writes `el_progress` itself.

### 4.4 What the import cannot recover, and reports instead

- **Late fills of permanent gaps below `R`.** The old engine gave those values up and never delivered them. They are
  copied (they are events), but the import does not deliver them: they are below `R`, and replaying from them would
  re-run everything after. The report lists their count per subscription and type. Open question 7.
- **A source without `transient_subscriber_gaps`** (an application on `NoEventStreamGapHandler`). `I = R`, with a
  report line saying the old engine tracked no gaps, so late commits it skipped cannot be identified.
- **CDC consumer positions** (`CdcConsumerGroup`). These are not `durable_subscriptions` rows and are not imported. The
  report lists them.
- **In-memory old state** (gap fills awaiting acknowledgement). It is gone when the old nodes stop. The `[I, R)` replay
  covers what had been persisted.

## 5. The procedure, as an operator runs it

| Step | Command (CLI `java -jar …-migration.jar <cmd> --config migration.yml`, or the `Migration` API) | Old engine | Writes |
|---|---|---|---|
| 1 | `preflight` | running | nothing (report) |
| 2 | `prepare`: the new schema through the engine's contributor (schema mode as configured), `registerAggregateType` per type, `el_migration` rows `COPYING` | running | target only |
| 3 | `copy` (one or more epochs; reruns resume) | running | target only |
| 4 | `verify` (copied ranges, online; optional) | running | report |
| 5 | Stop every old-engine node | stopped | — |
| 6 | `cutover`: §3.5, one transaction | stopped, tables `SHARE`-locked | target only |
| 7 | Start the application on the new engine | — | — |
| 8 | `verify --after-cutover` (any time; finds late old-table rows) | — | report |

Until step 7's first append, abandoning the move is a configuration change. The old tables are untouched, and the
target can be dropped. After the first append there is no way back short of a restore (§12.4).

## 6. Verification

### 6.1 What is compared

Per aggregate type: the row count; `min` and `max(global_order)`; and the hash of every row, aggregated per window of
`global_order` values (default 100 000):

```
md5(string_agg(md5(concat_ws('|', global_order, aggregate_id::text, event_order, event_id::text, caused_by::text,
                              correlation_id::text, <type name>, event_revision::text,
                              (extract(epoch FROM timestamp) * 1e6)::bigint, event_payload::text,
                              event_metadata::text, coalesce(tenant, '∅'))), '' ORDER BY global_order))
```

The same expression runs on both sides. On the new side the type name comes from a join on `el_event_types`, and the
cause is the copied value (a non-UUID cause that §2.4 nulled is compared as null, and its count is checked against the
pre-flight count). Windows that differ are bisected down to the rows that differ, and the report names them. The plan's
checksum covers `(global_order, aggregate_id, event_order, event_id)` and the payload. This one covers every column, at
the cost of the row hash, which the spike measures.

Then the structure is checked: each identity sequence's `last_value` ≥ `S` (§3.6); each head's `version` equals its
stream's `max(event_order)`, and there are as many heads as distinct `aggregate_id`s; each imported progress row has
`resume_from = I ≤ R`, and `I ≤` every open transient gap of that subscriber that has a row. Verification fails on any
mismatch, and the cut-over transaction then rolls back.

### 6.2 Online and under the stop

Ranges copied by an epoch are final (§3.3), so `verify` can check them while the old engine runs, and the result is
stored with the window in `el_migration.report`. Under the stop, the cut-over verifies only the windows the final pass
touched, plus the structural checks. This keeps the stop proportional to the delta, not to the table.

### 6.3 After the cut-over

`verify --after-cutover` compares the old tables' `max(global_order)` and `count(*)` above the recorded copied maximum
with zero. A row found there was written by an old node that should have been stopped. Such a row is reported with its
`global_order` and timestamp, and the tool does not try to merge it.

## 7. Failure cases

| Case | What happens | Bound |
|---|---|---|
| Pre-flight finds a non-UUID event id, an unparseable revision, too many types, cache ≠ 1, or a type name too long | Report, exit, nothing written | §3.1 |
| Crash during an epoch | The batch and its checkpoint are lost together; the rerun resumes at `copied_through` | §3.7 |
| A long transaction holds the epoch wait | Times out, copies nothing, names the blocker | §3.3 |
| Old writers still running at cut-over | `lock_timeout`, nothing copied, "writers still running" | §3.5 |
| Old node starts after the cut-over | Its events stay in the old table; `verify --after-cutover` reports them | §6.3 |
| New-engine node started before cut-over | `registerAggregateType` refuses while `COPYING` | §3.8 |
| Someone else wrote the target event table | Primary-key conflict stops the run | §3.7 |
| Verification mismatch at cut-over | The transaction rolls back to the last epoch's state; the report names the windows and rows | §6.1 |
| A filled transient gap far below `R` | Long replay `[I, R)`, shown in the report before the cut-over | §4.2 |
| Progress row already exists with another value | Import refused for that subscription | §4.3 |
| `jsonb` source | New table holds `jsonb`-rendered text for old events; equality is to `::text` | §2.3 |
| `uuid` aggregate ids with a serializer that does not produce lower-case text | Report warns; `fetchStream` through the adapter finds nothing for that stream; caught by §10.3's sample loads | §2.4 |

## 8. Resource cost

| | Connections | Server | Old engine impact |
|---|---|---|---|
| Pre-flight | 1 | One full scan per refusal check per table | Read I/O |
| Epoch | 1 | One range read and insert per batch, the index maintenance of 4 indexes (PK, stream order, event id, partial cause), WAL ≈ the copied size plus indexes | Read I/O and buffer churn; the wait does not block writers |
| Online verify | 1 | One range read per window on each side, and an md5 per row | Read I/O |
| Cut-over | 1 | Delta copy, heads, `setval`, delta verify, import, in one transaction | **All old appends blocked** for its duration |
| Disk | — | The new tables ≈ the old ones' size (`json` text instead of `jsonb` can be larger or smaller), plus WAL | — |

No thread or held connection is added to the engine at runtime. The guard is one indexed read per `registerAggregateType`.

## 11. Against the invariants

- **I8.** This phase (§9.2). A mapping with the `trustOldResumePoint` opt-in (§4.2, §18) gives I8 up for that
  subscription on the operator's statement that its gap fills were handled; I8 holds for every other mapping.
- **I1, I3.** Copied holes are permanent at cut-over and never held by a running writer, so the reader retires them at
  once (§3.6). The engine guard keeps every reader off a table while it is being filled (§3.8).
- **I2.** Per-aggregate order is the copied `event_order`, unchanged. Replays of `[I, R)` re-deliver in order.
- **I4.** No new-engine writer runs during the copy (§3.8). The copier's explicit values are below every value the
  identity hands out after `setval`.
- **I5, I6, I16.** Imported rows carry no lease (`lease_owner` null) and epoch 0. The first claim fences them as usual.
  An import never overwrites an existing row.
- **I10.** Heads are exact (§3.6), so the first append's optimistic check is right (`MigrationHeadsIT`).
- **I12, I14.** Unaffected: a replay of `[I, R)` is ordinary delivery.

## 16. Spike results (9-A)

**Run:** 2026-11-17, `MigrationCopySpikeIT` (package `…eventlog.integration.spike`, module
`postgresql-event-log-integration`, runs only with `-Dspike.run=true`). Raw results:
`target/spike-results/p9-a-bulk.txt` and `p9-a-online.txt`. The spike is throwaway code. The copy SQL is hand-written
in the test, and unit 9-C writes the real one.

### 16.1 Setup

- PostgreSQL 18.4 (the repo's pinned Testcontainers image, aarch64), `fsync=on` (checked with `SHOW fsync` and recorded
  per arm), server defaults otherwise (`shared_buffers` 128 MB, `max_wal_size` 1 GB). A fresh container per (run, arm),
  two runs per arm, with arm order reversed in run 2. The client is on the same VM.
- **Source:** 10 aggregate types (the trading demo's names), created by `PostgresqlEventStore` as the starter wires it
  (`TEXT` ids, `JSONB`, `TestPersistableEventMapper`, so causation, correlation and metadata are set). Each type gets 3
  real streams of 10 events appended through `appendToStream`. A bulk SQL generator then adds rows of the same shape:
  the same `FQCN:` event type names (3 names), revision `'1'`, the same metadata and the same payload keys at about
  980 B of `jsonb`. Streams have 10 events each, a third of the rows have a cause, and correlation ids are canonical
  UUIDs. Every fifth `global_order` value is a hole (20 %), and 7 values are burned at each table's end. The shape check
  (a real row against a generated row: column types, keys, sizes, metadata) is recorded per arm and matched in every arm.
- **Size: 1 million events only** (100 000 per type, 1 558 MB of source tables). **10 M and 30 M were not run.** The VM
  had 5.2 GB of free disk, and a 1 M arm already took it down to 1.2 GB free at its lowest (source + target + WAL).
  10 M needs about 15 GB more. The bulk rates below are flat from 1 000- to 100 000-value batches and CPU-bound, so I
  expect 10 M to scale about linearly (about 2 min per bulk copy), but that is not measured.
- **Target:** `EventLog.registerAggregateType` for each type. Event types are interned with `EventTypeRegistry.idOf`
  per batch's distinct names (§3.4). Each batch runs in its own transaction with `synchronous_commit = off`: a range
  `count(*)`, the `INSERT … SELECT` of §3.2 (with the cause regex), the row-count check, the batch's heads upsert and a
  checkpoint row (`spike_migration`, standing in for `el_migration`, which 9-B is building).
- **Caveat:** this is a shared 8-CPU dev VM, with another agent building and running ITs at the same time. Treat the
  absolute numbers as indicative. The comparisons within a run are more reliable.

### 16.2 Bulk copy and online verify (1 M events, 10 types)

| Arm | Run | Copy events/s | Server CPU | WAL/event | Target/source size | Verify events/s |
|---|---|---|---|---|---|---|
| `INSERT … SELECT`, batch 1 000 | 1 / 2 | 87 151 / 101 998 | 11.1 / 9.7 s | 1 500 B | 1 353 / 1 558 MB = 0.87 | 109 529 / 112 938 |
| `INSERT … SELECT`, batch 10 000 | 1 / 2 | 88 003 / 97 582 | 10.8 / 10.0 s | 1 500 B | 0.87 | 104 277 / 114 977 |
| `INSERT … SELECT`, batch 100 000 | 1 / 2 | 88 813 / 86 063 | 10.5 / 11.2 s | 1 500 B | 0.87 | 110 598 / 90 539 |
| `COPY` out + in to temp staging, batch 10 000 | 1 / 2 | 66 877 / 65 393 | 14.6 / 14.9 s | 1 500 B | 0.87 | 116 730 / 116 359 |

- The batch size does not matter in this range: the three `INSERT … SELECT` sizes are within each other's noise. The

- `COPY` is about 30 % slower, because every byte crosses to the client and back, and `COPY … FROM STDIN` into staging

- Building the source (the generator's `INSERT … SELECT` into the old table, with its three indexes) ran at 44 000 to
  52 000 rows/s. That is the old schema's own insert cost, for comparison.
- The target is 13 % smaller than the source (`json` text instead of `jsonb`, and the `smallint` type and revision). WAL
  is 1 500 B per copied event, about the target's size plus full-page writes.
- Every arm verified equal over all 20 windows (§6.1's hash, every column), with heads and sequences correct.

### 16.3 Online epochs against a running old engine (batch 10 000)

The old engine appended 1 event per new aggregate through `appendToStream`, paced at 1 000 events/s on 4 threads over
the 10 types. There was a 5 s warm-up, a 30 s baseline, epochs until the delta was under 5 000 rows, then a 30 s
baseline after, then the appender stopped and a catch-up epoch ran.

| Run | Epoch 1 (bulk) | Epoch 2 | Epoch 3 | Epoch waits | Append p99 baseline before / during epochs / after | p99 ratio (during ÷ mean of baselines) |
|---|---|---|---|---|---|---|
| 1 | 1 035 004 rows in 10.62 s (97 491/s) | 10 630 rows in 0.17 s | 173 rows | 0.3–2.1 ms, 0 polls | 1.23 / 3.43 / 2.58 ms | **1.80** |
| 2 | 1 035 002 rows in 10.41 s (99 425/s) | 10 417 rows in 0.15 s | 161 rows | 0.2–1.8 ms, 0 polls | 2.05 / 4.57 / 2.44 ms | **2.04** |

- The epoch wait (§3.3) is negligible when no long transaction is open: the appender's transactions last under 1 ms,
  so the first check already finds none. A held transaction was not part of this spike. That case is
  `MigrationEpochIT` in 9-C.
- The copy rate under load equals the bulk rate. The epochs converge geometrically (1 M → 10 K → about 170 rows),
  as the 1 000 ev/s write rate predicts.
- The p50 of the appends did not get worse (0.34 ms during the epochs against 0.54–0.63 ms in the baselines). The p99
  roughly doubled, from 1.2–2.6 ms to 3.4–4.6 ms. The copy saturates one server core and writes WAL at about
  140 MB/s, which competes with the appends' commit `fsync`s.

### 16.4 Cut-over (final pass under `SHARE` locks)

The delta was 10 000 events (1 000 per type, 100 streams of 10 per type) appended by the old engine after the catch-up
epoch, with 50 `durable_subscriptions` rows (5 per type) and their transient gaps (one hole and one filled value each).
Everything ran in one transaction, per §3.5:

| Step | Run 1 | Run 2 |
|---|---|---|
| `LOCK TABLE … IN SHARE MODE` (10 tables, no writers) | 0.5 ms | 0.2 ms |
| Copy delta + heads (10 batches) | 140.5 ms | 156.5 ms |
| `setval` × 10 | 2.6 ms | 3.1 ms |
| Verify the touched 100 000-value windows (§6.2 as written; about 285 000 rows per side) | 2 269 ms | 2 282 ms |
| *Alternative:* verify exactly the delta range (10 000 rows per side) | 92 ms | 92 ms |
| Structural checks on the delta's aggregates and sequences | 253 ms | 228 ms |
| Import 50 subscriptions (§4.2 value, one `INSERT … SELECT` per type into `el_progress`) | 3.8 ms | 3.2 ms |
| State update + commit | 2.0 ms | 1.2 ms |
| **Stop as designed** | **2 672 ms** | **2 674 ms** |
| Stop with exact-range verify instead | 494 ms | 484 ms |

The import writes `el_progress` directly, because `EventLogAdmin.importProgress` is 9-B's work. Its cost is negligible

### 16.5 Against the pass lines (§10.1)

| Pass line | Result |
|---|---|
| Bulk copy ≥ 20 000 events/s for the chosen arm | **Met**, 86 000–102 000 events/s (`INSERT … SELECT`, 1 M). 10 M and 30 M not measured (disk) |
| Old-engine append p99 during an epoch ≤ 1.5× without | **Missed**: 1.80× and 2.04×. In absolute terms the p99 went from about 2 ms to 3.4–4.6 ms, and p50 did not move |
| Cut-over of a 10 000-event delta over 10 types ≤ 5 s, incl. delta verify and import of 50 subscriptions | **Met**: 2.67 s as designed, 0.49 s with exact-range verify |
| Online verify ≥ 50 000 events/s | **Met**: 90 000–137 000 events/s (both sides hashed) |

| Recorded: target size against source size | 0.87 |
| Recorded: time per epoch wait | 0.2–2.1 ms with no long transaction open |

**About the missed line:** §10.1 says that only the cut-over line gates users, and that a miss is recorded with a
decision. The cause is server-side contention: one copier backend at full speed. It is not lock interference, since
the copy takes no lock that the appends wait on. **Recommended decision:** accept the doubling of p99 as it is, and give 9-C
an optional `settings.maxEventsPerSecond` throttle between batches (default unlimited at the time; 25 000 since §18) for operators whose latency
budget is tight. A copy throttled to 20 000 events/s still moves 10 M events in under 9 minutes. The spike did not
measure a throttled arm.

### 16.6 Recommendations for 9-C

- **Arm:** same-database `INSERT … SELECT` (§3.2), as proposed. `COPY` costs about 30 % more and is only needed for a
  cross-database move.
- **Batch size:** **10 000** `global_order` values (the proposed default). Rates were flat from 1 000 to 100 000.
  10 000 keeps each batch transaction short: about 0.1 s and 12 MB of WAL. That bounds what a crash re-copies and how
  long a batch holds its snapshot, and it gives the throttle a fine step.
- **§6.2 delta verify:** verify exactly the range the final pass copied (`(copied_through, max]`), not the aligned
  100 000-value windows the delta touches. The aligned windows made the stop 2.67 s instead of 0.49 s for the same
  10 000-row delta, and their cost grows with the window size rather than the delta. Ranges below `copied_through` were
  already verified online and are final (§3.3), so nothing is lost. **Proposed change to §6.2.**
- The structural check over the delta's aggregates (230–250 ms) is the next-largest step. It reads every event of each
  touched stream, and could be restricted to the head rows the final pass upserted.

### 16.7 Decisions on the spike (2026-11-17)

Claude settled these under the standing instruction to ask only on genuine forks:

- **Arm and batch size:** same-database `INSERT … SELECT`, batch 10 000 `global_order` values, as §16.6 recommends.
- **§6.2 delta verify:** the final pass verifies exactly the range it copied, `(copied_through, max]`. Ranges below
  `copied_through` are final (§3.3) and were verified online, so the aligned windows add stop time without adding
  safety.
- **Append p99 during an epoch (missed, 1.80× and 2.04× against 1.5×):** not decided yet. 9-C adds an optional
  `maxEventsPerSecond` throttle on the online copy (unthrottled by default), and 9-G measures the line again with the
  throttle set. If the line is still missed with a throttle that keeps the copy at or above 20 000 events/s, the miss
  goes to the maintainer with the numbers.
- **10 M and 30 M sizes:** not run on the development VM (disk); they belong to the dedicated-server rerun.

### 17.3 The trading demo (§10.3)

**How the source was produced.** `run-load.sh` needs the demo's `simulators` profile, whose images
(`exchange-simulator:dev`, `payment-gateway:dev`) are not in this repository and were not built on the VM. So the real
application ran on the old engine (unchanged code and configuration: profile `compose` with Docker Compose support off,

through its own in-application generators over HTTP: ledger load (300 accounts) and order flow (100 customers) twice,
funding load (100 customers), three instruments registered, 20 accounts' books rolled to a second generation (closing
books) and 3 closed generations archived. The source then had 387 `Accounts` snapshots, 3 archives, 89 permanent
gaps, about 18 500 transient subscriber gaps and 27 `durable_subscriptions` rows; holes were 1 132 in `Accounts` and
2 042 in `Orders`. The demo was stopped and copied with `CREATE DATABASE … TEMPLATE …`.

**Not covered:** `ReconciliationCases`, `TradeSettlements` and `UnknownExchangeOrders` have no events, because only the
simulators' webhooks create them. Their tables, subscriptions and resume points were migrated (empty), and step 4's
append and delivery checks ran on them, but no copied row of those types was compared.

**Step 2.** The demo ran again on the copy under the same generators (about 1 100 events/s) while the harness
`TradingDemoMigrationGateSpikeIT` (integration module, `spike` package, `-Dspike.demo.phase=online|cutover`) ran the CLI
in-process with a generated YAML: `preflight`, `prepare`, `copy --until-caught-up --max-delta 500` (51 epochs in all;
the first call took 86 s and 49 epochs to catch up under the writes, with epoch waits of up to 7.1 s on the demo's own
transactions), then `verify`. After the demo was stopped: `import-preview`, `cutover` with an import of every
`durable_subscriptions` row (views `CONTIGUOUS` with `IN_HANDLER_TRANSACTION`, routers and processors `FRESH` with
`PERIODIC`, all exclusive), `verify --after-cutover`, `verify --all`.

**Step 3, verifies equal: met.** §6.1 equal over all 10 types (268 441 events), zero late rows after the cut-over.

**Step 4, resumes without loss: met.**

- Every copied stream loaded through `EventLogEventStore.fetchStream` (`Accounts` 1 421 streams and 181 347 events,
  `Orders` 16 000 and 80 000, the others smaller), with global order, event order and event id equal, and every payload
  equal to the old row's as a Jackson tree.

### 17.4 Why the import replays so far back (follow-up)

**Question.** In §17.3, `AccountActivityProjection` was imported with `I` = 73 490 against `R` = 187 368, and three
`Orders` views each replayed about 43 000 rows. Is the filled transient gap at `I` an event that the old engine never
delivered, or one that it delivered while the gap row stayed behind?

**How it was checked.** The demo source was rebuilt with a shorter run (the same application, stubs and generators,
about 2 minutes of load). The gap tables were read while the demo ran and again after a graceful stop. The source of the
§17.3 run was removed after that gate, so its per-subscriber numbers come from the import report.

**(a) Delivered, row left.** `AccountActivityProjection` had 2 filled gaps, at `global_order` 4 385 and 4 386. Both
are `FundsHeld` events of streams that have 130 to 140 later events. `projection_account_activity` has the row for
both, keyed by `(account_stream_id, event_order)`, and only that projection writes that table. So the projection
handled both events, but their transient gap rows remained. The rows were still there after the graceful stop. The
events were appended 30–50 ms before their gaps were first discovered, so they were late commits that the subscriber
passed and then received as gap fills.

**(b) The old engine's gap handling** (`PostgresqlEventStreamGapHandler`, `GapFillsAwaitingAcknowledgement`,
`CdcEventStore`; read only):

- **A gap row is deleted** in three ways:
  - A poll whose gap query included the gap finds its event, and the gap is not a fill still awaiting
    acknowledgement (`reconcileGapsAndReport`).
  - The subscriber acknowledges a delivered fill (`resolveFilledGaps`). This happens in the subscriber's unit of work,
    atomically with the handling when there is one, and otherwise in a unit of work of its own.
  - A reset deletes it.
- **Gap recording under CDC is deferred.** Under CDC, which the demo runs with, a narrow gap is kept in memory and
  written at the next resume-point save or when the subscription ends (`recordDeferredGaps`). A fill that arrives while
  its gap is only in memory is meant to need no row deletion.
- **A gap is promoted to permanent** only after its first discovery is older than the threshold (120 s by default), and
  only by a poll whose query asked for that gap (the query includes at most 50 promotable gaps per poll), or when CDC's
  delivery tracker gives up on it.

I did not find the path that leaves the row of a delivered fill. The pattern is that only view processors
(`ViewEventProcessor` and its partitioned variant) were affected; no router or event processor was. Finding the cause in
the old engine is outside phase 9.

**(c) Open and filled gaps per subscriber.**

| Run | Subscriber | Open transient gaps | With a row in the copy (filled) |
|---|---|---|---|
| §17.3 | `AccountActivityProjection` | 1 998 | 4 |
| §17.3 | `UnclearedDepositsProjection` | 1 953 | 3 |
| §17.3 | other 4 `Accounts` subscribers | 1 771–1 983 | 0 |
| §17.3 | `LateFillsProjection`, `OrdersProjection`, `SettlementFillsProjection` | 423, 343, 298 | 1 each |
| §17.3 | other 3 `Orders` subscribers | 299–619 | 0 |
| §17.3 | `Deposits`, `Withdrawals`, others | 0 | 0 |
| rebuild | `AccountActivityProjection`, `AccountOverviewProjection`, `PositionsProjection` | 1 064–1 067 | 2, 3, 5 |
| rebuild | the other 17 subscribers | 9–2 049 | 0 |

In the rebuild, the unfilled open gaps match the holes exactly: 1 062 holes in `Accounts` and 2 049 in `Orders`. None of
them was older than the 120 s promotion threshold yet. A handful of filled gaps per subscriber is enough to move `I`
back across most of the stream, because `I` is the lowest filled open gap (decision 8).

**A signal for skipping such gaps.** The old tables hold no reliable one. The engine records no delivery per event: the
only record is the resume point, and `R` is past the gap whether or not the fill was delivered. The two candidates fail:

- An event timestamp earlier than the gap's `first_discovered` is also true of a late commit that was never delivered,
  because the timestamp is taken before the commit.
- A later event in the same stream below `R` shows that the event had committed before the subscriber passed that later
  event. It does not show that the gap query picked the event up.

The only proof is application-level, here the view's own row. So the import cannot skip these gaps safely by itself.
The options are an explicit per-mapping operator choice (for example "import `R` and ignore filled transient gaps" for
an idempotent view, with the risk stated) or accepting the replay, which is correct for an idempotent view. No code was
changed.

## 18. Decisions after the gate (2026-11-17)

**The import keeps the I8-safe value by default, with a per-mapping opt-in to the old resume point (maintainer,
QP-4b2431c225).** The gate showed that the old engine can leave a transient gap row behind after it has delivered the
fill (§17.4). Because the import uses `I = least(R, lowest filled open gap)`, a handful of such rows moved `I` back across
most of a stream, and the trading demo replayed up to about 109 000 already-handled events into views (§17.3). The tool
cannot tell a delivered fill from one that was never delivered, so it cannot skip these gaps on its own. The maintainer
decided to keep the safe value as the default and to add an opt-in on `ImportedSubscription`, `trustOldResumePoint`
(YAML `trustOldResumePoint: true`). With it the operator states that the subscriber already handled its gap fills, and the
import writes `R`. The opt-in gives up I8 for that subscription in exchange for no replay. To make the trade visible, the
import report and the import preview show `R`, the safe `I` and the rows the safe value replays for every mapping. They
also record the opt-in and list the filled gaps it skips, and the cut-over logs those gaps at WARN. The preview flags a
safe replay of more than 10 000 rows and points at the opt-in. Without the opt-in the behaviour is unchanged:
`MigrationInvariantIT` still passes, and `IMPORT_RESUME_UNCHANGED` must still fail.

**The online copy is throttled to 25 000 events per second by default (Claude).** `CopySettings.maxEventsPerSecond`
now defaults to 25 000 instead of 0. In the gate, 25 000 events/s kept the old engine's append p99 during an epoch at
0.84 to 0.92 times its p99 without a copy, while the unthrottled copy missed the 1.5× line (§17.1). 25 000 events/s is
also above the 20 000 events/s floor of §16.7, so a 10 M-event table still copies in under 7 minutes. Setting the value to
0 still turns the throttle off, and the cut-over is never throttled.
