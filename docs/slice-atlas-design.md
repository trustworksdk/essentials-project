# Slice Atlas — design

Status: **proposed, not shipped.** This document lives outside `essentials-plugin/` on purpose: the plugin
names only what ships (`essentials-plugin/CLAUDE.md` companion table). When a phase below ships, its
contract moves into the plugin — the manifest fields into `references/slice/slice-yaml.schema.json` and
`references/slice/manifest-guide.md`, the rendering rules into `commands/slice-map.md` — and the matching
section here is cut down to a pointer.

**§6 (`flow:`) and §7 (`scenarios:`) are the contract an external spec-driven-development (SDD) generator
targets.** They are written to be read on their own; point a generator at those two sections and §8.

## 1. Problem

LLM-generated, event-modelled systems grow faster than anyone's picture of them. The code is correct
slice by slice, and nobody can see the forest: which journeys exist, which events tie them together,
what a change just did to the shape, where a read model's data comes from. The field report behind
plugin 0.60.0-6 came from a project with 177 `slice.yaml` manifests — past the size where the current
`/essentials:slice-map --html` graph stops being readable.

The answer has to cost no model tokens to produce. The manifests and `slice-source.py` already carry
the whole graph deterministically; the Atlas is a better renderer of that data plus two optional
manifest fields, generated by scripts, with the model's role reduced to running one command.

## 2. Decisions (maintainer, 2026-10-08)

| # | Topic | Decision |
|---|---|---|
| A1 | Home | A **new command `/essentials:slice-map-html`** renders the page, so nobody has to remember a flag; `/essentials:slice-map` becomes the terminal report only and its `--html` flag is retired. The page is written by a new `slice-index.py atlas` subcommand that is documented as runnable directly (`uv run --script …`), so CI can publish it with no model involved. Both commands answer the same question — *what is here* — in two media, so they share Steps 1–4 of `commands/slice-map.md` rather than restating them. |
| A2 | v1 lenses | **Atlas** (semantic zoom, ending in a classic Event Modeling board), **Diff** against a git ref, **Information completeness**, **Coupling matrix**, **Metro map**. Base for all: issues dock, deep links, stable layout. |
| A3 | Processes | **Hybrid**: optional manifest field `flow:` (a name or a list of names); slices without one are grouped by derivation and an info issue says so. Order inside a process is derived from cause and effect, never declared. |
| A4 | Specs | Optional manifest field `scenarios:` — structured given/when/then that names the slice's own messages, with optional example values and an optional pointer to the test that runs it. A scenario may end in an error. When a slice has none, the board shows its invariants and test kinds instead. |
| A5 | Completeness | Map lens only, `info` issues. Name matching is a heuristic; the `/essentials:slice-check` audit stays precise. |
| A6 | Board top lane | Trigger cards — typically the API endpoint (method, path, auth); else the external system, schedule or automation. No `screen:` field. |
| A7 | Broken manifests | (Follows from the issues dock.) The Atlas **renders** a map with unparsed manifests — each as a red error node in its context, plus an `error` issue and a banner "map incomplete: N manifests did not parse" — and exits 1. Today's `html` refuses to write anything; the reason (a page that silently omits a slice) does not hold when the omission is the most visible thing on the page. The existing `html` subcommand keeps its behaviour. |

## 3. What exists today

`/essentials:slice-map` runs `slice-source.py` (package, files, payloads, read-model columns, two
divergence checks) and `slice-index.py map` (the manifest algebra: flows, writers, cross-context reads,
flags) and substitutes the JSON into `references/slice/slice-map-template.html`: a self-contained page
with five views (Contexts, Graph, Flow, Data, Endpoints). The Graph view is an SVG ranked by longest
path with role floors, with pan/zoom, hover cards, click-to-isolate and kind filters. Flags sit on the
slices as annotations at `info|warn|error`; the map grades nothing.

The Atlas keeps all of that data and both scripts. What it adds is: grouping above the slice
(processes), level-of-detail rendering, an issues list, four further lenses, and two manifest fields.

## 4. Architecture

```
slice-source.py ROOT --json            ─┐
slice-source.py ROOT --check --json    ─┼─► slice-index.py atlas ROOT --out FILE [--before-ref REF | --before-map FILE]
slice.yaml × N, slice CLAUDE.md × N    ─┘        │
                                                 ├─ map JSON (today's contract, §5 additions)
                                                 ├─ processes, issues, lineage, diff   (computed in Python)
                                                 ├─ layout: coordinates per lens        (computed in Python)
                                                 └─ inlined into references/slice/atlas/ (vanilla JS + SVG)
```

- **Code layout.** `slice-index.py atlas` is the entry point; the computation lives in two importable
  modules beside it — `scripts/slice_atlas.py` (processes, issues, lineage, diff, the `CLAUDE.md`
  conversion, page assembly) and `scripts/slice_atlas_layout.py` (coordinates for every lens). The page
  is `references/slice/atlas/atlas.html` (shell, styles, base features) plus one `lens-<n>-<name>.js` per
  lens; the script inlines the lens files and the data, so the written page is still one file.

- **Everything that can be computed is computed in Python** — processes, issues, lineage, the diff and
  every coordinate. The template only draws, filters and navigates. This makes the layout
  golden-testable and identical on every run, and lets the diff lens lay out the union of two maps once.
  (Today's template computes its own layout in JS; the Atlas template does not. The layout's edges are
  derived from `slices[]` by the same script in the same run, so they cannot drift from it; the page
  derives nothing, which keeps "one representation of the graph" — `commands/slice-map.md` §6 — true.)
- **Self-contained page**, as today: no CDN, no fonts, no fetch; opens from `file://`. No Node or npm
  anywhere (repo rule). Python stdlib plus the pinned `pyyaml` the two scripts already declare.
- **The page writes nothing and reads nothing** beyond its embedded JSON. View state lives in the URL
  hash (§9.2).

### Command: `/essentials:slice-map-html`

```
/essentials:slice-map-html [<path>] [--bc <name>] [--out <file>] [--diff <ref>]
```

Every argument is optional; the bare command is the normal use.

- **Output path.** Without `--out`, propose `target/slice-map.html` (`build/slice-map.html` on Gradle) —
  a build directory is already git-ignored — and ask once before writing. The ask stays: the plugin owns
  no directory (`essentials-plugin/CLAUDE.md` design invariants), so a path is never chosen silently.
- **Diff by default.** Without `--diff`, when the current branch is not the default branch, the "before"
  side is the merge-base with the default branch — the shape of what this branch changed, which is the
  review question. On the default branch, or with no git, the Diff lens says "no baseline" and the other
  lenses render as usual. `--diff <ref>` picks another baseline.
- **Steps.** Terrain and the no-manifest redirect (`slice-map.md` Step 1), doctor, the two
  `slice-source.py` runs into `mktemp -d`, then `slice-index.py atlas`. Report the one summary line the
  script prints and the path. No report sections — that is `/essentials:slice-map`.
- **`/essentials:slice-map --html`** is retired in the same release. Given the flag, `slice-map` says
  the page moved to `/essentials:slice-map-html` and runs that command's steps with the same path, so an
  old habit still works. `--md` stays on `slice-map`: it is the text report in a file.

### CLI (what the command runs, and what CI runs directly)

```bash
slice-index.py atlas ROOT --out FILE
    [--source-facts FILE] [--source-check FILE]      # as for `map`/`html`
    [--before-ref REF | --before-map FILE]           # enables the Diff lens
    [--bc BC] [--lens atlas|diff|lineage|matrix|metro] [--focus ID]   # initial state, written into the hash
    [--repair-braced-paths] [--sha SHA] [--project NAME]
```

- `--before-ref REF` builds the "before" map from `git archive REF -- <root>` extracted into a temporary
  directory, running both scripts there. It does not touch the working tree or `.git` (no worktree), so
  the command stays read-only. The "after" side is always the working tree, which is what the model just
  changed.
- `--before-map FILE` takes a map JSON produced earlier (`slice-index.py map` on the default branch,
  cached by CI) — the cheap path for a per-PR artifact.
- Exit codes: as `html`, except A7 (exit 1 still writes the page).
- The command prose stays thin: run doctor, run the scripts, ask for the output path, report the
  summary line the script prints. The model never reads a manifest to build the page.

## 5. Data contract additions

All additive to the `map` JSON of `commands/slice-map.md` §6; every key present, `[]`/`null` rather than
omitted. (Comments below are annotations, not part of the JSON.)

```jsonc
{
  "slices": [{ "…": "as today",
    "flows": ["checkout"],                 // declared `flow:`, normalised to a list; [] when absent
    "scenarios": [ /* §7, normalised; [] when absent */ ],
    "doc": "<h2>Invariants</h2><ul>…</ul>"  // slice CLAUDE.md, §9.4 subset, sanitised; null when absent
  }],
  "processes": [
    { "id": "checkout", "name": "checkout", "declared": true,
      "bcs": ["orders", "billing"], "sliceIds": ["orders.place_order", "…"],   // causal order
      "entries": ["orders.place_order"],
      "links": [{ "to": "fulfilment", "via": ["OrderPaid"] }] },
    { "id": "~orders.cancel_order", "name": "cancel order", "declared": false, "…": "…" }
  ],
  "issues": [
    { "id": "completeness-unsourced-column:orders.order_list:OrderList.discount",
      "code": "completeness-unsourced-column", "level": "info",
      "text": "column `discount` of OrderList matches no field of OrderPlaced, OrderLineAdded",
      "target": { "kind": "slice", "id": "orders.order_list", "part": "readModel:OrderList.discount" },
      "source": "atlas" }
  ],
  "lineage": { "fields": { "orderid": ["msg:command:PlaceOrder", "msg:event:OrderPlaced", "rm:OrderList"] } },
  "diff": null,      // §10.2 when a before-map exists
  "layout": { "atlas": { "…": "node id → {x, y, w, h}" }, "metro": { "…": "…" }, "matrix": { "…": "…" } }
}
```

**Issue ids are stable**: `<code>:<target id>[:<part>]`. Deep links, the diff lens ("new issues / fixed
issues") and a CI comparison all key on them. Today's flags become issues one to one, with these codes:
`map-parse-error`, `map-duplicate-id`, `map-kind-location`, `map-twin-broken`, `map-dangling-consume`,
`map-handled-undeclared`, `map-endpoint-missing`, `map-not-checked`. New codes are listed with the
feature that raises them (§6–§10). Levels stay `info|warn|error`, and remain annotations: the map
grades nothing.

**Aggregation rule.** An issue that would fire on most slices of a context fires once per context with
a count ("31 of 40 slices in `orders` declare no flow"). Otherwise a project that has not adopted the
optional fields gets a dock with 300 entries and stops reading it.

## 6. Contract: `flow:`

Optional, any kind, schema `1.4`.

```yaml
flow: checkout              # one journey
flow: [checkout, returns]   # a slice that serves several — typically a shared view
```

- Value: `^[a-z0-9][a-z0-9_-]*$`, a name or a non-empty list of names, no duplicates.
- **A flow name is global, not per bounded context.** A journey that crosses contexts (checkout spans
  `orders`, `billing`, `shipping`) is one process; the Atlas draws its per-context segments in one colour
  and the metro lens draws it as one line. Two contexts that pick the same name *mean* the same journey.
- **No order is declared.** Order inside a process is the causal rank (§10.1). An ordinal would have to
  be renumbered by every inserted slice.
- A generator should give every slice it creates for a journey that journey's name, and add a second
  name to a slice only when that slice genuinely serves both (a view read by two journeys, a translation
  used by both).

Derivation for slices with no `flow:` (A3): from each **entry slice** in a context — a command slice
with an endpoint, an inbound translation, a schedule-triggered automation — take the forward closure along
*command → slice → event → reacting slice → dispatched command*, **stopping at the context boundary and
at any slice that declares a flow** (those become process links, not members). Each closure is a derived
process, id `~<entry slice id>`, named after the entry slice humanised (`cancel_order` → "cancel order").
Closures may overlap; a slice in several derived processes belongs to each. Slices reached from no entry
go to one derived process per context, "unattached" — typically HTTP-only views.

Issue: `flow-undeclared` (`info`, aggregated per context).

## 7. Contract: `scenarios:`

Optional, any kind, schema `1.4`. The slice's specification by example, in Event Modeling's
given / when / then form. It is **data the board renders and scripts check, not a test**: the test is
named in `test:` and lives in the source tree.

### 7.1 Shape

```yaml
scenarios:
  - name: cancels a placed order               # required, unique within the slice
    given:                                     # optional; prior history
      - event: OrderPlaced
        with: { orderId: o-1, customerId: c-7 }
    when:                                      # required except on a view (§7.2)
      command: CancelOrder
      with: { orderId: o-1 }
    then:                                      # required
      - event: OrderCancelled
        with: { orderId: o-1 }
    test: CancelOrderDeciderTest#cancelsPlacedOrder   # optional

  - name: rejects an unknown order
    when: { command: CancelOrder, with: { orderId: o-404 } }
    then: { error: OrderNotFound, message: "Order o-404 not found" }

  - name: cancelling twice is a no-op
    given: [{ event: OrderPlaced }, { event: OrderCancelled }]
    when: { command: CancelOrder }
    then: { nothing: true }
```

**A step** is a mapping with exactly one message key and an optional `with`:

| Key | Names | Allowed in |
|---|---|---|
| `event` | an event type | given, when (reactors), then |
| `command` | a command type | when (command slices), then (automations, inbound translations) |
| `query` | a query type the slice `serves` | when (views) |
| `state` | a write target the slice `writes` — the current state of an entity, for lanes without an event stream (service-entity) | given |
| `external` | a message of the slice's `externalSystem` | when (inbound translation), then (outbound translation) |
| `schedule` | `true` — the time trigger of a schedule-driven automation | when |

`with` is a flat mapping of **example values**: keys are payload field names, values are scalars.
Values are rendered verbatim and never interpreted.

**`then`** is exactly one of:

| Form | Meaning |
|---|---|
| a non-empty list of steps | what the slice emits: events published, commands dispatched, external calls made |
| `{ error: <Name>, message?: <text> }` | the slice rejects. `<Name>` is the exception or domain-error type's simple name as thrown (`OrderNotFound`, `IllegalArgumentException`); `message` an example message. Nothing is emitted |
| `{ nothing: true }` | accepted, nothing emitted — the idempotent retry, the event a policy ignores |
| `{ readModel: <Name>, rows: [ {col: value, …}, … ] }` | a view's state after `given` (and the result of a `when` query). `rows: []` is a valid "empty" outcome |

An empty `then: []` is invalid: it is indistinguishable from a scenario left unfinished. Write
`{ nothing: true }`.

**`test`** names the test that executes the scenario, resolved under the module's test roots:

- `ClassName#method` — the usual form. Everything after `#` is taken verbatim, so a Kotlin backtick name
  works: ``CancelOrderTest#cancels a placed order``.
- `ClassName` — the scenario is the whole class (one parameterised test, one test class per scenario).
- `path/from/test/root/File.kt#method` — when the simple class name is ambiguous.

### 7.2 What each kind may say

| Kind | `given` | `when` | `then` |
|---|---|---|---|
| command | `event` (any event published in scope), `state` (∈ `writes`) | `command` ∈ `handles` — required | events ⊆ `publishes`; `error`; `nothing` |
| view | `event` ∈ `projections[].from` ∪ `consumes` | optional; `query` ∈ `serves` | `readModel` ∈ `owns` ∪ `reads[].name` ∪ `projections[].name` (the plugin's view template writes no `owns`), row keys ⊆ that model's columns; `error` (for a `when` query) |
| automation | `event`, `state` (its own to-do read model, if any) | `event` ∈ `consumes`, or `schedule: true` when the slice declares `schedule` — required | commands ⊆ `dispatches`; `nothing`; `error` |
| translation, inbound | `event`, `state` | `external` — required | commands ⊆ `dispatches`, events ⊆ `publishes`; `nothing`; `error` |
| translation, outbound | `event`, `state` | `event` ∈ `consumes` — required | `external` steps; `nothing`; `error` |

### 7.3 Checks, and where they run

| Check | Level | Runs in | Why there |
|---|---|---|---|
| Shape (one message key per step, `then` form, unique `name`) | error | schema (`slice-lint.py`) | precise, per file — the commit gate catches a malformed generator output |
| A name in `when`/`then` outside the slice's own lists per §7.2 | error | `slice-lint.py` (new cross-field rule) | precise: same manifest, no other file needed |
| A `given` event no slice in scope publishes | warn `scenario-given-unpublished` | Atlas | needs every manifest |
| A `with`/`rows` key that is not a payload field / column | info `scenario-unknown-field` | Atlas | needs source facts; `not checked` without them |
| `test:` resolves to no test | warn `scenario-test-missing` | Atlas, via `slice-source.py` | needs the test tree; `not checked` when unresolvable |
| Slice has no scenarios | info `scenario-none` | Atlas, aggregated per context | adoption signal, not a defect |

### 7.4 Compatibility — read before generating

The schema has `additionalProperties: false`, and **every project carries its own copy** of it
(`scripts/slice-yaml.schema.json`, installed by `/essentials:init` with the lint gate). A project whose
copy predates `1.4` rejects a manifest containing `flow:` or `scenarios:` at commit time.

A generator must therefore:

1. Check the project's `scripts/slice-yaml.schema.json` (or, without a lint gate, the plugin's) for a
   `scenarios` property before writing either field.
2. If absent, write neither field and tell the user to run `/essentials:upgrade`, which refreshes the
   gate (Group A2) — not add the fields and leave the gate red.
3. Stamp `schemaVersion: "1.4"` on a manifest it writes either field into. Readers accept any `1.x`, so
   manifests without the fields need no restamp.

### 7.5 JSON Schema (draft, lands in `slice-yaml.schema.json` at 1.4)

```json
"flow": { "oneOf": [
  { "type": "string", "pattern": "^[a-z0-9][a-z0-9_-]*$" },
  { "type": "array", "minItems": 1, "uniqueItems": true,
    "items": { "type": "string", "pattern": "^[a-z0-9][a-z0-9_-]*$" } } ] },
"scenarios": { "type": "array", "items": { "$ref": "#/$defs/scenario" } },

"$defs": {
  "scenario": { "type": "object", "additionalProperties": false, "required": ["name", "then"],
    "properties": {
      "name":  { "type": "string", "minLength": 1 },
      "given": { "type": "array", "items": { "$ref": "#/$defs/scenarioStep" } },
      "when":  { "$ref": "#/$defs/scenarioStep" },
      "then":  { "oneOf": [
        { "type": "array", "minItems": 1, "items": { "$ref": "#/$defs/scenarioStep" } },
        { "type": "object", "additionalProperties": false, "required": ["error"],
          "properties": { "error": { "type": "string" }, "message": { "type": "string" } } },
        { "type": "object", "additionalProperties": false, "required": ["nothing"],
          "properties": { "nothing": { "const": true } } },
        { "type": "object", "additionalProperties": false, "required": ["readModel", "rows"],
          "properties": { "readModel": { "type": "string" },
                          "rows": { "type": "array", "items": { "$ref": "#/$defs/scalarMap" } } } } ] },
      "test":  { "type": "string", "minLength": 1 },
      "note":  { "type": "string" } } },
  "scenarioStep": { "type": "object", "additionalProperties": false,
    "oneOf": [ { "required": ["event"] }, { "required": ["command"] }, { "required": ["query"] },
               { "required": ["state"] }, { "required": ["external"] }, { "required": ["schedule"] } ],
    "properties": {
      "event": { "type": "string" }, "command": { "type": "string" }, "query": { "type": "string" },
      "state": { "type": "string" }, "external": { "type": "string" }, "schedule": { "const": true },
      "with": { "$ref": "#/$defs/scalarMap" } } },
  "scalarMap": { "type": "object",
    "additionalProperties": { "type": ["string", "number", "boolean", "null"] } }
}
```

## 8. Rendering the board — what a generator's output turns into

So a generator author can predict the picture. One column per slice, left to right in causal order
within the process; lanes top to bottom:

| Lane | Contents |
|---|---|
| Trigger | endpoint card (`POST /api/orders`, auth), external-system card, schedule card (cron / delay), or ⚙ for an automation |
| Command · View | command stickies (blue) and view stickies (green) — Event Modeling puts both on this row |
| Events · `<stream>` | one lane per write target the process touches (orange); external events in their own lane |

Below each column, at the deepest zoom: the scenarios as given / when / then card stacks (given and
then-events orange, when-command blue, then-rows as a small green table, **then-error red with the
error name and message**, then-nothing grey). A slice without scenarios shows its invariants (with
`enforcedBy`) and its test kinds in the same place, labelled "no scenarios declared". A scenario with a
resolved `test:` gets a ✓ badge linking to the file path; a missing one a warn marker.

## 9. Base, shared by every lens

### 9.1 Issues dock

A collapsible panel listing every issue, grouped by level then context, filterable by code. Selecting an
issue switches to the lens and zoom where its target is drawn, flies the camera there, draws an error
marker on the target (on the column, cell, sticky or scenario card named by `target.part`), and opens the
detail card scrolled to the issue text. ↑/↓ walk the list. The header carries counts per level.

### 9.2 Deep links

The hash is the whole view state: `#lens=atlas&z=2&focus=orders.place_order&issue=<id>&q=Order`.
A link pasted in a PR comment reopens the same view. Unknown keys are ignored; a stale focus id shows a
"not in this map" toast rather than failing.

### 9.3 Stable layout

- No randomness anywhere; every sort has a total key ending in the node id.
- Within a rank, nodes are ordered by (process, lane, id), **not** by crossing minimisation: crossing
  minimisation moves neighbours whenever a slice is added, and a map whose shape jumps between commits
  destroys the reader's mental map — the thing the Atlas exists to build. A "tidy" toggle applies a
  deterministic barycenter pass for a one-off read, off by default.
- Contexts are packed in id order into cells that grow in size steps at most 25 % apart; adding a slice
  rearranges only its own context, unless that context crosses a size step — then the contexts after it
  shift as whole blocks, keeping their inner layout. (A strict guarantee needs one row of fixed-width
  contexts, about 50:1 wide at 60 contexts.)
- The layout JSON is golden-tested (§12).

### 9.4 Detail card

Manifest fields, payloads with the identity property first, read-model table, scenarios, issues, and
the slice's `CLAUDE.md`. The Markdown is converted in Python to a fixed subset — headings, paragraphs,
lists, emphasis, inline and fenced code, tables; links rendered as text — with **every character
escaped first**. No raw HTML from a manifest or `CLAUDE.md` ever reaches the page.

### 9.5 Everywhere

Search box (`/`) that dims non-matches; lens switcher (`1`–`5`); minimap; legend per lens; `Esc`
releases focus. Text is never drawn below 11 px — below that the level of detail drops instead.

**Theme.** Light and dark, following `prefers-color-scheme` with a toggle that overrides it. Colours
come from the Trustworks palette (the `tw-brand` plugin's `visual-style` skill): Aqua 100/80/60/40
`#96B7B9 #AAC5C7 #BFD4D5 #D5E2E3`, Gul 100/80/60/40 `#F3D4A1 #F5DCB4 #F3E4CD #FAEDDA`, Lys grå
`#EAEAEA`, Mørk grå `#666672`; font stack `"Neue Haas Grotesk Display Pro", "Neue Haas Grotesk Text
Pro", Arial, sans-serif`. Light is the default surface (white, Lys grå panels, Mørk grå text). Event
Modeling's colours map onto the palette: **events Gul** (the warm sticky), **commands Aqua 100**,
**views Aqua 40 with an Aqua 100 rule** — distinct from commands by fill weight, not by a new hue. The
only off-palette hues are muted status colours (error, warn), as the brand allows for status. Dark mode
keeps the same hues on a surface derived from Mørk grå, with stickies at reduced lightness so they do
not glare. No gradients on working surfaces.

## 10. Lenses

### 10.1 Atlas — "how is this shaped?"

Semantic zoom over **one continuous geometry**: a context contains its process boxes, a process box *is*
the extent of its board, so zooming in opens a box in place instead of jumping to another screen.

| Level | Scale (tuned on fixtures) | Draws |
|---|---|---|
| L0 Contexts | < 0.12 | contexts as regions sized by slice count; cross-context event links as bridges, width = number of events, label on hover |
| L1 Processes | 0.12–0.5 | process boxes (name, slice count, issue counts), links between processes labelled with the events; a cross-context process's segments share a colour |
| L2 Board | 0.5–0.9 | §8 board, compact: sticky names only, edges between stickies |
| L3 Board, detail | ≥ 0.9 | §8 board with payload fields on stickies and scenario stacks under columns |

Labels at L0/L1 are drawn at constant screen size. Elements outside the viewport are not drawn. A slice
in several processes is drawn in full in the first (by process id) and as a dashed portal sticky in the
others; clicking a portal flies to the original.

Causal rank is today's longest-path rank with role floors (`commands/slice-map.md` Step 3), computed
inside each process.

### 10.2 Diff — "what did this change do to the shape?"

Before and after maps are matched by stable ids: slice id, `(type, name)` for messages, `(from, to,
kind)` for edges, issue id for issues. The union is laid out once, so both states share coordinates.

- Added: green outline. Removed: red ghost at its old position. Changed: amber, and the card lists the
  manifest field changes (`publishes: +OrderShipped`, `scenarios: 2 → 3`, `flow: checkout → returns`).
- A summary bar: `+3 slices −1 · 7 changed · +2 events · issues +4 new / −2 fixed`. "New issues" is
  the single most useful number when reviewing generated code.
- A "changes + 1 hop" filter hides everything else.
- No rename detection: a moved slice is a remove plus an add; the card says when the two share a
  directory name.

`diff` JSON: `{ "before": {sha, sliceCount}, "slices": {added, removed, changed: [{id, fields}]},
"edges": {added, removed}, "issues": {new, fixed} }`.

### 10.3 Information completeness — "where does this field come from?"

Event Modeling's own check: every piece of information shown must have an origin.

- **Rule (v1, the only one that raises issues):** each column of a view's read model should match a
  field of at least one event in its `projections[].from` ∪ `consumes`. Matching normalises case and
  `_`/camel (`order_id` = `orderId`). Across a translation, `maps[]` (`from` → `to`) renames are
  honoured. Columns on a fixed technical list (`id`, `version`, `createdAt`, `updatedAt`, `lastModified`,
  `etag`) are skipped; the list lives in the script and is printed in the legend.
  Issue: `completeness-unsourced-column` (`info`).
- **Lineage highlighting (no issues):** clicking a field anywhere lights up every command, event and
  read model carrying a field of that normalised name, and draws the path command → event → view.
  Command-to-event lineage is shown but not judged: events legitimately add fields (timestamps,
  generated ids), and judging them would bury the dock.
- `not checked` when source facts are missing (no payloads, no columns).

### 10.4 Coupling matrix — "who touches what?"

Rows: write targets and read models, grouped by owning context. Columns: slices, grouped by context, then
kind. Cells: `W` writes, `O` owns, `R` reads (`R·via` with a reader interface), `R!` a cross-context read
without `via`. Cells outside the diagonal context blocks are tinted — coupling across a boundary is the
off-diagonal mass, visible at a glance at any size. A second tab is the context × context event matrix
(cell = number of events from row context consumed by column context). Rows and columns virtualise past
a few hundred. Clicking a cell opens both ends.

### 10.5 Metro map — "how do the journeys interleave?"

Each process is a line in its own colour; slices are stations; a slice in two or more processes is an
interchange. Layout: x = global causal rank, each line gets a horizontal track in process-id order, an
interchange sits on the track of its first line and other lines bend to it with 45° segments. v1 is
schematic — readable, stable, not optimised. Derived processes are drawn thinner and dashed until
declared, which makes the case for `flow:` visually.

## 13. Phases

Built on one branch and shipped together as one plugin version; the phases are the build order.

1. **Contract** — schema 1.4 (`flow`, `scenarios`), `slice-lint` rule, `manifest-guide.md`. Ships first,

   JSON and layout; goldens.

5. **Completeness lens.**
