# postgresql-event-store

Append-only PostgreSQL event store with durable subscriptions, gap handling, and CDC via WAL logical replication. Maven: `postgresql-event-store`.

## Jackson

Jackson 3 (`tools.jackson`) only — Jackson 2 support dropped in 0.60.

- Get serializer from `EssentialsJSONEventSerializers.create()` — never `new Jackson3JSONEventSerializer(...)` with hand-built mapper. Mapper config from `EssentialsObjectMappers` *is* persisted-JSON contract.
- `EssentialsObjectMappersWireFormatTest` = compatibility gate: asserts persisted format against golden docs (`wire-format/queue-payload.json`, `wire-format/persisted-shapes.json`) written by 0.50's Jackson 2 mapper. Proves 0.60 reads what 0.50 wrote. Never regenerate them — Jackson 2 writer gone; a diff there is a format break, fix the mapper.
- **CDC**: WAL converters/extractor parse via `JSONEventSerializer.deserialize(..., Object.class)` into plain maps/lists. Take the interface, never concrete serializer class.
- **WAL pre-filter**: `DefaultWalMessageFilter` scans tokens via Jackson 3 streaming API without materializing payload.
- **`canonicalJson` fidelity**: `PgOutputToPersistedEventConverter` re-serializes the payload it persists, through untyped binding. `EssentialsObjectMappers` enables `USE_BIG_DECIMAL_FOR_FLOATS` for exactly this reason — without it `1.10` would be rewritten as `1.1` in persisted events.

## Gotchas

- **Every delivery site that holds a `PersistedEvent` binds `CausationContext` around its handler** — `EventReferenceResolvingMessageConsumer` (phase 2, enclosing the handler's own UnitOfWork commit), `ViewEventProcessor.handlePersistedEvent`, `InTransactionEventProcessor.invokeHandler`, `PersistedEventSubscriber`, both `*InTransactionSubscription`s. Batched subscriber deliberately unbound (batch = many causes). New delivery site → bind too, or events written from it silently get no cause. Pinned by `CausationBindingIT`. Design: `docs/event-causation.md`
- **`loadEventsCausedBy` refuses unless `enableCausationIndex()` was called** — no silent seq scan over every table. `findEvent(EventId)` needs no index (event-id index per table, via `loadEvent` + interceptors). Results ordered by table name, then global order within a table — no cross-table order exists
- **A non-UUID cause is dropped (WARN), not fatal, in UUID-typed tables** — causation must never fail an append. Correlation id path unchanged (still throws)
- **In-transaction handlers run inside the appender's commit, not their own** — a lifecycle callback they register runs in a later commit pass, outside the per-event binding, under the appender's cause. Lazily appending repositories must capture the cause at registration (phase 4 of `docs/event-causation.md`)
- **Removing an overload can silently rebind its callers.** `AppendToStream` has an `(AggregateType, ID, Object...)` constructor, so a call whose specific overload disappears still compiles against it, with the leftover arguments appended as "events" - 0.60 hit this when it removed the `(…, Optional<Long>, List<?>)` constructor, and `EventStore.appendToStream(…, Optional<Long>, Object...)` had always done it. The varargs constructor now rejects `Optional`/`Collection`/array events; `EventStoreAppendToStreamDefaultsTest` pins every `appendToStream` default. Before removing an overload anywhere, check what its callers bind to afterwards (restore the old API in a scratch copy and read javac's removal warnings)
- **`@MessageHandler(unitOfWork = UnitOfWorkMode.NONE)` works on `EventProcessor` only.** It is the only processor that hands the `UnitOfWork` boundary to its `PatternMatchingMessageHandler` (`setUnitOfWorkFactory`), so the handler can run its blocking call outside a transaction and wrap its tail in `usingUnitOfWork`/`withUnitOfWork`. `ViewEventProcessor` and `InTransactionEventProcessor` both handle a message inside one shared `UnitOfWork` and therefore **reject** `NONE` handlers in `start()` — silently ignoring the mode would run the blocking call inside a transaction, which is the failure the mode exists to prevent. `InTransactionEventProcessor` checks before setting `started`, so a rejected processor still reports `isStarted() == false`; `ViewEventProcessor` does not. Guards pinned by `ProcessorNonTransactionalMessageHandlerGuardTest` (unit) and `NonTransactionalMessageHandlerIT` (behaviour)
- **Every exit of a poll must end its `UnitOfWork`** — `PollEventStoreTask.pollForEvents` and the `unboundedPollForEvents` lambda each open one per poll; the "no new events persisted" skip used to `return` without ending it, which leaked the transaction whenever the subscription was disposed before the next poll reused it (unsubscribe, stop, fenced-lock loss). Commit/rollback go through `commitIfStartedByThisPoll` / `rollbackIfStartedByThisPoll`, and a `finally` rolls back whatever is still open. A poll only ends a UoW it started — `unboundedPollForEvents`' first poll can join the subscriber's. Regression: `PollingUnitOfWorkLifecycleIT`, which disposes from inside the skip branch via the observer. It needs a **pooled** `DataSource`: with unpooled connections the leaked connection becomes unreachable when the poll thread ends and pgjdbc closes it on GC, so the test passes on broken code
- **`SubscriptionErrorPolicy` retries run synchronously on the delivery thread — don't turn them into a reactive `retryWhen`.** A reactive retry waits on a timer and frees the thread while the flux still has demand, so later events are handled during the backoff: out of order, and for `STOP` past the event it must stop at. `STOP` also rewinds a resume point that a later event already advanced. That delivery thread must stay **per subscription** on every path (polling `Publish-*`, CDC `Cdc-*` hand-over in `CdcEventStore`, batched `*-Handler`) — never a shared scheduler or the `cdc-dispatcher` thread, or one backoff stalls everyone. A stop mid-retry is a third outcome (`SubscriptionStoppedDuringRetryException`): never route it to the skip path. An interrupted backoff is **not** a stop by itself — `CdcEventStore`'s polling↔CDC source switch interrupts it on a live subscriber; decide on the subscriber's stopped state (`isStopped()`, not `isDisposed()`, which completion also sets), or the subscriber silently halts. Why in full: `SubscriptionErrorPolicyRetries` javadoc; pinned by `EventStoreSubscriptionManager_SubscriptionErrorPolicy_IT`, `PersistedEventSubscriberResumePointTest`, `CdcEventStoreSubscriptionErrorPolicyIsolationIT`
- **`ViewEventProcessor` escalates, and does not queue in the subscription's UoW, a failed direct handler that left UoW state a savepoint can't undo** (appended events, lifecycle resources with pending changes, rollback-only). `handleDirectlyUnderSavepoint` catches `Exception`, not `RuntimeException`: an interceptor (Kotlin, sneaky throw) can raise a checked one, which would skip the savepoint rollback and commit partial writes with the queued event. Subscriber rolls back, policy retries, then `PersistedEventHandler.handOffFailedEvent` queues it in its own UoW instead of skip/stop — policy gives up only if that queueing throws. Hand-off runs before `doFinally` advances the resume point; keep that order or a crash loses the event. Why: `handleDirectlyUnderSavepoint` / `queueAfterRollback` javadoc; pinned by `ViewEventProcessorIT`, `PersistedEventSubscriberResumePointTest`, and for the Spring `UnitOfWork` (own copy of both signals) by `SpringTransactionAwareEventStoreUnitOfWorkFactory_ViewEventProcessorIT` in `spring-postgresql-event-store`
- **`STOP` never retries, even with `maxRetries > 0`** — retry-then-stop is its own mode, `RETRY_N_THEN_STOP`, so configs that set `max-retries` beside `stop` keep their behaviour. A stop is undone by `resumeIfStoppedByErrorPolicy()` (polling + CDC; exclusive keeps its lock, serialized with the lock callbacks by `subscriberLifecycleLock`). Why: `SubscriptionErrorPolicy` / `EventStoreSubscription#resumeIfStoppedByErrorPolicy` javadoc
- **Error policy = handler's `subscriptionErrorPolicy()`, else manager's** — every path that builds a `PersistedEventSubscriber`/`BatchedPersistedEventSubscriber` resolves it via `EventStoreSubscriptionManagerSettings.subscriptionErrorPolicyFor(handler)`; a new construction site must too, or a processor's `getSubscriptionErrorPolicy()` is silently ignored. A handler wrapping another must forward `subscriptionErrorPolicy()`
- **A `STOP` leaves `isActive()` true on purpose** — surface it via `EventStoreSubscription.isStoppedByErrorPolicy()` / the `subscriptionStoppedByErrorPolicy` observer callback. Alerting goes through the level-triggered gauge `essentials.eventstore.subscription.stopped` (`SubscriptionStoppedMicrometerMonitor`, reads the flag live on every scrape), never the `stopped_by_error_policy` counter - a counter cannot say "still stopped". `isActive()` gates the manager's periodic resume-point checkpoint and means "holds the lock" for exclusive subscriptions; javadoc on `isStoppedByErrorPolicy` says why
- **Global event order is per-table sequence**, not cross-table. Subscribers to different `AggregateType`s have independent `GlobalEventOrder` spaces.
- **Table names go straight into SQL** via string concat. `PostgresqlUtil.checkIsValidTableOrColumnName` is first-line defense only — sanitize all external inputs before they reach `SeparateTablePerAggregateEventStreamConfiguration`.
- **CDC delivery modes**: `INBOX` (tailer writes to staging table, dispatcher polls) vs `DIRECT` (tailer calls consumer inline). `INBOX` survives tailer restarts; `DIRECT` logs a warning about re-delivery risk.
- **CDC is opt-in** — `CdcProperties.enabled` defaults to `false`, and the starter gates every CDC bean on `essentials.eventstore.cdc.enabled=true`. Enabling it also needs `wal_level=logical`, slot/wal-sender headroom, a `REPLICATION` role, and (for pgoutput) a publication covering the event-stream tables. Full checklist: `docs/cdc.md` §1.1
- **`CdcMode.AUTO` vs `REQUIRE`**: `AUTO` silently falls back to polling if WAL logical replication is unavailable; `REQUIRE` fails startup. The `CdcEffectivenessMonitor` tracks whether CDC is actually delivering. Note `AUTO` makes a half-configured CDC setup look fine — the app boots and stays correct, just on polling.
- **A poll on the inactive path during startup is a *warm-up*, not a fallback.** `CdcAvailability` starts `INACTIVE` and only goes `ACTIVE` once the tailer has connected and taken the slot, but the lifecycle starts subscriptions **before** `walReplicationTailer` — so every subscription that comes up during boot legitimately begins on polling and is switched to the CDC bus by `buildAdaptiveLiveSource`'s `stateChanges()` subscription moments later. `CdcAvailability.fallbackUsed()` therefore routes on `everActive`: before the first `active(slot)` it increments `warmupPollCount` / `essentials.cdc.warmup_poll_total`, afterwards `fallbackCount` / `essentials.cdc.fallback_total`. Counting warm-up as fallback is what previously made a healthy boot report "CDC has fallen back to polling N times" with an empty `reason` and no error, N varying run to run with a fenced-lock race. Don't "simplify" the two counters back into one — `fallback_total` is the alertable signal and must stay free of startup noise
- **`essentials.cdc.eventstore.fallback.poll.count` still includes warm-up polls** — it is incremented in `CdcEventStore.pollEvents` next to `availability.fallbackUsed()` and counts every trip down the polling branch, unlike `fallback_total`. Deliberate: it measures the polling branch, not CDC health. Read it together with `essentials.cdc.active`, never on its own
- **Mid-stream switch off the CDC bus = fallback.** `buildAdaptiveLiveSource` calls `fallbackUsed()` when a running subscription's state goes `ACTIVE` → non-active (tracked per subscription; non-active → non-active is not a second one). Before, only `pollEvents`' start-on-polling path counted, so an outage every running subscription polled through left `fallbackCount` at 0
- **A CDC subscription must never back-pressure the `CdcEventBus` sink.** Multicast sink is paced by slowest subscriber: one handler stalled in its backoff used to fill it, so every emit for the aggregate type hit `FAIL_OVERFLOW` - dropped for healthy subscriptions under `LOG_AND_DROP`, `CdcBusOverflowException` for the dispatcher under `FAIL_FAST` (F-871). Bus leg = `busLeg`: `BusHandOver` (unbounded request, offers to a unicast sink over `ArrayBlockingQueue(pageSize)`; full → cancel bus + overflow error, delivered after the queue drains) → `publishOn` (fuses, delayError) → `retryWhen(overflow → catch up again)`. Keep `retryWhen` after `publishOn` and inside the switch, or the tracker is read before the buffered events went through. Retry, not `onErrorResume`: repeated overflows must not nest the pipeline. Overflow is not a CDC fallback - own counter `live_source.overflow.count`, never `fallbackUsed()`, not `switch.count`. Self-healing: catches up, rejoins bus. Pinned by `CdcEventStoreLiveSourceOverflowTest`, `CdcEventStoreSubscriptionOverflowIT`
- **Every move onto the CDC bus catches up first - attach, then read head, then load `[highest delivered + 1 .. head]` (+ awaited gaps by order), then drain the bus.** Bus replays nothing to a late subscriber; bare attach lost what polling had not fetched (since its last fetch, the `activeCutbackDebounce` window, an in-flight handler) at warm-up and after every outage, and the next bus event moved the high-water mark past it. Head read after attach = `BackfillThenLiveOrdered`'s argument; end at head, not at "first bus event": global order has holes. Only exception: first attach of a `BackfillThenLiveOrdered` live source (`forBackfillThenLiveOrdered`) - it back-fills to its own head itself; catching up there would load the backlog twice. Catch-up = `backfillFlux` on the `Cdc-*` scheduler (head read lazily on it, never on the subscribing/parallel thread). Failed catch-up retried after `CATCH_UP_RETRY_DELAY`, never ends the subscription. `BusHandOver` drops what is at/below the tracker's watermark and not awaited, so a fresh sink's retained events can't overflow the buffer on attach. Pinned by `CdcEventStoreBusCatchUpTest`, `CdcEventStoreBusHandOverIT`
- **`BackfillThenLiveOrdered` must request live events only as its subscriber takes them** (`doOnNext(liveSub.request(1))` on `orderedLiveSink`'s output). Refilling on drain let a paused subscriber (batched handler busy on its own thread) overflow `orderedLiveSink` → `CdcBusOverflowException` ended the flux, subscription silently halted with `isActive()` true; a backfill completing before `merge` subscribed the sink dropped events as `FAIL_ZERO_SUBSCRIBER`. Pinned by `BackfillThenLiveOrderedTest`, `CdcEventStoreSubscriptionOverflowIT`
- **CDC dedup = `CdcDeliveryTracker`, never a high-water mark.** Bus = commit order, not global order: lower `IDENTITY` committing after higher one arrives late. Old `> lastSeen` dropped it for good (bus leg, polling gap-fills, `BackfillThenLiveOrdered` at/below head; drain parked till stall threshold). Tracker: watermark W + delivered runs above W; pass iff not delivered; late event delivered out of global order (same contract as polling gap-fills, resume point only advances). Gap given up after `SubscriptionGapHandler.transientGapGiveUpThreshold()` (`thresholdBased(n)` -> n s; empty for a lambda strategy / custom / no-op handler -> `DEFAULT_GAP_TIMEOUT` 120 s; `CdcDeliveryTracker.gapTimeoutFor`), cap 10 000 runs (WARN once). Gap = one run whatever its width; only `MAX_AWAITED_ORDERS_PER_GAP_END` (5 000) deep from each end recorded as transient rows (orders in-flight txs can hold); middle of a wider one (sequence `setval`, restore) awaited in memory only (`awaitedInMemoryOnly`, one range, split O(log runs) by a late fill), after timeout drained apart (`drainTimedOutGapsAwaitedInMemoryOnly`), no rows ever; restart/crash inside the window loses it - same contract as a cap-dropped gap; never record or give up a gap order by order again - a 1M hole wrote 1M rows before hand-on. Polling resumes `W + 1`; catch-up reads from highest delivered + 1 and re-queries awaited gaps by order on first page (max 1 000). Bus thread reads tracker lock-free only (`isAtOrBelowWatermarkAndNotAwaited`). Crash safety: `DeliveryGate` (one per subscription, one gap handler instance) records an opened gap with the gap handler before handing the event on (resume point moves past gaps), and resolves a filled one only once the subscriber is done with it - `acknowledged`, in the subscriber's UoW, when it passed a `SubscriberAcknowledgement` (forgotten afterCommit; tracker keeps it delivered meanwhile; other tenants' fills when the tenant filter drops them), else `handedOn` via `reportingHandedOn` after the gate / after `BackfillThenLiveOrdered`'s output (`hide()` first: the reporter is no `QueueSubscription`); back-fill pages leave the gaps they fill open for it, and every reconcile is given the fills awaiting acknowledgement so it cannot promote them; each delegate poll gets a fresh acknowledgement the gate forwards to (`newDelegateAcknowledgement`), so it leaves fills to the gate; stores never dispose an ack registration when a subscribe ends (late in-flight acks still resolve) - only a re-subscribe of the same flux (`retry()`/`repeat()`) disposes the ended subscribe's registration before registering the next (`internal.AcknowledgementRegistrations`, shared by both stores), and an unacked fill from it keeps its gap and is handed on again; `SubscriberAcknowledgement` WARNs only while > 1 registration is active (atomic count); tracker seeded from `getTransientGapsFor` at subscribe so a below-resume-point fill survives restart / lock hand-over. Gate records an opened gap's upper end via reconcile (with the event), a wide gap's lower end via `SubscriptionGapHandler.addTransientGaps` (default no-op). A tracker give-up is durable: the gate drains the tracker's timed-out ranges (`drainTimedOutGaps`, one `LongRange` per gap, which expires due gaps first) after every `deliver` and in `subscriptionEnded` (`handOn`'s `doFinally`; skipped when a UoW is current on the ending thread) and records them via `SubscriptionGapHandler.giveUpTransientGapRanges` (default expands to `giveUpTransientGaps`; PG = one DELETE…RETURNING→INSERT statement, array params; own UoW, under the handler's monitor, never across commit; a failure `requeueTimedOutGaps`), so a late commit is dropped by the running subscription and after a restart alike. A give-up is a permanent gap of the whole aggregate type - every subscriber skips it - so only gaps waited the full `gapTimeout` are drained: a cap-dropped gap (> 10 000) is never collected, stays transient, next subscription waits again. `PostgresqlEventStreamGapHandler`: per-order `giveUpTransientGaps` deletes `MAX_GLOBAL_ORDERS_PER_STATEMENT` (1 000) per statement - one `IN` list broke PG's 65 535 bind-parameter cap; new SQL binds order lists as one `bigint[]`, never one param per order; reconcile reads permanent gaps of its range only, into a `Set`. Non-acking subscriber: `handedOn` runs in the downstream's `onNext`, so it logs a resolve failure, never throws (would end the subscription); `acknowledged` acks the delegate poll even when resolving failed; every event the gate drops is acknowledged to the delegate poll (except a fill the subscriber still holds), or the delegate strands its gap. `recordOpenedGap` passes no `transientGapsIncludedInQuery` - nothing queried them - so the CDC live path promotes only via give-up. Everything in the pipeline loads all tenants, tenant filter after tracker - SQL tenant filter = fake gaps. CDC `TenantFilter` resolves the `TenantSerializer` at the first event with a tenant and keeps it (aggregate type may be configured after subscribe); until then compares `toString()` + one WARN - never throw there, it ends the subscription (polling's `tenantFilter` does throw). `BackfillThenLiveOrdered` records on emit (backfill filter, drain); its live source only peeks. Its drain never waits for a global order: after backfill, buffered live events in global order, then each as it arrives (commit order). Was strict +1 past head → every rolled-back append parked it till `liveDrainStallThreshold` (180 s); never make it wait for a hole again - holes never fill. Threshold property, `CdcLiveDrainStalledException`, `stall_detected` counter kept for compat, inert. Drain serialized by missed-counter (one drainer, re-entrant safe). The drain is also the only emitter of the live-sink's error/completion (`orderedLiveSink` is a checked sink: a direct `tryEmitError` racing the drain returned `FAIL_NON_SERIALIZED`, ignored, and the failure was lost); `BusHandOver`'s hand-over sink is `Sinks.unsafe()` with a single serial producer. Pinned by `CdcDeliveryTrackerTest`, `BackfillThenLiveOrderedTest`, `CdcEventStoreCommitOrderIT`, `CdcEventStoreGapFillAcknowledgementIT`, `CdcEventStoreConcurrentWritersIT`, `CdcEventStoreLiveTailHoleIT`, `CdcEventStoreSequenceJumpIT`
- **Interruptions ≠ fallbacks.** `CdcAvailability.set` records one interruption per `ACTIVE` → `FAILED`/`INACTIVE` transition, except `INACTIVE` with `STOPPED_REASON` (requested stop). Kept after recovery — `active()` clears `reason`, so interruptions are the only trace of a recovered outage. Tailer's stop path must keep passing `CdcAvailability.STOPPED_REASON`, or every shutdown counts as an interruption
- **One stack trace per dropped replication connection.** `streamOnce` logs RETRY_CONNECTION errors without the throwable — `runPollLoop`'s `streamOnce failed` logs it with LSN context. Slot-lock release failure on a broken connection (SQLState `08*`) is DEBUG: session end releases advisory locks
- **`everActive` distinguishes "healthy" from "CDC never came up"** — both report `fallbackCount = 0`. A non-zero `warmupPollCount` with `everActive = false` means nothing was ever delivered over CDC
- **Slot-lock contention is the design, and must not be logged as a fault.** A replication slot is exclusive, so in a deployment of n instances n-1 are permanently standing by — the same shape as an exclusive subscription behind a fenced lock. It used to WARN every 20th attempt with a failure count and "check for stuck replica pods or duplicate deployments", which on an ordinary second instance repeated for the life of the process; duration cannot separate a stand-off from a healthy standby, because a healthy standby stands by forever. Now: one INFO on entering standby, a reminder every 30 min, DEBUG in between, and `logConnectAttempt`/`logNormalExit`/"Opening replication connection" drop to DEBUG while `standingBy()` — they were three INFO lines every few seconds, burying the one line that says what is happening. **The alertable question is "is anything delivering", not "does this instance hold the slot"** — that is `CdcEffectivenessMonitor`'s and the `essentials.cdc.wal2json.slot_lock_acquired` gauge's, and no instance can answer it alone
- **pgoutput publication coverage**: `WalReplicationTailer.onStreamStarted()` checks that every event-stream table is in the configured publication. Missing tables → CDC runs silently without events. Most common operator mistake.
- **CDC must reproduce the polling path's `PersistedEvent`, field for field — including types.** `PersistedEventRowMapper` deserializes `aggregate_id` via the configured `AggregateIdSerializer`, so `PersistedEvent.aggregateId()` holds the *typed* id. The WAL only carries text, so CDC converters must do the same via `AggregateIdSerializerResolver`; skipping it hands subscribers a raw `String` under CDC and a typed id under polling. That broke `EventProcessor.forwardEventToInbox` for every forwarded event (`Expected java.lang.String to be an instance of …Id`), silently starving projections while CDC itself reported zero failures. Payload parity is gated by `WalReplicationWithEssentialsAggregatePgOutputIT#cdc_delivered_events_are_field_for_field_identical_to_polled_events`, which diffs CDC-delivered events against `loadEventsByGlobalOrder` including the aggregate-id's runtime class. Don't mistake `CdcEventStoreSubscriptionParity_IT` for that gate — it runs against an INACTIVE `CdcAvailability`, so it exercises fallback-to-polling and never touches the converter. Payload JSON is compared *parsed*, not textually: the polling path returns Postgres's `jsonb` rendering while CDC returns the converter's canonical compact form, and that re-serialization is deliberate
- **The CDC inbox `lsn` column is a dedup key, not a WAL coordinate** — it comes from `LogicalDecodingPlugin.inboxDedupKey(payload, lsn)`, which defaults to the raw LSN. pgoutput must override it: the streaming protocol reports **every** RELATION (`'R'`) message at `0/0`, so a raw-LSN key lets `unique(slot_name, lsn)` + `on conflict do nothing` collapse all tables' schema onto one row — the first table works, every other one quarantines its every insert with `MissingRelationMetadataException`. Single-table tests cannot see this; CDC tests need ≥2 event-stream tables
- **The decoder's relation cache is in-memory, its source is the inbox** — RELATION messages stream once per replication session, so a restarted dispatcher starts blind. `CdcDispatcher` primes from retained `'R'` rows on start and re-primes once per tick on a cache miss; those rows are exempt from `DispatchedRowPolicy.DELETE` so the source survives
- **`polling.gapReconciliations` is a pass count, not a gap count** — one per poll, gap or no gap. Gap numbers live in `gaps` and come from DB row counts (concurrent non-exclusive reconcilers must not double-count). CDC backfill calls the gap handler directly — any new gap-handler call site must report `gapReconciliationOutcome` too, or its gaps vanish from stats.
- **A pgoutput slot older than its publication can never stream** — pgoutput resolves the publication as of each decoded change, so the first change between slot and publication creation fails `publication "…" does not exist` (SQLState `42704`) and, nothing confirmed, every reconnect replays it. The tailer recreates the slot when that error names its publication *and* the publication exists now — once per `start()`, so a publication being dropped/recreated repeatedly surfaces as an ERROR instead of a recreate loop. A genuinely missing publication is left alone. Pinned by `WalReplicationWithEssentialsAggregatePgOutputIT#pgoutput_slot_created_before_its_publication_is_recreated_instead_of_failing_forever`. How the demo DB got a slot older than its tables is unexplained — not reproducible on a fresh DB
- **Replication slot name** computed by `DefaultCdcSlotNameProvider`; slot persists on PG side — deleting/recreating mid-stream causes gap. `PgReplicationSlots.forceRecreate` exists for recovery but loses all unread WAL.
- **Polling read position never moves backwards** (`accumulateAndGet(.., Math::max)` in both poll loops). Gap fills sort first and lie below it; `set(order + 1)` re-delivered everything above a fill. `PollEventStoreTask` reconciles only the prefix it publishes within demand (`eventsWithinDemand`) - a gap fill beyond demand stays a transient gap, else resolved-then-dropped = lost. **A gap fill's gap is resolved only once the subscriber is done with it** - the transient gap is the only durable record of a fill below the resume point, so resolve-then-handle lost it on any stop/crash in between. With a `SubscriberAcknowledgement` (`pollEvents`/`unboundedPollForEvents` overload; the manager's subscribers pass one and acknowledge inside the handler's UoW, plus skipped/handed-off events, never STOP/stopped/ignored ones): `GapFillsAwaitingAcknowledgement` registers a fill right before publishing, never re-publishes it while awaiting (later polls read it again - gap open), keeps its gap out of resolution and gives it to every reconcile (no promotion), and resolves it with `SubscriptionGapHandler.resolveFilledGaps` in the acknowledging UoW (forgotten afterCommit). Covers a batch queue, an async I/O retry and the `limitRate` queue. Without one: resolved after the poll published it (`resolveGapsFilledByPublishedEvents`, one extra UoW per poll with fills; none if cancelled first), and the subscribers fall back to holding the resume point (`holdResumePointBelow`, lowering on an ignored fill) only while `!isHonoured()`. Gap handler calls hold its monitor (acks run on the subscriber's thread), never across a commit. The gap handler never promotes a gap whose event it is given, nor one the reconciling query did not ask for (only a query that asked and got no event proves it still missing): `findTransientGapsToIncludeInQuery` adds the gaps the promotion strategy would promote now (≤ 50, lowest first) to whatever the include strategy returned, `reconcileGapsAndReport` promotes only those in `transientGapsIncludedInQuery`. Custom include strategies compose the default via `ResolveTransientGapsToIncludeInQueryStrategy.defaultSelection()`. Gap handler must be built on the event store's `UnitOfWorkFactory`: another one resolves gaps in a separate transaction (crash window); handler detects "no current UoW on own factory", WARNs once and runs in own UoW. Polling loads **all tenants** (`loadEventsForPoll`), tenant filter in memory after reconcile, same as CDC - SQL filter turned other tenants' orders into transient→permanent gaps. Re-subscribe of an acked flux: see `internal.AcknowledgementRegistrations`. Interrupted `PollEventStoreTask` without a cancel → `sink.error(InterruptedException)` + WARN, else the subscriber waits forever; scheduler released by `sink.onDispose` (error too, not just cancel). Default gap query (`TransientGapsQuerySelection`, per subscription and `defaultSelection()` instance - `RotationKey`; the `ScopedValue` is bound only on the gap handler's thread, another thread falls back to the instance's shared map): all ≤ 50, else 20 newest + 10 lowest + rotating 20; old "2 lowest" starved a late commit above rolled-back holes until promotion, lost it when promoted together. Reconcile walks holes between events (`internal.GapEnds`), never orders of the range: a new hole is recorded only `SubscriptionGapHandler.MAX_AWAITED_ORDERS_PER_GAP_END` (5 000, shared with CDC) deep from each end; middle of a wider one (`setval`, restore) awaited in memory only (`internal.GapMiddlesAwaitedInMemory`, per poll flux like the read position; one `TreeMap` entry per range, split O(log n) per delivered order; `await` only extends above the highest order ever awaited, so a repeated poll never re-awaits a delivered order), same contract as CDC: each poll does one indexed `findLowestGlobalEventOrderPersisted(uow, type, range)` per middle and loads ≤ batch size orders from the first hit, delivered as gap fills (ack/hand-on rules unchanged; every consumed order leaves the middle, any tenant, whichever query read it); dropped after `transientGapGiveUpThreshold()` (else 120 s), DEBUG, no rows; restart/crash inside window loses it - a 1M hole wrote 1M rows, sorted every poll, then 1M permanent. Poll after an empty one: one indexed `findLowestGlobalEventOrderPersisted(uow, type, LongRange.from(next))` replaces the range query (`rangeToRead`) - none → reads no range (idle cost unchanged), above the range → range widened straight to it + batch, hole reconciled by that poll; was growth over empty polls only, hours for a 1M `setval` at starter defaults. Pinned by `PollingGapHandlingIT`, `PollingSequenceJumpIT`, `GapEndsTest`, `GapMiddlesAwaitedInMemoryTest`, `PersistedEventSubscriberResumePointTest`, `TransientGapsQuerySelectionTest`
- **Gap promotion window**: transient gaps become permanent after the DB transaction timeout elapses. Changing PG `statement_timeout` affects gap behavior. Use `PostgresqlEventStreamGapHandler` (not `NoEventStreamGapHandler`) in production.
- **Exclusive subscriptions use `PostgresqlFencedLockManager`**. If lock TTL is shorter than subscription resume time, ownership flaps. Size lock TTL accordingly.
- **`EventStoreUnitOfWork` accumulates events in-memory** then fires callbacks at commit. Interceptors touching accumulated events (e.g. `FlushAndPublishPersistedEventsToEventBusRightAfterAppendToStream`) must handle re-entrant appends carefully.
- **Warm-up subscribers** (backfill phase) must not stay pinned to polling mode after catching up — `CdcEventStore` tracks per-subscriber phase transitions explicitly. Switch happens after `activeCutbackDebounce` (first state change is not debounced, later ACTIVE ones are)
- **Tests build serializers via factories** (`EssentialsJSONEventSerializers.create()`, `EssentialsObjectMappers.createJSONSerializer()`) — hand-built mapper drifts from persisted format.
- **Multi-tenancy**: tenant filtering happens at query time via optional `Tenant` param on all load/poll ops. No row-level security — tenant isolation is application-layer only.
- **`EventStoreSubscriptionObserver` is a single-slot SPI** — one instance is handed to `PostgresqlEventStore` and the subscription manager. Anything new that needs the callbacks decorates, never replaces: `StatisticsCollectingEventStoreSubscriptionObserver` delegates first and records after, and swallows its own recording failures (logged once) so observability can never break a subscription.
- **Subscription statistics are per-JVM, resume points are cluster-wide** — mixing them silently is the trap. `DefaultEventStoreApi` marks the join explicitly (`runningInThisInstance`, nullable live-state fields), because an exclusive subscription legitimately reports zero throughput on every instance that does not hold the lock. A zero counter is not a stall.
- **Polling callbacks fire only on the polling path** — `eventStorePolled` / `resolvedBatchSizeForEventStorePoll` / `skippingPollingDueToNoNewEventsPersisted` are invoked by `PostgresqlEventStore`; `CdcEventStore` only delegates `getEventStoreSubscriptionObserver()`. `handleEvent` still fires under CDC (`PersistedEventSubscriber`), so a CDC-served subscription shows throughput with zero polls. Don't read that as a broken subscription
- **`api` DTOs must stay loadable without reactor on the classpath** — `admin-api-spec` reflects over them with only the API types present, so a DTO method signature mentioning `EventStoreSubscription` (which drags in reactive-streams) fails spec generation with `NoClassDefFoundError: org/reactivestreams/Subscription`. Live-state mapping therefore lives in `DefaultEventStoreApi`, not in `ApiSubscription`
- **`findAllSubscriptions` deliberately queries no event stream** — `findHighestGlobalEventOrderPersisted` scans per aggregate type and is exposed as its own on-demand operation. Don't compute lag inside the list call; the admin UI's cost banner says why
