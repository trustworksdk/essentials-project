# postgresql-queue-shard-owned-adapter

Presents the shard-owned engine as a `DurableQueues`, so `Inbox`, `Outbox` and `DurableLocalCommandBus` run on it unchanged. Published, like the engine it adapts — no `maven.deploy.skip`; only the `examples/` modules carry one. It serves the `DurableQueues` surface only partially, and the two operations it refuses say so in their own message.

Engine docs: `docs/durable-queue-shard-owned.md`.


## Why this is a small adapter and not a rewrite

Inbox, Outbox and `DurableLocalCommandBus` touch a handful of `DurableQueues`' ~30 methods and never touch a `QueueEntryId`: `queueMessage`, `queueMessages`, `consumeFromQueue`, `purgeQueue`, `getTotalMessagesQueuedFor`, `getUnitOfWorkFactory`.

## Classes

| Class | Responsibility |
|---|---|
| `ShardOwnedDurableQueues` | The adapter. Builder-constructed |
| `ShardOwnedDurableQueueConsumer` | `DurableQueueConsumer` over a `Subscription` |
| `ShardOwnedQueuedMessage` | `QueuedMessage`, in a full and a partial shape |
| `MessageEnvelope` | The persisted payload format |
| `QueueEntryIdCodec` | `QueueEntryId` <-> `(QueueName, MessageId)` |

## Gotchas

- **`queueMessage(queue, OrderedMessage, delay)` is the one call whose ORDERING differs from `PostgresqlDurableQueues`.** There the delay blocks the whole key; here only visible rows are dispatched, so an undelayed later `order` for that key goes first. `toEngineMessage` is where the adapter reaches `Message.delayedOrdered`, which is why that factory cannot simply be retired. Left deliberately — reasoning and reopen trigger in `docs/durable-queue-shard-owned.md` §18.3.
- **`InboxName.asQueueName()` is `Inbox:<name>`, and the codec's separator is a colon.** So every queue this module exists to serve contains the separator. `decode` splits on the **last** colon — a `MessageId` never contains one. Splitting on the first truncates every inbox and outbox to `"Inbox"`/`"Outbox"` and reports "no such message" against a queue that exists. `an_inbox_or_outbox_queue_name_survives_although_it_contains_the_separator` derives the names from the real types, so a change to that derivation breaks the test rather than production.
- **The queue name has to be inside the `QueueEntryId`.** Most of the by-id surface takes an entry id and nothing else, which works for `PostgresqlDurableQueues` because its ids are UUIDs. A `MessageId` is unique per queue only — `u-0-1` exists in every queue — so ignoring that would let `deleteMessage` delete an unrelated queue's message and return `true`.
- **Acks never enlist in a caller's transaction.** They are batched and flushed on the owner's connection under a fence. Since 0.60 retired `TransactionalMode` that is the contract for every `DurableQueues`; before it, this adapter had to refuse `FullyTransactional` for this reason.
- **Enqueue IS transactional and that is the load-bearing test.** `HandleAwareUnitOfWork.handle().getConnection()` -> `enqueue(Connection, …)`. `an_outbox_enqueue_rolls_back_with_the_callers_transaction` was verified to fail when that path is disabled — without it the Outbox leaves messages describing work that rolled back.
- **`ShardOwnedQueuedMessage` is still partial on the push path, but the id is no longer part of what is missing.** The engine's `MessageHandler` receives `(messageId, key, payload, payloadType)`. The id was split off from the rest because the two halves have completely different prices: the owner already knows its own lane and shard and `seq` is already a column of `ShardOwnedStorage.Row`, so supplying it costs the cursor read **nothing** — where `attempts`, `enqueued_at`, `visible_at` and `last_error` would each add a column to a read that runs ~2x per delivered message. Those still throw. A stub `getTotalDeliveryAttempts()` of 0 would make attempt-keyed logic silently never fire, which is why it is a throw and not a default.
- **Widening the handler cost exactly what the old version of this note predicted**: 2 internal interfaces (`PayloadHandler`, `OrderedPayloadHandler`), 3 call sites in engine main, `HandleMessage`, and ~100 lambda sites across the engine's tests, the adapter, the starter and the perf lab. Mechanical, and the compiler finds every one. What it bought is that a handler needing the absent fields can now fetch them itself with `getQueuedMessage(getId())` — a per-lookup cost paid by the handler that wants it, instead of a per-message cost paid by everyone.
- **The partial message's throw reaches callers through *log statements*, and this is why the id was worth bridging.** `ViewEventProcessor` passed `queuedMessage.getId()` as a log argument; arguments are eager, so it ran on every delivery whatever the level and dead-lettered every projection message. That specific failure is now impossible — `getId()` is answered. The shape still applies to `getTotalDeliveryAttempts()` and the timestamps: when a framework class touches the partial surface the failure looks like the framework being broken, so grep for those in delivery paths before blaming the engine.
- **`markForRedeliveryIn(delay)` redelivers, but not after `delay`.** The adapter turns it into a throw, and the engine schedules from its own policy — there is no id to schedule against from inside a handler. The attempt also counts against the policy's budget.
- **Retry is the engine's, not `DefaultDurableQueueConsumer`'s.** That class implements redelivery itself; this consumer does not use it. Running both would put two retry clocks on one message. The `RedeliveryPolicy` is translated once into `ConsumerOptions` at subscription time — note the off-by-one: the policy counts *re*deliveries, the engine counts attempts.
- **`MessageEnvelope` is a persisted format from the first enqueue.** `payloadType` (the engine's opaque int) carries `FORMAT_VERSION`, so a future format is distinguishable per row — it is the only field outside the envelope, hence the only one readable before deciding how to parse. Payload and metadata are nested JSON *strings*, which is why they appear escaped in the readable views; a flat three-string object beats embedding a document whose shape depends on an unresolved type.
- **Metadata travels as its own envelope field**, not merged into the payload — a payload with its own `metaData` property would otherwise collide.
- **An unknown queue name REGISTERS by default; zero restores the refusal.** Refusing was the original default and it made the adapter a non-starter: under `DurableQueues` almost every queue is invented by the framework and named by it — `Inbox:<processorName>` (`EventProcessor`), `<processorName>:queue` (`ViewEventProcessor`), `Outbox:<name>`, `DefaultCommandQueue` — so declaring them up front means hard-coding three conventions that differ between the two processors. The demo's six queues were five invented and one declared. What refusing protected against also weakened: `shardCount` caps the *unordered* lane's instance count, `growShardCount` raises it online with no restart, and the ordered lane does not read it — so guessing low costs a ceiling until someone raises it, against an inbox that silently never consumes. `setAutoRegisterShardCount(0)` is for an application that names all its own queues and wants a typo to fail.
- **The default makes `setDataSource` effectively required** — registration writes through it. Omitting it now fails at `build()` with `autoRegisterShardCount needs a dataSource to register with`, not at the first unknown name. The adapter's own IT had never passed one, because it never needed one.
- **The unresolvable-name throw still matters where refusal is chosen.** It comes from `resolve`, which for an `Inbox` in `SingleGlobalConsumer` mode lands inside the fenced lock's `onLockAcquired` callback — that used to leave the lock held with the inbox silently never consuming. `DBFencedLockManager` now releases the lock when a callback throws, so the message is logged each tick and the inbox starts on its own once the queue is registered, with no restart. See `foundation/CLAUDE.md`.
- **Pass the same `MessageQueues` the rest of the process uses.** Two registries each build their own `MessageQueue` per name, which register as two competing consumers and get half the shards each.
- **`getQueuedMessages` works now, and refusing it was a mistake with a visible cost.** The admin console's message browser is built on it, so every application running its `DurableQueues` on this engine served HTTP 500 from that page while the queue list, depths, dead letters and by-id operations all worked — 10 of the 11 methods `DefaultDurableQueuesApi` calls. `MessageQueue.messages(offset, limit, ascending)` backs it, ordering by `(lane, shard, seq)` — which **is** the message id, so it satisfies the contract's "sort order for `getId()`" exactly. Not arrival order, and neither is `PostgresqlDurableQueues`' answer; what it guarantees is that paging never duplicates or skips a row.
- **`hasOrderedMessageQueuedForKey` is served, and refusing it was silently expensive.** `ViewEventProcessor` asks it before forwarding an event: key already queued → queue behind it, otherwise handle inline. Throwing did not disable that decision — `UnsupportedOperationException` is an `Exception`, so the processor's own `catch` swallowed it and took the *"direct handling failed, enqueuing for retry"* branch **for every event**, logging a failure that had not happened and making the inline path unreachable. Ordering survived only because everything then went through the queue in subscription order. The stated objection was wrong too: it is a prefix seek on the ordered PK `(queue_id, shard, msg_key, key_order)`, on the producing thread, not on the delivery path. Measured after the fix: both `*:queue` projections report `delivered = 0` while their tables are populated — every event handled inline, the queue untouched.
- **`EventProcessor` and `ViewEventProcessor` forward differently, so `delivered` means opposite things on their queues.** `EventProcessor.forwardEventToInbox` enqueues unconditionally, so on an `Inbox:<processorName>` queue the count is the event rate. `ViewEventProcessor.handlePersistedEvent` handles inline and queues only what it could not — a failed attempt, or work held behind one — so on a `<processorName>:queue` the count is an **error signal** and zero is the healthy state. It is also self-reinforcing in both directions: nothing enters such a queue unless inline handling throws, and once nothing is in it `hasOrderedMessageQueuedForKey` keeps answering false. Measured on the demo: 2 254 account events, projection current to within two seconds of the last one, `delivered = 0`. Reading that as a stalled projection is the obvious mistake, which is why the console now says which is which.
- **`DurableQueuesInterceptor`s run here, in the adapter — not bridged onto the engine's chain.** `addInterceptor` used to throw, on the grounds that the engine has its own `MessageQueueInterceptor`. True, and it still does; what the throw missed is that `ShardOwnedQueueAutoConfiguration` displaces the `durableQueues` bean that `EssentialsComponentsConfiguration` applies the interceptor beans to, so selecting this engine silently dropped every one of them — `RecordExecutionTimeDurableQueueInterceptor` included. Nothing threw and the queue timers just stopped. The adapter now runs the chain around its own methods (`InterceptorChain.newInterceptorChainForOperation`, the same idiom as `PostgresqlDurableQueues`). Bridging onto the engine chain was the wrong shape and was considered first: that chain carries two operations, `EnqueueMessages` and `HandleMessage`, against `DurableQueues`' twenty-one — it would have carried two and dropped nineteen, which is the "silence instead of spans" failure in a new costume. The two chains are independent and both may be used.
- **Each public method runs only its own chain, which is why the `do*` helpers exist.** `queueMessage` used to delegate to `queueMessages`, `acknowledgeMessageAsHandled` to `deleteMessage`, `retryMessage` to `getQueuedMessage`. Through a chain that shows an interceptor two operations for one call, and a metrics interceptor then reports twice the enqueues. `doQueueMessages`, `doDeleteMessage`, `doGetQueuedMessage`, `doGetDeadLetterMessage(s)` and `doMarkAsDeadLetter` are the uninterceptable insides; `queueing_one_message_is_one_operation_and_not_two` pins it.
- **A `HandleQueuedMessage` interceptor is handed the *partial* message.** Same surface the handler gets: `getId()` is answered, `getTotalDeliveryAttempts()` and the timestamps throw. `RecordExecutionTimeDurableQueueInterceptor` tags with `operation.message.getQueueName()` only and was always safe; a third-party interceptor reaching for the **attempt count** still fails the delivery, and the stack trace will look like the framework breaking. `a_delivery_interceptor_gets_the_queue_name_the_payload_and_the_id_but_not_the_attempt_count` pins the boundary, and `a_handler_can_use_its_message_id_to_read_the_fields_it_was_not_given` pins the escape hatch.
- **Not supported, each for a structural reason, both throwing with it:** `queryForMessagesSoonReadyForDelivery` (ordering by next-delivery timestamp across every shard of both lanes — no index produces it and there is no single sequence to merge on; a different question from paging by id, which `getQueuedMessages` answers), `getNextMessageReadyForDelivery` (needs a row-lease session outliving the call). `getNextMessageReadyForDelivery` is also the one operation of the twenty-one an interceptor never observes, because there is no call to intercept.
- **`resurrectDeadLetterMessage` returns empty even on success.** The message re-enters at a fresh sequence, so its `QueueEntryId` changes and the old one no longer addresses it.
- **Two `queue` packages export `QueueName`, `Message` and `QueuedMessage`.** Single-type imports for the engine's other types; those three written out in full wherever an engine one is meant. Star-importing both is a compile error, and it is the first thing that happens to anyone adding a file here.
- **The test module needs both Jackson majors, the datatype modules and objenesis explicitly.** `foundation` declares them optional/provided, so none is transitive, and `EssentialsObjectMappers` picks a branch at runtime — naming one flavor makes the tests fail under the other profile instead of exercising it.

## Not done

- ~~No Spring auto-configuration.~~ **Done**: `spring-boot-starter-postgresql-queue-shard-owned` selects this `DurableQueues` on `essentials.shard-owned-queue.durable-queues-enabled` (default false), with `auto-register-shard-count` beside it. It orders itself with `@AutoConfiguration(beforeName = "…EssentialsComponentsConfiguration")` — by name, so the starter takes no compile dependency on `spring-boot-starter-postgresql` — and wins because that class declares its `PostgresqlDurableQueues` `@ConditionalOnMissingBean`. The adapter is a **hard** dependency of that starter, not optional: optional plus `@ConditionalOnClass` would make the flag a silent no-op for anyone who set it without adding the jar.
- ~~Three operations still throw.~~ **Two do**, and the admin surface needs neither: `queryForMessagesSoonReadyForDelivery` and `getNextMessageReadyForDelivery`. `addInterceptor`/`removeInterceptor` were the third and are now served — see the interceptor gotchas above. `getQueuedMessages` — the one the console's message browser is built on — is served too.
