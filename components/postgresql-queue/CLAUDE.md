# postgresql-queue

PostgreSQL-backed durable queue — `FOR UPDATE SKIP LOCKED` polling, ordered/unordered delivery, dead-letter, competing consumers. Maven: `postgresql-queue`.

## Package Structure

- `dk.trustworks.essentials.components.queue.postgresql` — all main sources (flat, no sub-packages for domain logic)
- `dk.trustworks.essentials.components.queue.postgresql.jdbi` — JDBI argument/column mappers for `QueueName` and `QueueEntryId`

## Key Classes

| Class | Internal role |
|-------|---------------|
| `PostgresqlDurableQueues` | Main impl of `BatchMessageFetchingCapableDurableQueues`; owns table init, consumer registries, interceptor chain, LISTEN/NOTIFY wiring |
| `PostgresqlDurableQueuesBuilder` | Builder (prefer over constructors); default: `SingleOperationTransaction`, centralized fetcher, 20ms poll interval |
| `DurableQueuesSql` | All SQL strings; parameterized via `{:tableName}` binding → avoids injection after `PostgresqlUtil.checkIsValidTableOrColumnName` guard |
| `DurableQueuesSerialization` | Wraps `JSONSerializer`; deserializes payload + metadata; throws `DurableQueueDeserializationException` on failure (not runtime crash) |
| `QueuedMessageRowMapper` | JDBI `RowMapper<QueuedMessage>`; shared by single + batch fetch paths; injected with payload/metadata deserializer lambdas |
| `MessageMappingResult` | Record holding successful + failed mappings per batch poll; failed entries don't abort successful ones |
| `PostgresqlDurableQueueConsumer` | Traditional per-queue polling consumer; extends `DefaultDurableQueueConsumer` from foundation |
| `SingleOperationTransactionDurableQueuesInterceptor` | Wraps each `DurableQueues` operation in its own UoW when mode = `SingleOperationTransaction` |
| `QueueTableNotification` | Deserialization target for PG LISTEN/NOTIFY payloads from the `durable_queues` trigger |
| `QueueNameDuplicationFilter` | Collapses N notifications for same `queue_name` in a single poll batch into 1 → reduces redundant wakeups |
| `PostgresqlDurableQueuesStatistics` | Separate bean; implements `DurableQueuesStatistics`; owns its own table + TTL job for delivery logs |
| `PostgresqlSplitDurableQueues` | Two-table variant: composes two `PostgresqlDurableQueues` (`<base>_unordered` / `<base>_ordered`) so each carries only the indexes its own access pattern needs. Owns both tables' DDL, the consumer registry and the single fetcher |
| `PostgresqlSplitDurableQueuesSettings` / `…Builder` | Config record + builder for the above; defaults are `PostgresqlDurableQueuesBuilder`'s |

Foundation classes used but not owned here (in `foundation` module):
- `CentralizedMessageFetcher` — single poll thread across all queues, dispatches to worker threads
- `CentralizedMessageFetcherDurableQueueConsumer` — consumer registered with centralized fetcher
- `DefaultDurableQueueConsumer` — per-queue poll-thread base (traditional mode)

## Test Structure

- All ITs under `src/test/java/.../queue/postgresql/`
- Require real Postgres via **Testcontainers** (`@Testcontainers` + `PostgreSQLContainer<>`)
- Base class pattern: `PostgresqlDurableQueuesIT` extends `DurableQueuesIT` (from foundation test module); concrete subclasses flip `useCentralizedMessageFetcher()` → `true`/`false`
- Naming convention: `Centralized*IT` = centralized fetcher, `Traditional*IT` = legacy per-consumer, `SingleOperationTransaction*IT` = explicit-ack mode
- `*PerformanceIT` / `*LoadIT` / `*LatencyIT` — throughput/latency benchmarks, not part of normal CI
- `PostgresqlDurableQueuesTest` — unit tests using Mockito mocks (no DB), covers table name validation, init behaviour

## Extension Points

- `DurableQueuesInterceptor` — implement to intercept any queue operation; registered via `builder().addInterceptor(...)` or `durableQueues.addInterceptor(...)`; order controlled by `InterceptorOrder`
- `QueuePollingOptimizer` — pluggable per-queue backoff strategy for traditional consumers (`setQueuePollingOptimizerFactory`)
- `CentralizedQueuePollingOptimizer` (or custom `QueuePollingOptimizer`) — per-queue backoff for centralized fetcher (`setCentralizedQueuePollingOptimizerFactory`)
- `JSONSerializer` — swap Jackson serializer; affects payload + metadata columns
- `NotificationDuplicationFilter` — pluggable dedup for LISTEN/NOTIFY (module ships `QueueNameDuplicationFilter`)

## Gotchas

- **`FullyTransactional` mode is broken for retries/DLQ**: rollback reverts attempt count → retry logic fails. Always use `SingleOperationTransaction` in production.
- **Table name → SQL injection risk**: `sharedQueueTableName` is interpolated directly into SQL via `{:tableName}`. `PostgresqlUtil.checkIsValidTableOrColumnName` is first-line defense only; caller must sanitize.
- **Schema auto-migrates on startup**: old composite indexes (`idx_*_queue_name`, `idx_*_next_delivery_ts` etc.) are **dropped** and replaced each start. Not zero-downtime safe across versions if index names change.
- **`useOrderedUnorderedQuery` flag**: when `true` (the default everywhere as of the queue fix), enables separate ordered/unordered CTE paths + corresponding partial indexes. Both paths must stay in sync in `DurableQueuesSql`. It used to be `false` in `PostgresqlDurableQueuesBuilder` while the Spring starter defaulted it to `true`, so non-Spring callers silently got the unified query — up to **5.4× slower** on a backlog mixing ordered and unordered messages, because that query runs the ordered per-key barrier (a correlated `NOT EXISTS`) against every candidate row including unordered ones that cannot need it, and sorts by `key_order` which is a constant `-1` for those rows. Pure-ordered traffic is indifferent. (Measured at 4000 rows, medians of 5 repetitions, PostgreSQL 17.5.) `CentralizedFetcherDurableQueueIT` / `CentralizedFetcherDurableQueueIT_WithOrderedUnordered` are the `false`/`true` pair and both now set the flag explicitly, so neither can drift onto the default.
- **Centralized fetcher is default**: `transactionalMode` defaults to `SingleOperationTransaction` (not `FullyTransactional`). **Builder and constructors now agree** — until 0.40.x the multi-arg constructors hardcoded `FullyTransactional` while `builder()` defaulted to `SingleOperationTransaction`, so the same component behaved differently depending on how it was created. They were converged on the builder's defaults (`SingleOperationTransaction` + `DEFAULT_MESSAGE_HANDLING_TIMEOUT` of 30s), because `FullyTransactional` is the side that is broken for retries/DLQ. A caller that genuinely wants `FullyTransactional` must now name it explicitly. This is a behaviour change for existing constructor callers — see `docs/MIGRATION-NEXT_MAJOR.md`.
- **Batched fetch (`setUseBatchedFetch`)**: opt-in, one claim statement across all active queues instead of one per queue per poll (`DurableQueuesSql.buildBatchedSqlStatement`, `fetchNextBatchOfMessagesBatched`). **Competing consumers ARE handled** — candidates are picked unlocked, then a second scan re-checks `is_being_delivered = FALSE` under `FOR UPDATE SKIP LOCKED`, so a row another instance claimed in between is dropped. Both were marked "work in progress - doesn't handle competing consumers yet"; that note was stale and is now replaced by evidence: `PostgresqlBatchedFetchCompetingConsumersIT` (2 instances, 4 queues, exactly-once + negative control proving the duplicate detector fires). Still opt-in — correctness is evidenced, throughput is not yet measured, so nothing justifies flipping the default.
  - `batchedFetchSwitchThreshold` = per-queue fetch for active-queue counts **≤** threshold, batched **above** it. Default 4, so a 4-queue deployment silently stays on per-queue fetch; tests that mean to exercise batching must set it to 0.
  - Slot limits are **bound** (`:slotsN::int`), not interpolated — the statement text must stay stable as slot counts move or PostgreSQL cannot reuse a prepared plan. Text still varies with active-queue *count*; unavoidable in a `VALUES` list.
  - Bug #19 (duplicate consumption with multiple pods) is about **over-fetch**, not this statement: `Math.max(0, maxParallelConsumers - activeWorkers)` in `CentralizedMessageFetcher.calculateAvailableWorkerSlotsPerQueue` is load-bearing — `Math.max(1, …)` over-fetches, messages queue behind busy workers past `messageHandlingTimeout`, get reset as stuck, and another pod takes them.
- **Batched acknowledgement (`setUseBatchedAcknowledgement`)**: opt-in. `CentralizedMessageFetcher` coalesces acks into one `DELETE ... WHERE id IN (...)` per batch via `BatchedAcknowledgementBuffer` (foundation). ⚠️ **Not measured to help.** The **16.5×** figure is from a raw-SQL harness; through the component it is **1.02×** on a backlog drain and **1.00×** in steady state with a worse p99 (`docs/durable-queues-measurements.md` §2). Keep it opt-in and don't quote 16.5× as what a deployment gets. Three enforced constraints:
  - `IN_ORDER` messages never buffered — barrier reads completion from *absence* of lower-`key_order` row, so buffered ack stalls key. Measured 0.82×, worse than no batching. Fetcher checks `getDeliveryMode()`. Ordered can't batch until cursor design decouples completion from row deletion.
  - Requires `SingleOperationTransaction` — buffer relies on `resetMessagesStuckBeingDelivered` for acks lost before flush; `FullyTransactional` has no such recovery. Ctor rejects.
  - `flushInterval` ≤ ¼ `messageHandlingTimeout` — else stuck-reset resurrects buffered-ack messages → double delivery. Ctor enforces.
  Off by default: widens redelivery window by one flush interval (semantic change, not just faster). Ack-counting interceptors must implement **both** `intercept(AcknowledgeMessageAsHandled…)` and `intercept(AcknowledgeMessagesAsHandled…)` or they go blind when batching is on.
- **Index set is now five, and evidence-driven** (`PostgresqlIndexUsageIT`, opt-in via `-Dbenchmark.run=true`, sweepable with `-Dindexusage.orderedKeys`): `ready`, `next_msg`, `unordered_ready`, `ordered_head`, plus `ordered_unique` under `REJECT`. Two were removed — `ordered_ready` (zero scans at both 8 and 200 keys) and `ordered_msg` (superseded by `ordered_unique`, which is the same columns partial on `key IS NOT NULL` and which the planner takes for the barrier at both cardinalities). Net **−28% index bytes**. `ordered_msg` is still created under `ALLOW`, where no unique index exists to serve the barrier.
  - **Sweep key cardinality before dropping any index.** `ready` looked dead at 200 keys and takes 21 scans at 8; `ordered_msg` looked essential at 164978 scans until the unique index existed. Single-shape index evidence is not safe to act on — §11 showed the ordered plan is highly sensitive to messages-per-key.
  - Dropping indexes **redistributes** rather than removes: `next_msg` went 408 → 10676 scans afterwards.
- **`orderedMessageDuplicateStrategy` defaults to `REJECT`** — adds a unique index `(queue_name, key, key_order) WHERE key IS NOT NULL`. Two `OrderedMessage`s sharing key *and* order never block each other (the barrier blocks only on a **strictly** lower `key_order`), so that key's ordering silently does not hold. Safe by default because every ordered message the framework produces keys on aggregate id and orders by `EventOrder`, unique per stream; the exposure is app code deriving order from something non-unique. Rejection doubles as idempotent enqueue for an at-least-once upstream.
  - **Partial on `key IS NOT NULL`** — unordered messages all carry NULL key and `key_order = -1`, so a non-partial unique index would reject the second unordered message ever queued. Pinned by a test.
  - **Startup fails on pre-existing duplicates**, naming them, rather than running unprotected — `CREATE UNIQUE INDEX` cannot succeed against them. Look for duplicates *before* attempting the index: a failed statement aborts the transaction, so a diagnostic query after the failure dies with "current transaction is aborted".
  - `ALLOW` restores the old behaviour. `PostgresqlOrderedMessagesMultiNodeIT`'s negative control needs it, since it requires the broken state to prove its detector fires.
- **`QueuedMessage.getDeliveryMode()` is derived, not stored** — `DefaultQueuedMessage` returns `IN_ORDER` iff the wrapped `Message` is an `OrderedMessage`, so it cannot disagree with the persisted `delivery_mode` column (`QueuedMessageRowMapper` rebuilds an `OrderedMessage` from that column). It previously returned `NORMAL` unconditionally, which made it contradict both the column and Mongo's own implementation; found because it defeated batched acknowledgement's ordered-message exclusion. That exclusion now keys off `instanceof OrderedMessage` as well, so the two are independent.
- **A cast inside a `log.debug(...)` argument is live code** — `resurrectDeadLetterMessage` cast the `QueuedMessage` itself to `OrderedMessage` (never possible; a `QueuedMessage` *wraps* a message). SLF4J argument expressions evaluate eagerly regardless of level, so it was only unreachable because the `getDeliveryMode()` bug kept the branch false. **The two defects concealed each other** — fixing either alone would have produced a `ClassCastException` or an unverifiable fix. Pinned by `PostgresqlOrderedDeadLetterResurrectionIT`.
- **`PostgresqlSplitDurableQueues` (two-table split)**: ordered and unordered messages in separate tables, so each carries only the indexes it needs. **Insert-and-storage optimisation, not a throughput one.** Component-measured: unordered 1.07–1.36x total (all of it enqueue 1.34–1.66x, drain parity, ~9% fewer index bytes); ordered parity with ~29% fewer index bytes; steady state indistinguishable from the shared table, capacity within 7%. The **1.38x/1.62x** figures are raw-SQL prototype numbers and never described this implementation. Their premise fails too: "six indexes down to one" counts declarations, but under single-mode traffic the ordered indexes are partial on `key IS NOT NULL` and hold 8 KB (§4).
  - **Two defects made it 5x SLOWER than the shared table, both found by measurement not review, both caused by reusing v1's statements against a schema that deliberately is not v1's**: (1) the composite asked each table for messages it cannot hold — fixed with `ClaimScope`; (2) the split's unordered index omitted `key IS NULL`, which v1's `unordered_ready` has always carried, so every claim took heap fetches instead of an index-only scan and the cost grew with backlog (0.75x at 10k, 0.16x at 40k). A redundant-looking index predicate was load-bearing. Composition, not a rewrite: both tables keep v1's columns, so each is driven by v1's statements unchanged (§7c/§7d of the implementation plan). Acceptance gate is `foundation-test`'s shared `DurableQueuesIT` running against it **unmodified** — `PostgresqlSplitDurableQueuesIT` has no test methods of its own, and anything it had to relax would be a semantic difference the split introduced.
  - **Everything addressed by `QueueEntryId` is ONE statement over both tables** — ack, `deleteMessage`, `retryMessage`, `markAsDeadLetterMessage`, `markAsDeadLetterMessageDirect`, `resurrectDeadLetterMessage`, `getQueuedMessage`, `getDeadLetterMessage`, `getQueueNameFor`. Each was "try the unordered delegate, then the ordered one", which is **two** defects, not one slow path: two statements, and **two runs of the interceptor chain**, because `addInterceptor` registers on the composite *and* on both delegates — so a metrics/tracing/counting interceptor silently double-counted every operation on an ordered message. No correctness test could see it; `PostgresqlSplitDurableQueuesByIdOperationsIT` counts statements and chain invocations instead of results.
    - The cost was originally dismissed as "per failure, not per message". **Wrong**: `retryMessage` is on the delivery path — `CentralizedMessageFetcher` calls it when a handler throws, when a consumer is unregistered, **and for every `markForRedeliveryIn(...)`**, which is ordinary control flow for a handler that defers work, not an error. `markAsDeadLetterMessage` is likewise reached from the fetcher, not only from the admin API.
    - Still composition, not a rewrite: each delegate's own statement is wrapped verbatim as a data-modifying CTE and `UNION ALL`-ed, so v1's statements stay the single definition of what these operations *mean*. Relies on both tables having identical columns — the same invariant `migrateFromSharedTable`'s `INSERT ... SELECT` rests on. The three UPDATEs already end in `RETURNING *`; `deleteMessage` and `markAsDeadLetterMessageDirect` get a `RETURNING 1` appended because they report by rows-affected.
    - `hasMessagesQueuedFor` deliberately still tries one table then the other (`anyTrue`) — it short-circuits on the first table with anything, so the second statement runs only when a combined one would have had to scan both regardless.
  - **`DurableQueuesSql.getQueuedMessageByIdSql()` / `getQueueNameForQueueEntryIdSql()` were dead code** while `PostgresqlDurableQueues` carried inline copies of the same SELECTs — so editing the `DurableQueuesSql` version changed nothing, and the two copies had already drifted (`:id` vs `:queueEntryId`). Now wired up, which is also what let the split compose them. If you add SQL here, check it has a caller.
  - **Registry and claim are separate layers, and must stay separate.** The composite owns the consumer registry and the polling optimizers; the delegates own the tables. So `selectQueuesReadyForPolling` (which queues to visit) / `claimNextBatchOfMessages…` (claim from this table) / `reportPollingOutcome` (feed the optimizers) are three methods, not one. They used to be one, and asked through their public `fetchNextBatchOfMessages`, each delegate consulted its own empty registry and skipped every queue.
  - Report the polling outcome **once over both tables**. Per table, a queue served by the unordered table gets told "no messages" by the ordered one and backs off.
  - The ordered table is claimed **first**, then the unordered one with `slots - alreadyTaken`. Without that subtraction each table fills the full budget and the fetcher hands out up to 2× `parallelConsumers` — the over-fetch behind Bug #19.
  - `queueMessages` on a mixed batch must return ids **positionally**, not grouped by table: callers correlate ids to messages by index, so regrouping silently pairs every id with the wrong message. Pinned by `PostgresqlSplitDurableQueuesRoutingIT`.
  - **The composite owns the LISTEN/NOTIFY wiring**, because v1 installs the trigger inside its schema init and delegates skip that. It installs the trigger on **both** tables, listens on both names, and routes `QueueTableNotification`s **by queue name** into its own registry — so an ordered enqueue wakes the poll that also covers the unordered table. Keying by table would have broken exactly that. With no listener it resolves `QueuePollingOptimizer.None()`: backoff with nothing to end it is only slower.
  - **Switching is not just a flag.** The split never reads the shared table, so flipping `essentials.durable-queues.use-split-queue-tables=true` with a backlog stops those messages being delivered — silently. `migrateFromSharedTable(sharedTableName)` moves them (`INSERT ... SELECT` per mode + `DELETE`, one transaction, bootstrap lock), and **refuses while any row is `is_being_delivered`** — the signature of a live v1 consumer. Trivial only because §7c kept the columns identical. No rolling upgrade: a v1 pod and a split pod on the same base name read different tables.
  - Flag defaults to **false** and stays there until there is operational experience.
  - ⚠️ **How the split should be composed is PARKED pending review (2026-08-25) — don't extend this structure further.** Every defect it has shipped sits on the undrawn boundary between what was reused from v1 and what was re-derived, and the gate that justified composing two `PostgresqlDurableQueues` (the shared `DurableQueuesIT` running unmodified) proves semantics while all three defects were invisible to semantics. Two candidates on the table: an explicit `QueueMessageStore` SPI that is *not* a `DurableQueues`, or a clean-room second attempt built from the requirements without reading this. `docs/durable-queues.md` §7 has the full statement and the open items that are blocked on it.
- **`PostgresqlDurableQueues.Role`** — `STANDALONE` vs `SPLIT_DELEGATE`, and it is deliberately not a boolean. Two things follow from the role and they are the same fact: a delegate does not own its table (skips DDL), and it holds only half the messages (a by-id miss is expected, so `logMessageNotFound` logs at debug instead of error — otherwise an ordinary ordered-message retry emits a spurious ERROR on every delivery). It started as `initializeSchema`, and that name hid the second consequence.
  - **JDBI type-mapper registration is NOT schema initialization.** It sat inside `initializeQueueTables()` behind the same guard, so a delegate could not bind or read a `QueueName` at all (`NoSuchMapperException`). It now runs unconditionally in `registerJdbiTypeMappers()`.
- **The queue's NOTIFY wake-up sets a permission, it does not compare a counter** — `QueuePollingOptimizer.messageAdded(...)` → `CentralizedQueuePollingOptimizer` sets `nextAllowedPollEpochMs = now`. That makes it immune to the missed-wakeup race the event-store's `NotifyEpochSource`/`NotifyAwareEventStorePollingOptimizer` pair exists to solve (compare-a-counter, so *when* the baseline is snapshotted matters). Don't port that epoch machinery here on the strength of the improvements plan's I2 — it solves a problem this path does not have. `messageAdded` has exactly one caller per implementation: the notification handler. That is what makes it a usable assertion target for wake-up tests, and why such a test needs a no-listener negative control to stay honest.
- **`PostgresqlOrderedMessagesMultiNodeIT` is flaky in full-module runs** — its guard assertion "both nodes must consume, or the run is not exercising cross-node behaviour" has failed twice under `mvn verify` and passed every time in isolation. The guard is timing-dependent: it asserts that work landed on *both* nodes, which under a loaded parallel build it sometimes does not. The ordering assertion it guards has never failed. Re-run in isolation before treating it as a regression.
- **`QueueNameDuplicationFilter` deduplicates within one poll batch only** — not across polls. 100 queued messages for same queue → 1 notification per poll cycle, not permanently collapsed.
- **`DurableQueueDeserializationException` keeps message in queue**: deserialization failure does not auto-DLQ the message; consumer must handle/re-throw to trigger redelivery policy.
- **Bootstrap lock**: `initializeQueueTables()` acquires `PostgresqlUtil.acquireBootstrapLock` → serializes DDL on multi-node startup; do not hold external locks that could deadlock this.
