# postgresql-event-log-processor

The application layer of the new event store engine (`components/postgresql-event-log`): typed events, the two
processors, application-sourced page transactions, the commit path and the admin SPI. Unreleased phase-8 work on a
feature branch; it is in no release list, like the engine.

- Design: `docs/plans/event-store-engine-phase8.md` §3, §4.4, §9.2 (unit 8a-C); the `EventStore` adapter §5, §9.4, §9.5 (unit 8b-B). Package `dk.trustworks.essentials.components.eventlog.processor`.
- Depends on the engine, `foundation` and `postgresql-event-store` (for its value types, `EventMetaData`, `JSONEventSerializer`, `AggregateIdSerializer`, `TenantSerializer` only — never its subscription model). JDBI, Spring TX/JDBC, pgjdbc and SLF4J are `provided`. `architecture/DependencyRulesTest` enforces: no old subscription/processor/gap packages, no fenced lock or durable queues, no Reactor, no Jackson (serialize only through the application's `JSONEventSerializer`, from `EssentialsJSONEventSerializers`), and Spring only in `SpringPageTransactions`, `EventLogCommits` and `UnitOfWorkPageTransactions`.
- `EventDeserializer`: `StoredEvent` -> `DeliveredEvent`. An `FQCN:` event type is deserialized through `serializer.resolveClass` (never `Class.forName`); an event *name* keeps its JSON text as payload.
- `ViewProjection` (`CONTIGUOUS`, exclusive, `PageHandler`) and `EventReactor` (`FRESH`, exclusive, `PeriodicHandler`): a builder that makes a `SubscriptionDefinition` and a handler; lambda dispatch by payload class, superclasses, then interfaces (`Dispatch`, cached). **The processors catch nothing**: failures, retries, shrink and parking are the engine's (I14). Deserialization happens inside the handler call, so a bad payload is a handler failure and parks; never wrap it in an I/O-classified exception (`08*`, `SQLTransientConnectionException`), which the engine retries forever.
- `ViewProjection.rebuild` stops, truncates and calls `eventLog.admin().reset(key, from, connection)` in one transaction, then restarts. `EventReactor.reset(StartFrom)` resolves `head()` as resume point + lag from the admin row.
- Page sources: the engine guards the page `Connection` only; typed resources are this module's job. `UnitOfWorkPageTransactions` installs `PageGuardTransactionHandler` on the application's `Jdbi` once (it wraps the transaction handler: a handle whose page is open refuses commit/rollback) and hands out a `HandleAwareUnitOfWork` proxy refusing commit/rollback. The unit of work's own `beforeCommit` callbacks run at the engine's commit, after the progress update. `SpringPageTransactions` = `PROPAGATION_REQUIRES_NEW` + `DataSourceUtils.getConnection`; its `TransactionStatus` refuses `setRollbackOnly`.
- Commit path: `EventLogCommits.afterCommit(UnitOfWork, EventLog, type)` registers `eventLog.commitCallback()`; `afterSpringCommit(EventLog, type)` binds one `TransactionSynchronization` per transaction and event log (calls the commit callback after commit; wakes at once without an active synchronization).
- Admin SPI `api/EventLogSubscriptionsApi` maps 1:1 onto `EventLogAdmin` with `ProgressKey` keys; reads need `SUBSCRIPTION_READER`, changes `SUBSCRIPTION_WRITER` (or `ESSENTIALS_ADMIN`). Its `EssentialsAdminApiSpec` rows and controller are 8b-C.
- Annotated base classes (phase 10 §3.5, unit 10-A2): abstract `EventLogViewProcessor` / `EventLogReactor`, one `ViewProjection` / `EventReactor` per aggregate type built at first `start()` (hooks `consistency()`, `startFrom()`, `errorSettings()`, `tenant()` are read then, never in the constructor), each aggregate type registered at `start()`. Dispatch is `MessageHandlerDispatch`: shared's `PatternMatchingMethodInvoker` with this module's method pattern (payload, optional `DeliveredEvent`), **not** foundation's `PatternMatchingMessageHandler` - that one accepts only a `Message` second parameter and wraps a handler's exception in `ReflectionException`, which would hide `ParkEventException` from the engine. The handler's own exception must reach the engine unwrapped. No event-type filter is derived from the handler types: `EventTypeFilter` matches exact names, so a handler on a supertype would drop its subtypes. They implement foundation's `Lifecycle` (not Spring's: Spring is allowed in three classes only); `DependencyRulesTest` allows exactly the `MessageHandler` annotation from `foundation.messaging`. ITs: `EventLogViewProcessorIT`, `EventLogReactorIT`, with must-fail arm `ANNOTATED_DISPATCH_SWALLOWS_FAILURE` (set through the package-private `seams(...)` before the first start).
- `EventLogViewProcessor.rebuild()` + protected hook `onRebuild(ProjectionContext)` (phase 10 §9, unit 10-E): one gate transition stops all projections, then ONE transaction of `dependencies.pageTransactions()` runs `onRebuild` and `ViewProjection.resetProgress(connection)` (package-private, the reset half of `ViewProjection.rebuild`) for every aggregate type; commit if any row reset, else roll back (returns `false`); restart if it was started, also after a failure (the rollback left view and progress as they were). Deliberately not `ViewProjection.rebuild` per type: that commits and restarts each type separately, so with a shared view table type B's clear would wipe rows type A had already replayed, and a crash between them leaves A reset and B not. Hook is once per rebuild, unlike the old `onSubscriptionsReset` (per aggregate type). `engine()` page source refused (nothing bound to write through). The rebuild's `begin()` runs on the caller's thread, so `UnitOfWorkPageTransactions` refuses a caller already in a unit of work. Tests: `EventLogViewProcessorTest` (mocked source: hook in the open page, failure rolls back), `EventLogViewProcessorIT` (clear + replay, failing hook rolls back and restarts) with must-fail `REBUILD_CLEARS_OUTSIDE_RESET_TRANSACTION` (arm: never-started view, no progress row, the clear must roll back).
- `EventLogInboxProcessor` (phase 10, unit 10-H; promoted from the trading demo): the inbox-based `EventProcessor`'s counterpart. A private nested `PageForwarder` (an `EventLogViewProcessor`, so `CONTIGUOUS`, from the beginning, aggregate types registered at start) hands every event to `forward`, which skips payloads `PatternMatchingMessageHandler.handlesMessageWithPayload` rejects and enqueues a `ForwardedEvent` (`OrderedMessage` + `IdentifiedByKeyAndOrder`, key = aggregate id, order = event order, metadata + `EVENT_ID_METADATA_KEY`) inside the page transaction; the inbox consumer (a `UnitOfWorkBoundaryOwningMessageConsumer`) binds `CausationContext` and calls the handlers through foundation's `PatternMatchingMessageHandler` (here the old semantics are wanted: `Message`/`OrderedMessage` second parameter, `UnitOfWorkMode`). The forwarder is a separate object because `EventLogViewProcessor` dispatches to `this`'s handlers. The only class allowed `foundation.messaging` beyond `@MessageHandler`, and `FailoverRedeliveryPolicy` from the old processor package (`DependencyRulesTest`). Tests: `EventLogInboxProcessorTest`, `EventLogInboxProcessorIT` (PostgresqlDurableQueues on the page's JDBI factory, test dep `postgresql-queue`; an `Inbox` proxy fails a page once after an enqueue) with must-fail `INBOX_FORWARD_OUTSIDE_PAGE_TRANSACTION`.
- Mutants: `ProcessorMutant` (`PROCESSOR_SWALLOWS_FAILURE`, `DESERIALIZE_OUTSIDE_HANDLER_RETRY`, `HANDLER_COMMITS_EARLY`, `ANNOTATED_DISPATCH_SWALLOWS_FAILURE`, `INBOX_FORWARD_OUTSIDE_PAGE_TRANSACTION`), settable only through package-private seams (`ProcessorSeams`, the sources' package-private constructors). Engine seams (its `WatermarkMutant`s, crash hooks) are reached through `test/.../eventlog/ProcessorTestBridge`, a test-only class in the engine's package (split package on the test class path; never put one in main). Arm (e)'s `PROGRESS_OUTSIDE_PAGE_TRANSACTION` is the engine's `PROGRESS_AFTER_COMMIT`; arm (a)'s `NO_SHRINK` is the engine's.
- ITs extend `AbstractProcessorIT` (static container, fresh schema, Hikari pool closed in `@AfterEach`): `ViewProjectionIT` (§9.2 (a)-(e), JDBI and Spring sources), `EventReactorIT` ((f), (c)), `EventLogCommitsIT`, `EventLogSubscriptionsApiIT`. Every `must_fail_*` expects an `AssertionError` (waits go through `awaitTrue`, which never throws a timeout exception).
- `EventStore` adapter (8b-B): `EventLogEventStore implements ConfigurableEventStore<EventLogAggregateEventStreamConfiguration>` (the configuration adds the engine's `AggregateTypeTables`; `addAggregateEventStreamConfiguration` calls `EventLog.registerAggregateType`). Built with the started `EventLog`, an existing `EventStoreUnitOfWorkFactory` (JDBI or Spring, unchanged), the `JSONEventSerializer` and the `PersistableEventMapper` (optionally tenant serializer, enrichers, a shared `EventStoreEventBus`). Appends: interceptor chain, map + enrich, serialize, `EventLog.append` on `unitOfWork.handle().getConnection()` with the expected order given or the stream's last order read in the unit of work (as the old engine); `StreamAppendConflictException` -> `OptimisticAppendToStreamException` with the old engine's message (`optimisticConcurrencyMessage`, copied word for word; keep it in step); `registerEventsPersisted` (the local bus's commit stages) and `EventLogCommits.afterCommit(unitOfWork, eventLog, type)` (tier-2 wake after commit, JDBI and Spring units of work alike). One tenant per append operation. Loads map `StoredEvent` to `PersistedEvent` as the old row mapper does (`FQCN:` -> `EventType`, otherwise `EventName`). Every `pollEvents`/`unboundedPollForEvents` throws `UnsupportedOperationException`; `findEvent(EventId)` throws as `EventStore`'s default; the observer is the no-op one. Every append is reported to `AppendedEvents.appended` (ES-4; made public for this), so `AppendedEvents.recordDuring` sees adapter appends. Reactor appears only in the poll signatures (`DependencyRulesTest` exempts the class); `reactor-core` is `provided`.
- Engine payload/metadata columns are `json`: the stored text is the serializer's compact output, byte-equal to what the old engine stores in `JSON` columns (jsonb would reformat it). `EventLogEventStoreIT` (§9.4) compares bytes with `PostgresqlEventStore` and the conflict message with the old engine's; mutants `CONFLICT_UNMAPPED`, `PUBLISH_BEFORE_COMMIT` (`ProcessorMutant`, package-private ctor), and a hand-built `JsonMapper` serializer.
- The adapter's constructor registers the old engine's JDBI argument factories and column mappers (`EventOrder`, `GlobalEventOrder`, `EventId`, `CorrelationId`, `EventRevision`) on the factory's `Jdbi`, found through a public `getJdbi()` (as the old persistence strategy does; `PostgresqlAggregateSnapshotRepository` needs them). For another factory, call `EventLogEventStore.registerJdbiTypes(jdbi)`.
- Repository IT copies (§9.5): under `src/test/java` in the ORIGINAL packages (`…eventsourced.aggregates.*`, `…eventstore.postgresql.spring`), fixtures byte-identical. A copy differs from its original only inside `// >>> adapter-copy: replaces N original lines: <reason>` … `// <<< adapter-copy` blocks (store construction via `processor/repository/RepositoryItAdapter`, the `pollEvents` collector replaced by an engine subscription, jsonb-formatted JSON text replaced by the compact text). `RepositoryItCopiesTest` stores each original's SHA-256 and checks the copy line by line outside the blocks: when an original changes it fails; re-sync the copy and update the hash.
