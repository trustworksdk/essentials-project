# postgresql-queue-shard-owned

Shard-owned PostgreSQL durable queue engine. **Experimental — builds and tests with the reactor but is NOT published** (`maven.deploy.skip=true`), because the SPI is still moving.

How it works: `docs/durable-queue-shard-owned.md`. Measurements: `docs/durable-queue-measurements.md`. Historical design proposal + defect log (what `§4.3`-style refs in source comments point at): `docs/archive/durable-queue-design-history.md`.

## The one idea everything follows from

Every message is assigned to a shard at enqueue. Each shard has exactly one owning consumer at a time, held by a lease. A consumer reads only shards it owns. That removes the claim write (`n_tup_upd` is zero), removes `SKIP LOCKED` contention, and makes per-key ordering a consequence of ownership rather than of a query.

## Gotchas

- **§4.3 and §4.4 must be read together.** The range-delete ack is bounded by `min(lowest in-flight, lowest pending hole)`. Without that floor a hole that commits late sits *below* the acked prefix and is deleted undelivered — it reproduced as 896 of 900 messages.
- **An interrupted handler is not a success.** A handler that catches `InterruptedException` and returns is indistinguishable from one that finished; treating them alike loses messages on every graceful shutdown.
- **Lease keys include the lane.** The two lanes have separate owners; sharing a lease row let an unordered message land in a shard leased by the ordered consumer, which never reads that lane.
- **Releasing a lease does not bump the fence** — the next acquirer does. Bumping on release invalidates the releasing owner's own in-flight acknowledgements.
- **The ordered lane sheds by draining, never by releasing.** Dropping the lease mid-key hands the successor a key the outgoing owner is still running — reordering, not the duplicate at-least-once allows. `beginShedding()` stops new dispatch, waits out the in-flight keys, flushes acks under the still-valid fence, then releases. A shed that outlasts `shedGrace` is abandoned and retried: unbalanced beats reordered.
- **`ShardWakeup` is a flag under a monitor, not a semaphore.** Acquire-then-drain loses signals (a 256 ms latency tail); acquire-without-drain leaks permits and spins the owner hot. Both were real.
- **The listener must reconnect AND re-run `LISTEN`.** The subscription is per-connection. Its failure is silent — owners fall back to the backstop poll, so delivery continues and only latency degrades, which means no delivery-based test can detect it. Assert on notification counts.
- **An owner must reconnect, never die.** A `SQLException` escaping the run loop kills the thread while the heartbeat keeps renewing the lease on another connection — the shard is then held forever and served by nobody. The lease bounds the retrying: if the database is really gone, renewal fails and the owner stops.
- **The ordered lane needs the same lease machinery as the unordered one.** It once had no heartbeat, no lease check and no fence on acknowledgement; every test passed because every test finished inside a lease lifetime.
- **Tests that assert exactly-once are wrong.** The contract is at-least-once; a shard moving mid-flight legitimately redelivers. Assert distinct delivery plus bounded overlap.
- **All durable time is `now()`, server-side.** Never send a client timestamp for `visible_at`, `lease_until` or `last_seen` — that is what makes node clock skew irrelevant. `ServerSideTimeTest` guards it.
- **Testcontainers' JDBC URL already has a query string.** Append parameters with `&`. A second `?` is silently ignored by pgjdbc, and a socket timeout that never applies turns a failure test into a no-op.
- **An owner holds one connection for its lifetime.** Pool starvation therefore cannot reach its reads — it starves enqueue, the listener and lease renewal instead. Test the right thing.
- **Every enqueue path runs its batch in an explicit transaction.** Do not rely on PostgreSQL's implicit transaction: pgjdbc syncs large batches in chunks, so a ten-row batch is atomic and a five-thousand-row batch is not. Measured at 2 295 of 5 000 rows surviving a failed enqueue. A caller already in a transaction is left alone — their commit decides.
- **Test batch behaviour at a size callers will actually use.** Small batches are atomic by accident.
- **A failure-injection test must assert the injection worked.** Three in this module initially injected nothing: a malformed JDBC parameter silently ignored, a false premise about pooled connections, and `REVOKE` against a table owner (owners keep all privileges — use a trigger).
- **A live owner does not redeliver what it has already handed out**, even when acknowledgement is failing. Redelivery on at-least-once comes from a NEW owner having no memory, not from the current one retrying.
- **`ShardOwnerMetrics` carries the consumer's `QueueObserver`, not just counters.** Same wiring, two audiences: the counters debug the engine, the observer feeds the consumer's metrics and tracing. Threading one object keeps the owners' already-wide constructors from growing.
- **Retry, dead-letter and delivery-failure events are emitted from the owners, never from `PostgresqlMessageQueue.invoke`.** Only the owner counts attempts. `invoke` once emitted `deliveryFailed` with a hardcoded `attempt = 0`.
- **An observer callback with no call site is worse than a missing one** — a metrics binding over it publishes a counter that is permanently zero, and a dashboard reads that as health. Three of seven were dead when the Micrometer binding was written. Test a binding by driving the engine and reading the meters; a mock observer only proves the binding counts what it is told.
- **`lease_until` NULL vs set is the pre-claim/session distinction.** NULL = Tier 2 pre-claim, consumed at once, never expires, must be picked up by a new owner. Set = a pull session's row lease, must be hidden from the owner until it lapses. A bare fence cannot express both.
- **Session fences are negative**, from their own sequence, so they never collide with owner fences in the shared `lease` column.
- **The range-delete ack must skip row-leased rows** — otherwise a session-held row is deleted undelivered once its hole expires. Same shape as the §4.3 bug.
- **There is no `SessionScope.KEY`, and its absence is the design.** Per-key exclusivity lives in the owner's in-memory in-flight set; a second party cannot enter it without the owner re-reading the DB per dispatch. The constant was removed rather than left throwing, so asking for it is a compile error and the reasoning lives in the enum's javadoc.
- **Row leases cannot retract what the owner already buffered**, so a message can reach both a push consumer and a MESSAGE/BATCH session. Legal on the unordered lane, which is why those scopes are unordered-only.
- **Configuration is separate from `start()`.** `configureUnordered`/`configureOrdered` then `start()`; `startConsuming*` is the two together. A container has nowhere to pass a handler at start time, which is why the split exists.
- **`stop()` must clear owners, wake-ups and the shard map.** Idempotent is not enough — a restart that resurrects owners with superseded fences holds shards it cannot serve, and every write is refused silently by the fencing clause.
- **Handler threads do NOT scale with shard count.** `OrderedShardOwner` once allocated a `keyConcurrency` platform pool per owner — 8 shards x 8 = 64 threads for one consumer. It now shares the runtime's virtual-thread executor, bounded by `keyConcurrency` per shard via `keysInFlight`, which is where per-key serialisation always lived.
- **Multi-queue is where this engine used to break, and only `ShardOwnedMultiQueueCostIT` tests it** — every other IT uses `QUEUE_ID = 1`. Scale it with `-Dcost.queues=25 -Dcost.shards=8 -Dcost.pumpThreads=1`.
- **Share one `ShardRuntime` across every queue in the process.** It owns the pumps, the listener, the handler executor and the heartbeat, and none of those are queue-specific — `queue_id` is a bind parameter, and the wake-up channel is global with the queue id in the payload. Held connections are then `pumpThreads + 1` **in total**: 5 connections and 21 threads at 300 queues, against 1 800 connections when each queue had its own.
- **A `ShardOwnedQueue` built without a runtime borrows the one shared per `DataSource`** (reference counted, last borrower closes it). It used to create a private one, which meant 100 queues stood up 100 runtimes and exhausted a 500-connection pool. A default that degrades as the caller adds queues is a defect, not a caveat.
- **The sweep backs off while a shard is empty** — doubling to `maxSweepInterval` (30s), reset on any delivery. It is the backstop for a *lost* notification, not the delivery path, so a quiet shard costs 0.10 queries/s instead of 4.0: 481/s at 300 queues rather than 18 252/s. `pollBackstop` is the park ceiling, not a floor.
- **The backoff costs cross-process p99**: ~2.7ms to ~5.6ms over three runs each; the local hand-off path is unaffected. Set `maxSweepInterval == sweepInterval` to restore the old behaviour for a latency-critical queue.
- **Idle cost is ~4 queries/s per owned shard** at every scale: a 500 ms sweep plus a 500 ms backstop poll. Gate the per-shard figure, never the total — an absolute ceiling fails just for running bigger.
- **Sequences are per (queue, shard)** — `shard_queue_seq_q<queue>_s<shard>`, created by `registerQueue`. They were once per shard alone, shared by every queue, which manufactured `queues - 1` holes per message and pinned the ack floor for the whole `holeExpiry`.
- **Both lanes park on `ShardWakeup` now.** The ordered lane once slept 200 us and re-queried, polling as fast as the DB could answer: 52 000 queries/s from twenty idle owners, now 160. The wake-up payload is `queueId:lane:shard` — the lane matters, or an unordered enqueue wakes the ordered owner of the same shard into an empty read.
- **Local hand-off masks the cursor read.** Tier 2 stamps the row so `readFromCursor` skips it — a test that enqueues through an owned shard never exercises the cursor, holes, or the ack floor. Call `setLocalHandoffEnabled(false)` when that is what you are measuring.
- **Count held (checked-out) connections, not `pg_stat_activity` rows.** The latter is mostly pool growth.
- **`ShardPump` = one thread, one connection, many shards.** Count from `settings.pumpThreads()`, never from `shardCount`.
- **Each shard has its own `ShardWakeup`, cascading to its pump's.** The pump parks on its own and asks each shard `needsAttention()` — otherwise one shard's notification makes the pump read every shard it serves (measured 14.5 cursor reads per message; 2.0 after).
- **The head sweep must skip this owner's *fresh* pre-claims.** It deliberately does not skip pre-claims at all, so a hand-off lost between commit and dispatch is still recovered — but between the enqueue committing and `handOffLocally` being called, the sweep can deliver, ack and delete the row, and the hand-off then delivers it again. Skip until older than the hand-off grace.
- **Handler concurrency is `ConsumerOptions.parallelConsumers` (default 8), and nothing else.** Measured by `ShardOwnedConcurrencySweepIT`: throughput peaks at 32 but return per permit collapses after 4, and the peak is for one consumer alone on the box, so 8 takes 70% of it for a quarter of the budget. The current implementation has no default — `ConsumeFromQueue` makes it mandatory and callers here pick 1, 3 or 5. Ordered keeps `keyConcurrency` per shard on top.
- **There was a process-wide `handlerConcurrency` ceiling (512) and it was removed.** Nothing measured or derived it, and no test exercised it as a bound. Its documented job was protecting whatever handlers contend for — usually a connection pool — but against a default Hikari pool of 10 it was 51x too high to protect anything, and at `parallelConsumers` 8 it took 64 consumers to engage at all. A ceiling that cannot bind before the resource it guards is exhausted only makes a reader think the question was handled.
- **Take the permit BEFORE the cursor advances past a row, never after.** A row you cannot dispatch must still be there for the next read; advancing past it leaves it to the sweep and registers a hole no transaction owned. Every delivering path — cursor, hand-off, chase, sweep, retry — acquires first and releases on a duplicate.
- **Straggler deletes are NOT bounded by the ack floor.** The floor stops a *range* delete sweeping up undelivered rows; a targeted delete can only remove what this owner handled. Bounding both left 43 of 1 000 messages undeleted behind one slow handler.
- **Pending acknowledgements are a park deadline.** Without that, a late ack waits for the next sweep — up to `maxSweepInterval`. Fixing it also removed a cross-process p99 regression (5.6ms to 2.65ms) that had been written up as the cost of the sweep backoff.
- **Historic note — unordered delivery was inline for a while.** Making it asynchronous produced five defects in one change, because it makes the cursor, hole map, in-flight set and ack floor concurrent — the four things correctness rests on. The cost of inline is that a slow unordered handler occupies its pump and the other shards it serves; raise `pumpThreads`. Pumps stay platform threads either way: a virtual thread blocked in JDBC still holds a connection.
- **A retry lives in two places timed by two clocks** — the table (`visible_at`, database `now()`) and the in-memory schedule (`System.nanoTime()`). Either can fire first, so `deliver` drops any schedule entry for a seq it accepts. Without that, the sweep delivers and deletes the row and the stale entry delivers it again.
- **A delete affecting zero rows is ambiguous** — fence rejected, or rows already gone. Only the first means the shard moved; ask `stillOwns` rather than infer, or an owner drops a lease it still holds and everything in flight is redelivered.
- **`onTakeover` must run before an owner's first `pumpOnce`**, not before the pump's. Pumps start before any shard is leased and rebalancing adds shards later; bumping after delivery finds nothing to bump.
- **Everything the pump and the handler threads share needs `stateLock`** — `cursor`, `pendingHoles`, `inFlight`, `pendingAcks`, `retrySchedule`. An unguarded iteration in `flushAcks` threw CME out of `pumpOnce` and killed the pump, stalling every shard it served. The pump now catches `RuntimeException` per owner for the same reason.
- **`sweepRecoveries` is not automatically a defect signal.** A workload that enqueues faster than its handlers drain makes the sweep legitimately find work the cursor has not reached — 76% of deliveries in one such test, with delivery inline. Compare against a control before concluding the fast path has broken.
- **A relative sweep is measurable where an absolute number is not.** Throughput at saturation varies 861% here, but `AbRunner` interleaves arms in one run, so comparing concurrency levels holds to a few percent IQR. Do not refuse to measure a knob because the absolute figure is noisy.
- **Construct hazards, do not hope for them.** Race-dependent assertions passed by luck twice and hid a message-loss bug once. The ordered-rebalance overlap test needed three attempts before it measured anything: the workload drained before the shards moved, then the handler finished before the successor could acquire, then the drain pushed the shed past the end of the workload. Assert on state captured *at the moment the hazard occurred*, not after.
- **Verify a "broken on purpose" run really compiled the break.** `open(p,'w').write(open(p).read()...)` truncates before it reads; Maven then reuses the previously compiled class and the disconfirming run silently tests the fixed engine. Two of these looked like clean passes.

- **One instance id per subscription, NOT per lane.** `shard_queue_instance` is not keyed by lane, so registering `<id>-u` and `<id>-o` made one process count as two instances; every rebalance then computed `ceil(shards / 2)` and both lanes shed half their shards to nobody. Half of both lanes went permanently unowned ~20s after start — after the first rebalance, so every test that finished sooner passed. `ShardOwnedSpiFairShareIT` waits past it deliberately.
- **`stop()` releases the leases**, after the pumps have flushed. Without it a graceful shutdown left every shard unserved for the rest of the TTL — 30s per rolling restart — while `Subscription`'s javadoc promised the opposite.
- **`leaseTtl` is its own setting**, not `holeExpiry x 3`. The two are bounded by unrelated things; deriving one from the other let a long outbox transaction silently triple failover time.
- **A message's identity is `(lane, shard, seq)`.** Sequences are per (queue, shard), so seq 1 exists in every shard — deduplicating on `seq` alone only works while a batch happens to land on one shard. A test did exactly that and reported 300 duplicates the moment enqueue started spreading properly.
- **`enqueue` round-robins per MESSAGE, not per call.** Hashing once per call puts a 5 000-row batch on one shard and serialises it behind one owner.
- **An observer that throws must not fail the message.** A broken `aroundDelivery` used to get every message retried and dead-lettered. Distinguish by whether the handler itself completed: if it did, log and acknowledge; if an observer threw before calling through, the message really was not handled.
- **A fresh `MessageQueue` is NOT started.** The flag was seeded `true`, so the first `start()` was a no-op. `stop()` keeps consumers registered so `start()` can restart them.
- **`resurrect` takes a FRESH seq.** Re-inserting at the old value puts the row behind the owner's cursor, where only the head sweep finds it — up to `maxSweepInterval`.

- **The sweep backs off per SWEEP, not per pump iteration.** A pump iterates whenever any shard it serves has work, so doubling per iteration drove an idle shard to `maxSweepInterval` within milliseconds — which silently made delayed delivery and lost-notification recovery 30-second operations.
- **A failing statement is not a failing connection.** The pump asks `connection.isValid()` before treating a `SQLException` as connection loss. Conflating them made a permanently-broken statement look like a database blip: reconnect several times a second, forever, while every shard that pump served stopped delivering. Still paced at 200 ms, or a permanent failure spins — measured at 8 405 stack traces in one run.
- **Never subtract a client clock from a server timestamp.** `millisUntilNextVisible` asks the server for the *interval*, not for `min(visible_at)`. `ServerSideTimeTest` catches `System.currentTimeMillis()` in the storage class, and it caught exactly this.
- **`getDouble` + `wasNull`, not `getObject(Double.class)`** — `EXTRACT(EPOCH ...)` returns numeric and pgjdbc refuses that conversion.
- **Engine internals are package-private** (`ShardOwner`, `OrderedShardOwner`, `ShardPump`, `ShardWakeup`, `HandlerDispatch`, `LeasedOwner`). Their wide constructors are internal wiring; the project's 5-parameter ceiling applies to public and protected constructors, which is the line these sit on the far side of. `ConstructionErgonomicsTest` enforces it over this package, **unfrozen** — the module is compliant, so a frozen store would import other modules' debt and hide new violations here.
- **`ShardRuntime.SHARED` is an `IdentityHashMap`.** A `DataSource` is a resource, not a value, and framework proxies define equality as they like — two pools comparing equal would share one runtime drawing connections from the wrong pool. It also warns when a second borrower asks for settings different from the ones in force.
- **Builders, not constructors, for `ShardOwnedQueue` and `PostgresqlMessageQueue`.** The identifying arguments are a `short`, an `int` and a `String` in a row; transposing `queueId` and `shardCount` compiles and silently addresses the wrong queue.
- **No semantic types, deliberately** — `types` carries kotlin-reflect and kotlin-stdlib at compile scope, which this module does not want. The builders close the hazard those types would have guarded.

- **`shard_count` lives in the registry, with the name.** It is a property of the queue, not of the process: a key's shard is `hash(key) mod shardCount`, so a producer believing in 8 and a consumer believing in 4 write to shards nobody leases. `ShardOwnedQueueRegistryIT` reproduces that stranding before asserting the protection. Re-registering a name with a different count is refused.
- **Interning races are resolved by the DB, not by the caller.** `INSERT ... ON CONFLICT (queue_name) DO NOTHING` then **read back** — on conflict the insert wrote nothing because another process won, and its id is the one that counts. Burned sequence values are harmless; an id is a token.
- **`QueueName` is a local record, not a `CharSequenceType`.** Same reason there are no other semantic types here: `types` drags kotlin-reflect and kotlin-stdlib onto a module that depends on `shared` alone.

- **`payloadType` is opaque application metadata**, not an interned FQCN and not an index-density measure — it is in no index and nothing interns it. It reaches the handler via `MessageHandler.handle(key, payload, payloadType)`; it used to be written on every row and returned only on the pull and dead-letter paths, so the push path — how almost everything consumes — never saw the one thing it was for. Both lane reads now `SELECT payload_type`, and `Row`/`OrderedRow` carry it.

- **Interceptor vs observer is a real distinction, not two names for one thing.** Observer is *told*; interceptor is *in the path* and can modify or skip. An observer that throws must not fail its message; an interceptor that throws must. Both are read when a subscription starts, so both must be attached before `consume`.
- **The chain is skipped when empty** — `interceptors.isEmpty()` short-circuits in both `enqueue` and `invoke`, so the common path allocates no operation, chain or lambda. Delivery interception runs once per message; an unconditional chain is exactly the kind of obligation the cost decomposition exists to expose.
- **Interceptors are sorted at registration, not per call.** `@InterceptorOrder` is read reflectively; sorting per delivered message would put reflection on the hot path.
- **Only `EnqueueMessages` and `HandleMessage` are interceptable.** The other SPI members gain no capability from it — an observer already sees them and nothing useful substitutes for their results.
- **Not proceeding on `HandleMessage` acknowledges the message.** A dropped message and a handled one look identical afterwards; say so wherever this is documented.

- **By-id operations do NOT need a claim flag, and the SPI javadoc used to say they did.** `MessageId` is `(lane, shard, seq)` and the primary key is `(queue_id, shard, seq)` — addressing a row is a point lookup. The claim write this design removes is paid per *delivery*; an admin write is paid per *administrator*. Those were priced as if they were the same frequency. Acknowledgement stays session-scoped, because the engine cannot know an arbitrary caller did the work.
- **A by-id write races an in-flight delivery and cannot be fixed.** In-flight lives in the owner's memory. The mismatched ack is already tolerated (`stillOwns` disambiguates it); what is not guaranteed is that the handler did not run. Document it, do not try to close it.
- **The readable views are ergonomics, not storage.** `shard_queue_*_readable` render `bytea` via `shard_queue_readable()`, which falls back to hex on non-UTF-8 — a view that raises on one binary row is worse than one that shows hex. `recreate` must drop the views before the tables.
- **`shardCount` has a measured knee at 4; 8 buys 95% of what 16 does.** `ShardOwnedShardCountSweepIT`, ordered lane, 500 keys, 2ms handler: return per shard falls 1155 -> 151 msg/s from one shard to sixteen, and one shard is also the noisiest arm (74% IQR vs 3% at eight) because everything serialises through one owner. The guidance used to be qualitative with no number behind it — the same shape as the `handlerConcurrency` constant that was removed.
- **Size ORDERED for future peak, unordered for today.** Unordered grows with a rolling restart, so starting low is cheap to correct. Ordered needs the lane empty and every instance restarted together — a drain and a redeploy. At ~0.1 queries/s per idle shard, over-provisioning ordered is nearly free and under-provisioning is not.
- **`shardCount` can grow, and only the ordered lane pins it.** Unordered is round-robin so nothing depends on a message's shard; ordered is `hash(key) mod shardCount`, so growing mid-flight puts one key in two shards. `growShardCount` refuses while the ordered lane is non-empty and refuses to shrink. Instances must be restarted afterwards — the count is baked into a running queue.
