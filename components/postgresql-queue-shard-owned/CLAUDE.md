# postgresql-queue-shard-owned

Shard-owned PostgreSQL durable queue engine. **Published** as of the release that added its admin console page — the `maven.deploy.skip` gate was the "No admin UI" gap, now closed. `MessageQueue` freezes at the release that ships it: additive in minor, breaking only in a major. **Not frozen while unmerged** — the dead-letter work took that window deliberately (`resurrectKey` on the SPI, two counters on `QueueStatistics`, `blockedByKeyOrder` on `DeadLetter`). Widening it still costs: every addition breaks implementors, and `messages(int, int, boolean)` broke one inside this repo, `ShardOwnedMicrometerIT.CountingQueue`, which `resurrectKey` broke again. Land anything else that wants to move before this merges.

How it works: `docs/durable-queue-shard-owned.md`. Measurements: `docs/durable-queue-measurements.md`. Historical design proposal + defect log (what `§4.3`-style refs in source comments point at): `docs/archive/durable-queue-design-history.md`.

## The one idea everything follows from

Every message is assigned to a shard at enqueue. Each shard has exactly one owning consumer at a time, held by a lease. A consumer reads only shards it owns. That removes the claim write (`n_tup_upd` is zero), removes `SKIP LOCKED` contention, and makes per-key ordering a consequence of ownership rather than of a query.

## Gotchas

- **§4.3 and §4.4 must be read together.** The range-delete ack is bounded by `min(lowest in-flight, lowest pending hole)`. Without that floor a hole that commits late sits *below* the acked prefix and is deleted undelivered — it reproduced as 896 of 900 messages.
- **An interrupted handler is not a success.** A handler that catches `InterruptedException` and returns is indistinguishable from one that finished; treating them alike loses messages on every graceful shutdown.
- **Lease keys include the lane.** The two lanes have separate owners; sharing a lease row let an unordered message land in a shard leased by the ordered consumer, which never reads that lane.
- **Releasing a lease does not bump the fence** — the next acquirer does. Bumping on release invalidates the releasing owner's own in-flight acknowledgements.
- **The ordered lane sheds by draining, never by releasing.** Dropping the lease mid-key hands the successor a key the outgoing owner is still running — reordering, not the duplicate at-least-once allows. `beginShedding()` stops new dispatch, waits out the in-flight keys, flushes acks under the still-valid fence, then releases. A shed that outlasts `shedGrace` is abandoned and retried: unbalanced beats reordered. **Exception: a stuck handler** — once the grace runs out with a key in its handler longer than `stuckHandlerTimeout` (`OrderedShardOwner.keysInHandler`, timed from dispatch), `advanceShed` flushes acks and completes the shed with every key still in a handler, that one and any other still running, each of whose messages the next owner delivers again (`shedPastStuckHandler`), each in a handler longer than `stuckHandlerTimeout` charged an attempt by the release first (a younger one released uncharged), bar one the charge dead-letters, which is not delivered again (attempt-counts bullet); the heartbeat's drained-release loop releases the row and WARNs (`ShardOwnedQueue.releasedPastStuckHandler`, which also puts the owner in a set `keptUnitsInHandler` counts while the handler runs). Decided on the pump, not the heartbeat: the ack flush and the stopped dispatch stay on the owner's own thread. Unbounded, a hung handler kept the unit (cluster unbalanced, its other keys unserved) until a restart (design: `docs/durable-queue-shard-owned.md` §8.4, "Unbalanced beats reordered only for so long"). Pin: `ShardOwnedOrderedRebalanceIT.a_shed_held_up_by_a_handler_past_the_stuck_handler_timeout_...` (mutation-checked). The retry runs every heartbeat, so the abandon WARN is per stuck key set (`reportedStuckKeys`), not per attempt — a hung handler otherwise logged it every tick for as long as it hung; repeats go to DEBUG.
- **Release the lease row BEFORE ending the owner — only via `ShardOwnedQueue.releaseLeaseRows`.** Every release site with an owner uses it: both lanes' sheds, dead-pump hand-back, `stop()`. `abandonAcquisition` has no owner (a refused unit is never placed or built) and calls the same fenced statement directly; a failed one goes to `unreleasedAcquisitions`, retried every heartbeat, later runs' included (`retryUnreleasedAcquisitions`): no owner counts that row, so nothing else frees it. Fenced (instance id AND the owner's fence, `ShardOwnedStorage.releaseFencedLeases`): by instance id alone, a tick of an earlier run undoing its acquisition released the row a restarted run (same instance id) had re-taken under a newer fence. Ended first, a failed release left an owner reading as free while its row named this instance: next rebalance dropped it, nobody served the unit. `stop()` ends owners before releasing, but via `endKeepingLeaseRow` (row still counted). `ShardOwnedRebalanceIT.an_unordered_shard_whose_shed_release_fails_...` pins the unordered shed.
- **`ShardWakeup` is a flag under a monitor, not a semaphore.** Acquire-then-drain loses signals (a 256 ms latency tail); acquire-without-drain leaks permits and spins the owner hot. Both were real.
- **The listener must reconnect AND re-run `LISTEN`.** The subscription is per-connection. Its failure is silent — owners fall back to the backstop poll, so delivery continues and only latency degrades, which means no delivery-based test can detect it. Assert on notification counts.
- **An owner must reconnect, never die.** A `SQLException` escaping the run loop kills the thread while the heartbeat keeps renewing the lease on another connection — the shard is then held forever and served by nobody. The lease bounds the retrying: if the database is really gone, renewal fails and the owner stops.
- **A pump dies only on a critical error** (`ShardPump.run` javadoc). Per-owner guards (`pumpOnce`, `onTakeover`, selection checks, `stillLeased`, `flushOnStop`) catch `RuntimeException | Error`, rethrow only critical: one owner's failure stays its own. Rest → `serve` reconnects (`pumpLoopFailures`); while stopping → WARN, exit, uncounted.
- **Dead pump: shards handed back, not kept** (`ShardPump.run`, `ShardOwnedQueue.handBackUnitsOnDeadPumps`). Kept = leased, unserved until restart — worse than crash. Pump ends its owners (`markDead`; `add` after death); heartbeat releases rows before `rebalance`, ordered unit only at `inFlight() == 0` or once a key has been in its handler longer than `stuckHandlerTimeout` (released with it still running, its message - and any other key's in a handler past the bound, not a younger one's - charged an attempt first, one WARN; `ShardOwnedDeadPumpHandBackIT.an_ordered_unit_on_a_dead_pump_is_handed_back_once_..._past_the_stuck_handler_timeout`, mutation-checked). Pending acks not flushed → redelivered.
- **Lease row state is a field on the owner: `LeasedOwner.LeaseRow` `HELD` → `ENDED_ROW_HELD` → `RELEASED`, one way.** The rule lives once, in `LeaseRowState.advanceTo` (a CAS, no `stateLock`: nothing else changes with it); never hand-write a transition, test doubles included. Owners key their side effects on the state it returns, the same on both lanes (`LeaseRow` javadoc). Never derive it at a site. Pump death and `stop()` → `endKeepingLeaseRow()` (`ENDED_ROW_HELD`: serves nothing, row still this instance's); only `releaseLeaseRows` (after the release) or a unit found taken → `RELEASED`. Never end with `onLeaseEnded(RELEASED)` before the release: a heartbeat tick still running stops counting the unit, and its acquire loop can take it again. Count, drop, re-take, fence-check → `holdsLeaseRow()` (`!= RELEASED`): fair-share counts, `removeIf`, both acquire loops, heartbeat lease check, `stop()`. Serve, shed, `shardsHeld()` → `leaseHeld()` (`== HELD`). Derived from lease flag + `onDeadPump` + `owners`, four sites got it wrong: dropped with row unreleased, re-took unit, extra free unit per dead row, ended before release. `ShardRuntime.onDeadPump` now only says which pump (hand-back selection; `stop()` keeps dead-pump owners out of its ack flush). `LeasedOwnerLeaseRowTest` pins transitions; `ShardOwnedFencingIT` the fenced-out ack flush (`RELEASED` from `HELD` and `ENDED_ROW_HELD`, both lanes; a flush refused once the row is `RELEASED` already - a stop flush returning after its kept unit was given up and released - counts no `fencedOutAcks` and logs no lost lease); `ShardOwnedTakeoverAttemptsIT` the refused takeover charge.
- **`markDead` sets `dead` LAST, in `finally`** (`markDead` javadoc): `isDead()` true ⇒ every owner counted, bar any whose counting threw (rare, an OOM; `endOnDeadPump` javadoc). `onDeadPump` asks `awaitsHandBack`, never `isDead()`.
- **No live pump → acquire nothing, `leaseAtStart` included** (`hasLivePump`; `leaseAtStart` javadoc). Else every tick re-takes, re-releases. `start()`'s catch `releaseRuntime()`s (`ShardOwnedLifecycleIT.a_start_that_fails_after_borrowing_...`).
- **Pump death has no `QueueObserver` callback** — `shardsOnDeadPumps` only via `ShardOwnedQueue.metrics()`; `MessageQueue` users see ERROR + hand-back `shardOwnershipChanged`. Not built, deliberately: reopen trigger in design doc §18.3.
- **Dead-pump pins:** `ShardPumpExitTest` (pump), `ShardOwnedDeadPumpHandBackIT` (queue).
- **The ordered lane needs the same lease machinery as the unordered one.** It once had no heartbeat, no lease check and no fence on acknowledgement; every test passed because every test finished inside a lease lifetime.
- **Tests that assert exactly-once are wrong.** The contract is at-least-once; a shard moving mid-flight legitimately redelivers. Assert distinct delivery plus bounded overlap.
- **All durable time is `now()`, server-side.** Never send a client timestamp for `visible_at`, `lease_until` or `last_seen` — that is what makes node clock skew irrelevant. `ServerSideTimeTest` guards it.
- **Testcontainers' JDBC URL already has a query string.** Append parameters with `&`. A second `?` is silently ignored by pgjdbc, and a socket timeout that never applies turns a failure test into a no-op.
- **An owner holds one connection for its lifetime.** Pool starvation therefore cannot reach its reads — it starves enqueue, the listener and lease renewal instead. Test the right thing.
- **`PoolBudget` refuses pool pumps would exhaust, before `ShardRuntime.start()` takes a connection.** Engine knows no pool — asks `ConnectionPoolMetadata` SPI; starter adapts Spring Boot's `DataSourcePoolMetadataProvider`. Never add pool compile dep to engine. Refuses `maximum <= pumpThreads + 1`, warns above half, and otherwise logs the held/pool numbers at INFO on every start — the quiet case used to log nothing, which is how two runtimes holding 6 of a default 10 went unnoticed. Wording lives in `PoolBudget.assess` (pure, unit-tested). Sum across runtimes per `DataSource` only ever **warns** — start/stop bookkeeping slip must never refuse healthy pool. Test pools: size from `PoolBudget.heldConnections`, not guess.
- **Every enqueue path runs its batch in an explicit transaction.** Do not rely on PostgreSQL's implicit transaction: pgjdbc syncs large batches in chunks, so a ten-row batch is atomic and a five-thousand-row batch is not. Measured at 2 295 of 5 000 rows surviving a failed enqueue. A caller already in a transaction is left alone — their commit decides.
- **Test batch behaviour at a size callers will actually use.** Small batches are atomic by accident.
- **A failure-injection test must assert the injection worked.** Three in this module initially injected nothing: a malformed JDBC parameter silently ignored, a false premise about pooled connections, and `REVOKE` against a table owner (owners keep all privileges — use a trigger).
- **A live owner does not redeliver what it has already handed out**, even when acknowledgement is failing. Redelivery on at-least-once comes from a NEW owner having no memory, not from the current one retrying.
- **`ShardOwnerMetrics` carries the consumer's `QueueObserver`, not just counters.** Same wiring, two audiences: the counters debug the engine, the observer feeds the consumer's metrics and tracing. Threading one object keeps the owners' already-wide constructors from growing.
- **Retry, dead-letter and delivery-failure events are emitted from the owners, never from `PostgresqlMessageQueue.invoke`.** Only the owner counts attempts. `invoke` once emitted `deliveryFailed` with a hardcoded `attempt = 0`.
- **Every write an owner makes is fenced, the failure path included — ack, retry, dead-letter, the takeover charge and the exhaustion pass — with one exception.** `poisonOrderedBehindDeadLetter` is unfenced: the table alone decides what it moves (its `EXISTS` on a dead letter below the row on its key), so any owner of the shard would move the same rows the same way (why, and where that argument stops: its javadoc). `scheduleRetryIfOwned` and `moveToDeadLetterIfOwned` carry the same lease check as acknowledgements; a pull session's failure write is fenced too (shard-lease session) or guarded by its row lease (row-lease session), and counts `attempts + 1` on the stored count; the unfenced `moveToDeadLetter` remains for the operator's admin move. Before this, an owner that had lost its shard could dead-letter, or push out `visible_at` on, a row its successor was delivering. A fenced write that changes nothing is ambiguous — lease lost or row gone — so `stillOwns` decides, as on the ack path. On a lost lease the unordered owner forgets the message; the ordered owner keeps the key blocked with nothing scheduled, so a superseded owner never dispatches that key again.
- **A new owner's cursor starts at the shard's head, not at 0.** It used to start at 0, so the first read recorded every sequence value below the shard's first remaining row as a hole — the whole delivered-and-deleted history — and chased them for `holeExpiry`: 5 000 holes after a 5 000-message history, and about 6 statements per delivered message in `ShardOwnedUnorderedReadCostIT` until it was run on a fresh schema per phase. `onTakeover` now sets the cursor from `takeoverCursor` (just below the first readable row, else the sequence's last value). Three things go with it, and each is load-bearing:
  - **The range ack is bounded below** (`seq > takeoverCursor`) and anything at or below is acked by exact seq. Remove it and a range delete after a late commit deletes the late row before it is delivered: `ShardOwnedTakeoverHistoryIT`'s late-commit test loses the message.
  - **The post-ack bookkeeping removes only the deleted range** `(takeoverCursor, contiguousThrough]` plus stragglers, or a late row below the cursor that is being retried loses its attempt count.
  - **The head sweep is pinned to its base interval for `holeExpiry` after a takeover.** That is the window in which the hole chase used to find a late commit, and it is now the sweep's job.
- **No claim joins its locking subquery back to the table.** `claimForSession` was `UPDATE … WHERE (queue_id, shard, seq) IN (SELECT … FOR UPDATE SKIP LOCKED)`. With stale statistics (the table analyzed while drained) the planner nested a loop over the shard, quadratic in its size: 155 s instead of 7.5 ms for a 32-row claim at 20 000 rows per shard. It now binds `queue_id`/`shard` and `seq = ANY(ARRAY(subquery))`, the shape `postgresql-queue` uses for the same reason; `ShardOwnedSessionClaimPlanIT` guards the plan. A scratch table without the real schema showed only 35 ms, so measure against `ShardOwnedSchema`.
- **The unordered cursor read is capped at `min(readBatchSize, max(64, 2 x free permits))`.** Rows past the free permits are not dispatched and the cursor does not move past them, so they are fetched again on the next read. Reading the full `readBatchSize` (500) fetched about 24 rows per delivered message; the cap fetches about 4, with the same number of reads and the same drain time (`ShardOwnedReadAmplificationIT`, 4 000 small messages). Capping at the free permits alone fetched 1 row per message but doubled the reads and the drain time: fast handlers free permits while the dispatch loop is still running, and a bigger read keeps feeding them. The head sweep keeps the full batch, because it has to read past rows already in flight. The saving is database and network I/O - it grows with payload size - not speed.
- **The handler catch is `RuntimeException | Error`, then `rethrowIfCriticalError`.** A non-critical `Error` (an `AssertionError`) used to escape uncounted: the slot was freed, no attempt recorded, and the message looped forever without reaching the dead-letter table. Critical errors still propagate uncounted, matching `postgresql-queue`.
- **`RedeliveryRequested` is the third handler outcome, and it is not a failure.** No `handlerFailures`, no `deliveryFailed`, no exhaustion check; the requested delay replaces the policy's backoff. It is not an attempt either: only `visible_at` moves, so it can never feed the takeover exhaustion check (deliberate divergence from `PostgresqlDurableQueues`, where a manual redelivery counts). On the ordered lane the row carries `REDELIVERY_REQUESTED` (`lease = -1`, a column that lane never used) so a successor still holds its key; a failure write and the admin `retryMessage` clear it. It exists because the adapter's `markForRedeliveryIn` had only "throw" to express itself, which ignored the delay and could dead-letter a healthy message.
- **An observer callback with no call site is worse than a missing one** — a metrics binding over it publishes a counter that is permanently zero, and a dashboard reads that as health. Three of seven were dead when the Micrometer binding was written. Test a binding by driving the engine and reading the meters; a mock observer only proves the binding counts what it is told.
- **`lease_until` NULL vs set is the pre-claim/session distinction.** NULL = Tier 2 pre-claim, consumed at once, never expires, must be picked up by a new owner. Set = a pull session's row lease, must be hidden from the owner until it lapses. A bare fence cannot express both.
- **Session fences are negative**, from their own sequence, so they never collide with owner fences in the shared `lease` column.
- **The range-delete ack must skip row-leased rows** — otherwise a session-held row is deleted undelivered once its hole expires. Same shape as the §4.3 bug.
- **There is no `SessionScope.KEY`, and its absence is the design.** Per-key exclusivity lives in the owner's in-memory in-flight set; a second party cannot enter it without the owner re-reading the DB per dispatch. The constant was removed rather than left throwing, so asking for it is a compile error and the reasoning lives in the enum's javadoc.
- **Row leases cannot retract what the owner already buffered**, so a message can reach both a push consumer and a MESSAGE/BATCH session. Legal on the unordered lane, which is why those scopes are unordered-only.
- **A `ShardOwnedQueue` serves ONE lane, and that is the key to several things that otherwise read as inconsistencies.** `configureUnordered`/`configureOrdered` are mutually exclusive and now *refuse* the second call — they used to flip `activeLane` and leave the first handler populated but never invoked, which looks like "configure both lanes" and silently consumes only the second. A queue with traffic on both lanes needs **two** instances, which is what `PostgresqlMessageQueue.consume` builds, sharing one `consumerInstanceId` so the pair counts as one cluster member. Follows from it: `remaining()` and `ShardOwnedQueue.shardsHeld()` cover the configured lane only; `shardCount` is inert on an ordered-configured instance (that lane routes over the registry's `ordered_units`), though the builder still demands a positive value because `configureX` comes after `build()`; and `Subscription.shardsHeld()` is the pair's sum, with `unorderedShardsHeld()`/`orderedUnitsHeld()` for the per-lane figures; and `stop()` releases its leases in one statement for `activeLane` (`releaseHeldLeases`) — an instance holding both lanes would leave the other lane's leases to expire.
- **Configuration is separate from `start()`.** `configureUnordered`/`configureOrdered` then `start()`; `startConsuming*` is the two together. A container has nowhere to pass a handler at start time, which is why the split exists.
- **`stop()` must END its owners (`endKeepingLeaseRow()`), not just cancel the heartbeat.** Their rows still count as this instance's until `releaseHeldLeases` → `releaseLeaseRows` releases them (why: the `LeaseRow` bullet above). A shared runtime's pumps outlive the queue — in Spring until the runtime bean is destroyed, after every graceful-shutdown phase — and kept dispatching for the stopped queue until the liveness gate fired a lease TTL later, one WARN per owner. Ended owners are dropped by their pump; `stop()` flushes their acks itself first (fence still valid — release does not bump it), then releases. `ShardOwnedLifecycleIT.a_queue_stopped_on_a_shared_runtime_...` guards; every other lifecycle test used a runtime the queue owned, which stops the pumps and hid this. **Everything a run owns lives on its `Run`** — `owners`, `ownedShards`, `acquisitionReported`, the heartbeat — and a run is that object, compared by reference. Never add a queue-wide field a run writes, or a stale tick or a late stop reaches another run's state again. The one exception is `releasedPastStuckHandler` (owners a shed or a dead-pump hand-back released past `stuckHandlerTimeout`, which `keptUnitsInHandler` counts while a handler of theirs runs on): it holds no state of a run - its owners have left their run and released their rows, nothing decides anything from it, and a stuck handler runs on whichever run is current, or none - and it is pruned of owners with no key in a handler on every heartbeat tick, every `endRun` and every add (`pruneReleasedPastStuckHandler`), not only when the gauge is read: nothing in production reads it. Adopt only through `adoptIntoRun`; a tick works on the `Run` its heartbeat was scheduled for, never on `currentRun`; never call the `QueueObserver` under a run's monitor; count the release of EVERY owner that leaves (released, found taken, given up by `stop()`) through the run's `acquisitionReported` (`countRelease`, then `reportReleases`), or `acquired - released` drifts for good. `start()`, `stop()` and `stopAbruptly()` run one at a time under `lifecycleLock` rather than a run's monitor: a heartbeat tick takes that monitor (its lease check, `adoptIntoRun`) and must not wait behind a stop's drain. Except a stop that does not get the lock (after `SHUTDOWN_BUDGET`; at once for `stopAbruptly()` or an interrupted thread): it takes a `STARTING` run out under the run's monitor (`STOP_OWED_*`), returns, and leaves its work to that start (`endRunOfStart`); a later `start()` waits for that start, with one WARN (`lockForStart`). Whether a start is still running for a run is `Run.phase` (`STARTING` alone), moved under the run's monitor only along `Phase`'s diagram, a rule enforced once in `Run.advanceTo` (`Phase.canAdvanceTo`; `RunPhaseTest` pins it) — never inferred from the heartbeat, `currentRun` or the lock: a start escaping with a critical error leaves its run installed with no heartbeat and no start (`START_ABORTED`), and a stop that handed its work to it handed it to nobody. Protocol and why: `Run`'s, `adoptIntoRun`'s and `endOnStop`'s javadoc; pins: `ShardOwnedLifecycleIT`, `ShardOwnedDeadPumpHandBackIT`.
- **Every ordered insert must assign its xid BEFORE `nextval`** (`assignTransactionIdBeforeAllocating`: `SELECT pg_current_xact_id()`). xid is lazy; `nextval` assigns one only on its 1-in-32 WAL-logging call. Without it a writer holds a seq invisible to `backend_xid`, the watermark steps over it, and a later `key_order` of that key is delivered first — once in ~20 min in the two-instance trading demo. `ShardOwnedWatermarkXidWindowIT` reproduces it (BEFORE INSERT trigger = window between nextval and heap write); it must warm the sequence first, or the fresh sequence's logging `nextval` assigns the xid and hides the bug. A new ordered insert path needs the call too
- **`stop()` drains before it releases, and drains BEFORE `releaseRuntime()`.** `beginDraining()` (both owners; irreversible, unlike the ordered shed which un-sheds on timeout) stops dispatch; pumps keep acking what finishes; stop waits `shedGrace`. Order matters: a runtime the queue owns stops its pumps in `releaseRuntime()`, and nothing acks after that. Ordered units still busy after the grace are **kept** (lease not released, instance NOT deregistered) so a successor cannot start the key mid-handler — another instance takes one only once `leaseTtl` lapses. Once the kept handler returns the unit is **handed back** (`ShardOwnedQueue.handBackKeptUnit`): acks flushed under the kept fence, row released, so the next acquirer sees `previousOwnerReleased` — no takeover charge, no redelivery of the handled message. Run from the owner as its last key leaves the handler (`OrderedShardOwner.whenNoKeyInHandler`, registered by the stop's budget thread once it has flushed; on its own daemon thread: the queue may never run again — an unsubscribed pair), retried by every heartbeat tick, by `leaseAtStart`, by a later `endRun`, and by `PostgresqlMessageQueue.reserveSubscriptionIndex` for the lanes of an ended subscription (`reviewAndHandBackKeptUnits`: they never run again). A failed hand-back is not a hand-back: the unit stays not handed back while its row names the instance (`KeptUnit.notHandedBack`). **A kept unit's lifecycle is ONE field, `KeptUnit.Phase`** (`STOP_FLUSHING` → `AWAITING_HAND_BACK` → `GIVEN_UP` → `TAKEOVER_ASKED`, any of the last three → `HANDING_BACK` → `HANDED_BACK`, `FORCE_RELEASED` or back where it was claimed from), moved only by `KeptUnit.moveFrom`/`claimHandBack` along `Phase.canAdvanceTo` (`KeptUnitPhaseTest` pins it); in-handler and row-held stay live reads of the owner. Three flags (`handingBack`, `givenUp`, `takeoverAsked`) used to stand for it and had no state for the window between `endRun` publishing the unit and its budget thread's flush: a heartbeat, a restart's `leaseAtStart` or a `consume()` then handed the unit back beside that flush, which, refused, counted a lease lost (`fencedOutAcks`, WARN). `STOP_FLUSHING` is that window: no hand-back claims it and no review gives it up within `stuckHandlerTimeout`, and the budget thread leaves it in the `finally` around its flush, so the two never flush one owner at once (`ShardOwnedLifecycleIT.a_unit_a_stop_kept_is_not_handed_back_while_the_stop_is_still_flushing_it`, mutation-checked; it holds the budget thread by its thread name in a test `DataSource`). Bounded: that flush can run long though each of its database waits is bounded (below) — answers too slow to reach that bound, a long wait for a pool connection — so a unit still at `STOP_FLUSHING` once kept longer than `ShardOwnedQueue.stopFlushGiveUpAfter` (`KeptUnit.keptFor`, from construction) is given up whatever its handler does (`STOP_FLUSHING` → `GIVEN_UP`, one WARN). That floor is `stuckHandlerTimeout`, or `SHUTDOWN_BUDGET` + `stopNetworkWaitBound()` when longer: `stuckHandlerTimeout` bounds a handler, not a flush, and alone a short one gave up a flush that was only slow, whose delete was then refused beside the hand-back (`ShardOwnedLifecycleIT.a_unit_a_stop_kept_whose_flush_outlasts_a_short_stuck_handler_timeout_...`, mutation-checked). A unit at `STOP_FLUSHING` kept longer than `stopNetworkWaitBound()` gets its own rate-limited held-up WARN (flush not returned, release on request answers `BUSY`), key in a handler or not; the `leaseTtl` held-up WARN with the release-kept advice is for `AWAITING_HAND_BACK` units only (`..._held_up_for_its_stops_flush_...`, two tests, mutation-checked); `releaseKeptOrderedUnit` reviews first, so a stopped queue releases such a unit instead of answering `BUSY` for as long as the flush hangs (`ShardOwnedLifecycleIT.a_unit_a_stop_kept_whose_flush_never_returns_...`, four tests, mutation-checked). Heartbeat tick, `leaseAtStart` and `PostgresqlMessageQueue.reserveSubscriptionIndex` all go through `ShardOwnedQueue.reviewAndHandBackKeptUnits`, the one place the order lives (`handBackKeptUnits` is private to it): `reviewStuckKeptUnits` BEFORE `handBackKeptUnits`, a review that throws logged and the hand-backs run all the same. One given up with no key in a handler is handed back in that pass (clean: no charge, no redelivery), not taken over by the acquire after it (`..._is_handed_back_past_...`, `..._is_handed_back_by_a_start_past_...` and `ShardOwnedUnsubscribeIT.an_unsubscribed_unit_whose_stop_flush_never_returns_is_handed_back_by_the_next_consume_...`, each mutation-checked against the old order). The give-up is the backstop: the budget thread's every wait on the database is bounded too (`withinShutdownBudget` runs its work in `NetworkWaitBound.during`, so each connection `ShardOwnedStorage` hands it gets `setNetworkTimeout` = max(`leaseTtl`, `SHUTDOWN_BUDGET`) unless the connection's own network timeout is shorter — only ever tightened, so a deployer's `socketTimeout` stands — set back on close; `NetworkWaitBoundTest` pins set, restore and the min rule), so a flush on a connection that does not answer throws, the `finally` lets the units out and `handBackStillRunning()` drops (`ShardOwnedLifecycleIT.a_stop_whose_hand_back_the_database_never_answers_...`, mutation-checked). - **`stop()` must drop its run's owners, wake-ups and shard map** — the `Run` it took out is discarded and `releaseRuntime` forgets its wake-ups, so a restart builds a fresh `Run`. Idempotent is not enough — a restart that resurrects owners with superseded fences holds shards it cannot serve, and every write is refused silently by the fencing clause.
- **Handler threads do NOT scale with shard count.** `OrderedShardOwner` once allocated a `keyConcurrency` platform pool per owner — 8 shards x 8 = 64 threads for one consumer. It now shares the runtime's virtual-thread executor, bounded by `keyConcurrency` per shard via `keysInFlight`, which is where per-key serialisation always lived.
- **Multi-queue is where this engine used to break, and few ITs test it** — `ShardOwnedMultiQueueCostIT` (scale it with `-Dcost.queues=25 -Dcost.shards=8 -Dcost.pumpThreads=1`), and `ShardOwnedDeadPumpHandBackIT`'s two tests of a dead pump serving two queues (or both lanes of one), each counting and handing back only its own owners; every other IT uses `QUEUE_ID = 1`.
- **Share one `ShardRuntime` across every queue in the process.** It owns the pumps, the listener, the handler executor and the heartbeat, and none of those are queue-specific — `queue_id` is a bind parameter, and the wake-up channel is global with the queue id in the payload. Held connections are then `pumpThreads + 1` **in total**: 5 connections and 21 threads at 300 queues, against 1 800 connections when each queue had its own.
- **A `ShardOwnedQueue` built without a runtime borrows the one shared per `DataSource`** (reference counted, last borrower closes it). It used to create a private one, which meant 100 queues stood up 100 runtimes and exhausted a 500-connection pool. A default that degrades as the caller adds queues is a defect, not a caveat.
- **The sweep backs off while a shard is empty** — doubling to `maxSweepInterval` (30s), reset on any delivery. It is the backstop for a *lost* notification, not the delivery path, so a quiet shard costs 0.10 queries/s instead of 4.0: 481/s at 300 queues rather than 18 252/s. `pollBackstop` is the park ceiling, not a floor.
- **The backoff costs cross-process p99**: ~2.7ms to ~5.6ms over three runs each; the local hand-off path is unaffected. Set `maxSweepInterval == sweepInterval` to restore the old behaviour for a latency-critical queue.
- **Unordered lane: idle cost is about 0.2 queries/s per owned shard once the sweep has backed off** (measured, `ShardOwnedMultiQueueCostIT`: 5 idle queues, 8 queries/s in total). Before the backoff it is ~4 queries/s per shard: a 500 ms sweep plus a 500 ms backstop poll, because `ShardOwner` reads per shard. The ordered lane is different — `OrderedShardOwner` is a `BatchReadableOwner`, so its idle cost is per QUEUE (see below). Gate the per-shard figure, never the total — an absolute ceiling fails just for running bigger.
- **The schema is exposed as plain statements, and the engine still depends only on `shared`.** `schemaStatements()` is exactly what `initialize` executes; `queueSequenceStatements(queueId, shardCount)` is what `registerQueue` executes, through a `QueueDdlExecutor` (default: under the bootstrap lock). The schema-harness contributor built on these lives in `postgresql-queue-shard-owned-adapter` (`ShardOwnedSchemaContributor`). Add DDL to those statement lists, never as a direct `execute` beside them, or the harness stops seeing it.
- **Sequences are per (queue, shard)** — `shard_queue_seq_q<queue>_s<shard>`, created by `registerQueue`. They were once per shard alone, shared by every queue, which manufactured `queues - 1` holes per message and pinned the ack floor for the whole `holeExpiry`.
- **Both lanes park on `ShardWakeup` now.** The ordered lane once slept 200 us and re-queried, polling as fast as the DB could answer: 52 000 queries/s from twenty idle owners, now 160. The wake-up payload is `queueId:lane:shard` — the lane matters, or an unordered enqueue wakes the ordered owner of the same shard into an empty read.
- **Local hand-off masks the cursor read.** Tier 2 stamps the row so `readFromCursor` skips it — a test that enqueues through an owned shard never exercises the cursor, holes, or the ack floor. Call `setLocalHandoffEnabled(false)` when that is what you are measuring.
- **Count held (checked-out) connections, not `pg_stat_activity` rows.** The latter is mostly pool growth.
- **`ShardPump` = one thread, one connection, many shards.** Count from `settings.pumpThreads()`, never from `shardCount`.
- **Each shard has its own `ShardWakeup`, cascading to its pump's.** The pump parks on its own and asks each shard `needsAttention()` — otherwise one shard's notification makes the pump read every shard it serves (measured 14.5 cursor reads per message; 2.0 after).
- **The head sweep must skip this owner's *fresh* pre-claims.** It deliberately does not skip pre-claims at all, so a hand-off lost between commit and dispatch is still recovered — but between the enqueue committing and `handOffLocally` being called, the sweep can deliver, ack and delete the row, and the hand-off then delivers it again. Skip until older than the hand-off grace.
- **Handler concurrency is `ConsumerOptions.parallelConsumers` (default 8), and nothing else.** Measured by `ShardOwnedConcurrencySweepIT`: throughput peaks at 32 but return per permit collapses after 4, and the peak is for one consumer alone on the box, so 8 takes 70% of it for a quarter of the budget. The current implementation has no default — `ConsumeFromQueue` makes it mandatory and callers here pick 1, 3 or 5. Ordered keeps `keyConcurrency` per shard on top.
- **There was a process-wide `handlerConcurrency` ceiling (512) and it was removed.** Nothing measured or derived it, and no test exercised it as a bound. Its documented job was protecting whatever handlers contend for — usually a connection pool — but against a default Hikari pool of 10 it was 51x too high to protect anything, and at `parallelConsumers` 8 it took 64 consumers to engage at all. A ceiling that cannot bind before the resource it guards is exhausted only makes a reader think the question was handled.
- **Take the permit BEFORE the cursor advances past a row, never after.** A row you cannot dispatch must still be there for the next read; advancing past it leaves it to the sweep and registers a hole no transaction owned. Every delivering path — cursor, hand-off, chase, sweep, retry — acquires first and releases on a duplicate.
- **Straggler deletes are NOT bounded by the ack floor.** The floor stops a *range* delete sweeping up undelivered rows; a targeted delete can only remove what this owner handled. Bounding both left 43 of 1 000 messages undeleted behind one slow handler.
- **Pending acknowledgements are a park deadline.** Without that, a late ack waits for the next sweep — up to `maxSweepInterval`. Fixing it also removed a cross-process p99 regression (5.6ms to 2.65ms) that had been written up as the cost of the sweep backoff.
- **Historic note — unordered delivery was inline for a while.** Making it asynchronous produced five defects in one change, because it makes the cursor, hole map, in-flight set and ack floor concurrent — the four things correctness rests on. The cost of inline is that a slow unordered handler occupies its pump and the other shards it serves; raise `pumpThreads`. Pumps stay platform threads either way: a virtual thread blocked in JDBC still holds a connection.
- **A retry lives in two places timed by two clocks** — the table (`visible_at`, database `now()`) and the in-memory schedule (`System.nanoTime()`). Either can fire first, so `deliver` drops any schedule entry for a seq it accepts. Without that, the sweep delivers and deletes the row and the stale entry delivers it again.
- **The unordered range ack may only delete what this owner is done with, and "outstanding" includes a message waiting for its retry.** `flushAcks` bounds `DELETE ... WHERE seq <= n` by in-flight and hole floors; a backed-off message is neither, so it was swept with the traffic after it — redelivered from memory, row gone (lost on a crash), and its final dead-letter move found nothing and succeeded silently. Every unordered poison message with traffic around it vanished; the trading demo's fault harness found it, `ShardOwnedRetryAndDeadLetterIT` pins it. Three guards now: the floor includes `retrySchedule`; the range delete also requires `visible_at <= now()`, which covers a delayed or previous-owner backoff row whose hole has expired (`ShardOwnedDelayedDeliveryIT`); and a message that ever failed is acked by exact seq, since the in-memory retry clock can fire before the database's `visible_at`, and the range would then skip it into a redelivery. `moveToDeadLetter` returns false when there was no row, and the owners WARN instead of reporting a dead letter.
- **A delete affecting zero rows is ambiguous** — fence rejected, or rows already gone. Only the first means the shard moved; ask `stillOwns` rather than infer, or an owner drops a lease it still holds and everything in flight is redelivered.
- **`onTakeover` must run before an owner's first `pumpOnce`**, not before the pump's. Pumps start before any shard is leased and rebalancing adds shards later; bumping after delivery finds nothing to bump.
- **Attempt counts survive a change of owner, and a delivery whose outcome was never recorded is charged: by an unclean takeover, or by the owner releasing an ordered unit past a handler that has not returned (once per owner; a release that fails after its charge and is then taken over unclean charges that delivery again).** Four parts, each guarded by `ShardOwnedTakeoverAttemptsIT` (each was mutation-checked), and a fifth below them:
  - The first failure under an owner continues from the row's stored `attempts` (`storedAttempts`, failure path only — the delivery read still leaves it out). Starting from 1 gave every message a fresh budget per takeover and made the takeover bump write-only.
  - `acquireLeaseGrant` reports whether the previous owner released the unit (`owner IS NULL`). A clean handover charges nothing, so a deploy or rebalance costs queued messages no attempts. The previous owner is read by a CTE joined in the UPDATE's `FROM`: referenced only from `RETURNING`, the CTE ran after the UPDATE and read nothing, so every takeover looked unclean.
  - An unclean takeover charges only what the previous owner could have had in flight: the lowest `capacity + ackBatchSize` never-charged visible rows, due retries, and rows pre-claimed under `fence - 1` (unordered); the first `ackBatchSize + 1` visible rows per key plus due retries (ordered), skipping a key held by an earlier retry in backoff, a pending requested redelivery or a dead letter, and any row a live pull session holds. The same exclusions apply to the exhaustion dead-letter. The charge is fenced (owner + fence, like the ack): an owner whose lease moved on before its pump took it over (taken, or released by `stop()`) used to charge the successor's in-flight rows a second time; a refused charge (0 rows, `stillOwns` false) is a lost lease, `RELEASED`, nothing dispatched. Charged once per ownership — `onTakeover` also runs on every pump reconnect. `takeoverCharged` is set as soon as the bump commits; the exhaustion pass has its own `exhaustionPending` flag, so a failed pass retries (200 ms later on a healthy connection, the next connection otherwise) without a second charge, and a plain reconnect never runs it — it would park the owner's own in-flight last attempt (`ShardOwnedTakeoverExhaustionRetryIT`).
  - Rows the charge brings to `maxAttempts` are dead-lettered at takeover with `EXHAUSTED_BY_TAKEOVERS`. The pass also parks rows a pull session failed to the limit, and live rows have no `last_error`, so the text must not claim no failure was recorded. A message that takes the process down never fails, so nothing else would park it; the bump alone never did.
  - **A release past a stuck handler charges too, on the releasing side.** The shed and the dead-pump hand-back past `stuckHandlerTimeout`, and `releaseKeptOrderedUnit` with a key in a handler, release the row, so the next owner sees `previousOwnerReleased` and charges nothing; a hung handler records nothing either. Released uncharged, a message whose handler hangs on every delivery was handed on with its count unchanged and never dead-lettered. So before each of those releases `OrderedShardOwner.chargeKeysInHandlerBeforeRelease` charges `attempts + 1` on rows in a handler (`keysInFlight` carries each key's seq and dispatch nanos; `ShardOwnedStorage.chargeRowsInHandler`, fenced) and dead-letters those at `maxAttempts` with `EXHAUSTED_IN_A_RELEASED_HANDLER` (no exhaustion pass runs after a clean grant). Which rows: `ReleaseChargeScope` - shed and dead-pump hand-back charge only rows in a handler longer than `stuckHandlerTimeout` (`PAST_STUCK_HANDLER_TIMEOUT`, as the unordered lane; both fire once ONE key passes the bound, so a co-resident key that entered its handler moments before was charged, dead-lettered at `maxAttempts - 1` with a healthy handler and its key blocked - the user's call, F-647); release on request charges every key (`EVERY_KEY_IN_HANDLER`). Once per message per owner (`chargedOnRelease` recorded on commit, `deadLetterMoveMade`, moves retried until done), so a retried release charges only what has gone past the bound since. A `QueueObserver` told of such a dead letter that throws is not a failed charge: `OrderedShardOwner` throws it only once every move is made (`owesReleaseCharge(scope)` false), and `ShardOwnedQueue.chargeKeysInHandlerBeforeRelease` WARNs (`orderedChargeFailedWithNothingOwed`) and returns the answer, so the shed, the dead-pump hand-back and the release on request all release the unit (pins: `ShardOwnedDeadPumpHandBackIT.a_dead_pumps_unit_whose_charge_dead_lettered_its_message_is_handed_back_even_when_the_observer_told_of_it_throws`, `ShardOwnedUnsubscribeIT.a_kept_unit_released_on_request_whose_charge_dead_lettered_its_message_is_released_even_when_the_observer_told_of_it_throws`; mutation-checked). A failed charge leaves only that owner's unit held, retried next heartbeat: the shed loop and the dead-pump hand-back release the others in the same tick. The ordered tick's fair-share comparison leaves shed-complete units out (`shedOrAcquireOrderedShards`), as it does `ENDED_ROW_HELD` ones, while the acquire step still counts their rows towards its limit: counted, a unit whose charge kept failing held the run above its share, so each tick only re-asked that shed and returned, and never reached the acquire step - a given-up kept unit was taken over by nobody while the charge failed. As on the unordered lane, the charged counts also go into `attemptsBySeq`, so a failure the handler reports after a refused release counts on from the charge rather than writing an older count over it, and a handler whose message the charge dead-lettered records nothing when it then fails (`seqsDeadLetteredOnRelease`; it used to WARN that the row was no longer in the table) - pins: `ShardOwnedUnsubscribeIT.a_failure_reported_after_a_refused_release_on_request_*` (two tests, each mutation-checked). Counted in `takeoverAttemptBumps` on the releasing owner's metrics; the release WARNs name the charge. Pins: the shed and dead-pump stuck-handler ITs and `ShardOwnedUnsubscribeIT.a_kept_unit_released_on_request_while_its_key_is_in_the_handler_...` assert exactly one bump (the last also fails if a release on request spares young keys); `ShardOwnedOrderedRebalanceIT`/`ShardOwnedDeadPumpHandBackIT` `..._does_not_charge_a_key_that_entered_its_handler_just_before` the young key uncharged, not dead-lettered (`maxAttempts` 1; mutation-checked against charging every key); `ShardOwnedDeadPumpHandBackIT.a_dead_pumps_unit_whose_release_is_refused_charges_on_a_retry_...` the once-per-message charge across refused releases (mutation-checked against a one-shot charge and against no memo); `ShardOwnedUnsubscribeIT.a_message_whose_handler_hangs_on_every_delivery_is_dead_lettered_...` the dead letter after two releases; `ShardOwnedUnsubscribeIT.a_kept_unit_whose_release_on_request_the_database_refuses_...` one bump and stored attempts 1 after a refused release and its retry (all mutation-checked); `ShardOwnedDeadPumpHandBackIT.a_dead_pumps_unit_whose_charge_before_its_release_fails_...` a failed charge holding only its own unit in the dead-pump hand-back; `ShardOwnedOrderedRebalanceIT.a_shed_unit_whose_charge_before_its_release_fails_is_held_while_a_unit_shed_after_it_is_released` the same in the shed loop (mutation-checked against rethrowing the failure), and `..._keeps_failing_does_not_keep_a_given_up_kept_unit_from_being_taken_over` the acquire step running while it fails (mutation-checked against rethrowing and against counting shed-complete units in the fair-share comparison).
  - **The unordered lane charges too, but only past `stuckHandlerTimeout`.** It waits for no handler: the shed and the dead-pump hand-back release a shard at once, `stop()` once `shedGrace` runs out, so the same uncharged hand-on happened on every rebalance and restart, each leaving a hung handler holding a `HandlerDispatch` permit. `ShardOwner.chargeInHandlerBeforeRelease` charges the messages in a handler longer than the bound (`inFlight` is `seq -> dispatch nanos`; same `ShardOwnedStorage.chargeRowsInHandler`) and dead-letters at `maxAttempts` with `EXHAUSTED_IN_A_RELEASED_HANDLER`; a message in a handler for less is released uncharged (slow, not hung - the user's call, F-642). Once per message per owner (`chargedOnRelease`, recorded on commit; dead-letter moves until made), so a retried release charges only what has gone past the bound since; `owesReleaseCharge()` leaves out what is charged, and spares a connection when there is nothing to write. The charged counts also go into `attemptsBySeq`: an owner serving on after a refused release otherwise counted a later failure of that handler from its own older count, and `scheduleRetryIfOwned` wrote it over the charge. Call sites in `ShardOwnedQueue`: the unordered shed loop and the dead-pump hand-back (`chargeInHandlerBeforeReleaseOrWarn`: a failure with a charge still owed holds only that shard, WARN, retried next tick) and `handBackWithinBudget` (`chargeBeforeReleaseOnStop`: one connection for every owing owner, as `releaseHeldLeases` has one; a failure with a charge still owed leaves that shard unreleased - no tick follows a stop - so the next owner's unclean takeover charges it). A failure that leaves nothing owed - the `QueueObserver` told of a dead letter threw, which `ShardOwner` throws only once every move is made - releases the shard all the same (`chargeFailedWithNothingOwed`, WARN). A handler of a message dead-lettered this way that later fails, its owner still serving after a failed release, records nothing (`deadLetteredOnRelease`). WARN per charging release: `releasedPastStuckUnorderedHandlers`. Pins: `ShardOwnedUnorderedReleaseChargeIT` (stops to the dead letter, the shed's exact count, the uncharged message under the bound, the shed loop's and the stop's failed charge, the observer that throws, the once-per-message charge across refused releases, and the two handler failures after a refused release) and `ShardOwnedDeadPumpHandBackIT.an_unordered_shard_on_a_dead_pump_is_handed_back_with_...` / `a_dead_pumps_unordered_shard_whose_charge_before_its_release_fails_...`, all mutation-checked.
- **Everything the pump and the handler threads share needs `stateLock`** — `cursor`, `pendingHoles`, `inFlight`, `pendingAcks`, `retrySchedule`. An unguarded iteration in `flushAcks` threw CME out of `pumpOnce` and killed the pump, stalling every shard it served. The pump now catches `RuntimeException | Error` (non-critical) per owner for the same reason.
- **`sweepRecoveries` is not automatically a defect signal.** A workload that enqueues faster than its handlers drain makes the sweep legitimately find work the cursor has not reached — 76% of deliveries in one such test, with delivery inline. Compare against a control before concluding the fast path has broken.
- **A relative sweep is measurable where an absolute number is not.** Throughput at saturation varies 861% here, but `AbRunner` interleaves arms in one run, so comparing concurrency levels holds to a few percent IQR. Do not refuse to measure a knob because the absolute figure is noisy.
- **A database restart is a fourth failure, and the test has to prove two things it would otherwise assume** (`ShardOwnedDatabaseRestartIT`). First, that the server really went: `pg_postmaster_start_time()` before and after, because a restart that silently did not take leaves every other assertion passing. Second, that the messages committed into the outage were still pending when it happened — delivery is held behind a latch across it, since the enqueuing JVM owns the shard and the local hand-off otherwise delivers them in under a millisecond. Also: **`docker restart` re-allocates a dynamically published port** (measured, 37576 → 37577), so the container's host port is pinned via `withCreateContainerCmdModifier`; without it the engine cannot reconnect for a reason that is purely Testcontainers.
- **An instance that has not confirmed liveness within `leaseTtl` stops dispatching** (`deliveryPermitted` → `LeasedOwner.deliveryPermitted()`, checked in `ShardPump` **before** `needsAttention()` so the wake-up flag is not consumed and lost). Its units are already takeable by then — liveness is the instance row, and everyone's fair share treats a row older than the lease as dead — so anything it delivers from there is work a successor is doing too. Not a fence and not a replacement for one; the fence is what makes the window *safe*, this is what stops it being *wasteful*. Units are kept, because releasing them needs the database it cannot reach. `ShardOwnerMetrics.deliveryPauses` counts it; `ShardOwnedStaleLivenessIT` asserts it.
- **Staleness is evaluated on the heartbeat, not only on the dispatch path.** The first version checked it only where owners dispatch, and the test never saw a pause: a partitioned instance has no work, so nothing asked. An instance with a quiet queue is exactly the one an operator is trying to find.
- **The gate reaches owners through a setter, not the constructor.** `ShardOwner` and `OrderedShardOwner` are already at their argument ceiling, and this is one supplier the queue owns.
- **The WAL advantage is a constant, not a percentage — quote it with a payload size.** Measured 200 B → 64 KB (`ShardOwnedVsBaselineCostIT.compare_per_message_cost_across_payload_sizes`, benchmark-gated): the saving is a fixed ~1 200–1 350 bytes per message, because a narrower row and the absent claim write are per-message costs while the payload is one both engines pay. So −71% at 200 B, −39% at 1 800, −11% at 8 000, **−1.6% at 64 000**. Crossing the TOAST threshold (between 1 800 and 8 000) costs ~200 bytes of the saving: once the payload leaves the row both engines' rows are narrow, and what is left is the claim write.
- **A payload-size sweep needs an INCOMPRESSIBLE filler.** PostgreSQL compresses before moving a value out of line, so the old `"x".repeat(n)` filler collapses at 64 KB and never reaches the TOAST table — the sweep would report large payloads as nearly free. Both arms use random bytes now (Base64 for the baseline's JSON). Same trap as the disk-fill test.
- **A size sweep cannot hold the message count fixed** — 20 000 × 64 KB is 1.3 GB per repetition and fills the lab's volume mid-run. Hold the *bytes* per run constant (16 MB) and let the count fall out; per-message cost is a ratio that does not care about the denominator.
- **A full disk is two different failures and the queue meets the milder one last** (`ShardOwnedDiskPressureIT`). A relation that cannot extend is not a queue that cannot write — measured: filler rows of 1 MB down to 512 B all refused while all 20 queue enqueues were accepted, landing in already-allocated pages. Data-file exhaustion is an ordinary ERROR; **WAL exhaustion is a PANIC** that takes the cluster down and brings it back through crash recovery (seen at 192 MB with no ballast). And a full cluster cannot TRUNCATE its way out, so the test frees space by deleting a ballast file from outside the database — which is also the operational advice.
- **`socketTimeout` decides when a partitioned node finds out; nothing else does.** Measured over a real network partition (`ShardOwnedCrossHostPartitionIT`, benchmark-gated): with `socketTimeout=3` the cut-off node notices in 3.3s, without one it had not noticed within 90s — and the pool's `connectionTimeout` never fires, because the heartbeat thread is blocked inside a read on a connection Hikari still considers healthy and never asks for another. Takeover is 3.2s in both arms: it is decided by the membership row going stale, not by anyone noticing. Recommend `socketTimeout` wherever the DataSource is documented.
- **That measurement needs the node in a container and the database addressed by IP.** `docker network disconnect` is the partition — packets stop routing, every socket stays open, nobody is told. By network *alias* the disconnect also takes the DNS name, so the next connection fails fast on an unknown host, which is nothing like a partition; `databaseIpOn` reads the container's address instead. The node JVM runs `ShardOwnedNodeMain` from `eclipse-temurin:25-jre` with `/workspace` and `~/.m2` bind-mounted at identical paths, so `System.getProperty("java.class.path")` works verbatim inside it.
- **A partition is not a connection reset, and the engine meets them on different paths.** `pg_terminate_backend` (`ShardOwnedConnectionLossIT`) sends an RST: the owner learns at once, reconnects, keeps its leases. A partition sends nothing — the owner keeps running, keeps delivering from memory, and learns only at its socket timeout, which is the window fencing exists for. `SIGSTOP` is not a substitute either: a frozen node acts on nothing while stopped. `ShardOwnedNetworkPartitionIT` uses `PartitionableProxy`, a forwarder that stops *reading* so TCP backpressure stalls both directions without closing anything — chosen over Toxiproxy because two dependencies and a pinned image CI must pre-pull is a poor trade for seventy lines. Verified disconfirming: with `partition()` neutered both instances stay live, fair share gives 4 units each, and the takeover assertion fails `expected: 8 but was: 4`.
- **Construct hazards, do not hope for them.** Race-dependent assertions passed by luck twice and hid a message-loss bug once. The ordered-rebalance overlap test needed three attempts before it measured anything: the workload drained before the shards moved, then the handler finished before the successor could acquire, then the drain pushed the shed past the end of the workload. Assert on state captured *at the moment the hazard occurred*, not after.
- **Verify a "broken on purpose" run really compiled the break.** `open(p,'w').write(open(p).read()...)` truncates before it reads; Maven then reuses the previously compiled class and the disconfirming run silently tests the fixed engine. Two of these looked like clean passes.

- **A dead letter is addressed by `(shard, seq, source_lane)`, never `(shard, seq)` alone.** Unordered numbers `seq` per shard, ordered per queue, so one `(shard, seq)` can be parked in both lanes; the table's only unique key is `id`. `resurrect` matched without the lane and restored the other lane's row too. `deleteMessage` falls through to the dead-letter table (it used to touch only the live lanes, so deleting a dead letter returned false and it stayed listed). `ShardOwnedAdminSurfaceIT` pins both.
- **Poisoning a row behind a block asks the table, not memory.** Owners re-read blocks on the sweep cadence, so after an operator deletes a key's dead letter the in-memory block is stale; moving on it wrote the key's next message as a fresh unblocked dead letter, re-blocking the key. `poisonOrderedBehindDeadLetter` is one CTE that moves only rows with a dead letter below them (`EXISTS`) and returns the seqs moved; the owner refreshes blocks and hands the rest back to `readyByKey`. The `EXISTS` must use the owner's block rule — **any** dead letter below, `min(key_order)` as in `orderedDeadLetterBlocks` — not only one that itself failed: with the failed one deleted and rows parked behind it, the stricter test refused every row the owner handed back, so a message for the key was neither delivered nor parked, every pass. `blocked_by_key_order` then names the lowest remaining dead letter. `deleting_the_failed_dead_letter_leaves_the_key_blocked_behind_the_rest_until_it_is_resurrected` pins it.
- **`dispatchReadyKeys` tests the block before `dispatch.tryAcquire()`.** It used to acquire first and `continue` on a blocked key without releasing, leaking one `parallelConsumers` permit per hit until the consumer stopped dispatching. No reproducer IT — the path needs a refresh to discover a new block on a key whose rows are already held.
- **"A key is never in two handlers at once" holds only while handlers finish inside `leaseTtl`.** A heartbeat stall past the lease lets the cluster take the unit; a running handler cannot be recalled, so the successor starts the key beside it (fence keeps the queue correct, not the key). `ShardOwnedOrderedRebalanceIT` hit it: 1 s lease, 3 s handlers, a 1 s stall on a loaded build → 2 overlaps. Two guards: `evaluateLiveness` pauses dispatch at **4/5** of the lease (it paused at the full lease — the moment takeover is already allowed — while measuring from the heartbeat's return, a round trip late); `LeaseOverrun.check` in both owners' `runHandler` counts `handlersOutlastingLease` and WARNs once a minute per consumer. A test asserting no overlap must give the lease headroom over its handlers, or it measures a liveness lapse instead of what it is named for.
- **A caller that owns a `ShardRuntime` must pass it to `PostgresqlMessageQueue.builder().setRuntime(...)`.** Left unset, the queue's consumers borrow the runtime shared per `DataSource` — a second one next to the caller's, with its own pumps and listener, each holding a connection for good. Every `ShardRuntime` constructor starts it, so an unused one still holds `pumpThreads + 1`.
- **One instance id per subscription, NOT per lane.** `shard_queue_instance` is not keyed by lane, so registering `<id>-u` and `<id>-o` made one process count as two instances; every rebalance then computed `ceil(shards / 2)` and both lanes shed half their shards to nobody. Half of both lanes went permanently unowned ~20s after start — after the first rebalance, so every test that finished sooner passed. `ShardOwnedSpiFairShareIT` waits past it deliberately. A second `consume()` is the caller-side version of the same confusion — it is a competing consumer, not "the other lane" — and it is warned about rather than refused, because a genuine competing consumer is legal and the engine cannot tell the two apart. The warning is emitted from inside the registration lock, against `consumers` rather than the subscription index: a `consume()` whose `start()` threw has already taken an index but left nothing running, and warning there points the reader at the wrong failure.
- **Registration, the `started` flag and the `start()` calls are ONE critical section in `consume()`, and `start()`/`stop()` CAS *inside* the same lock.** Guarding only the list left two holes. A `stop()` interleaving after the add and before the starts stopped the new consumers while they were still unstarted — a no-op — and stopped every previously registered one for real; `consume()` then set `started` back to true, so the queue reported started with an earlier subscription silently dead, and `start()` could not recover it because its CAS sees true and returns. Separately, a throwing `start()` must leave nothing registered (bar a critical error, which stops nothing: `consume()` then registers the pair, or `stop()`/`close()` never reach the lane it left running): `startOrdered` begins with `verifyWatermarkPrerequisites`, so a database hiding `backend_xid` fails there *by design*, and registering first left a RUNNING unordered consumer no handle could reach — a caller retrying `consume()` then took the next subscription index and the process registered as two instances, which is the `fairShare` stranding the per-subscription identity exists to prevent. `a_failed_consume_leaves_nothing_running` pins it and was verified to fail against the old ordering. The lock is `PostgresqlMessageQueue.lifecycleLock`, NOT `consumers`' monitor, and that section has one bounded exception: `consume()`/`start()` hold the lock across their consumers' database work, so `stop()` waits `ShardOwnedQueue.SHUTDOWN_BUDGET` for it (interrupted: not at all), then marks the queue stopped, stops every registered consumer plus the pair being started without the lock (the one still leasing hands its work to its start) and leaves the holder a stop it owes (`handOver` guards one `Holder` value — `NONE`, `STARTING`, `UNDOING_A_QUEUE_START`, `UNDOING_A_SUBSCRIPTION_START`, `STOP_OWED`, `FINISHING_OWED_STOP`, `STOPPING` — every stop and the holder decide from, with `stopsWithoutLock` and `beingStarted` as data beside it — `beingStarted` holds the pair of EVERY `consume()` not yet registered, each taking out only its own: an observer's `consume()` on a starting `consume()`'s thread (reentrant) once overwrote the outer pair, so a stop giving up left the outer lanes running, `a_message_queue_stop_giving_up_on_a_consume_stops_its_pair_after_an_observers_nested_consume_returned`; no separate flag for a hand-over state, nor for a qualifier of one (which start is undoing is the value itself: `startEachOrUndo` is passed the undoing value its caller's kind moves to; a flag each start set and restored by hand around its starts once told them apart) — same rule as `Run.Phase`: moved only by `moveHolder`, along the diagram in `Holder`'s javadoc (`Holder.canMoveTo`; `PostgresqlMessageQueueHolderTest` pins it), never a hand-written `holder =`; a move off it is logged at ERROR with the caller's stack and the holder stays put, a move to where it stands is silent (the second owed stop), so a move that may rightly not apply reads the holder first and asks only for one it can make (`startEachOrUndo`); but not forward-only: no per-start object, it goes back to `NONE` per holder). `Subscription.start()` is a fourth holder (`STARTING`) and does NOT mark the queue started, nor does a `consume()` but one made while no subscription is registered (`consumers` empty): `stop()`/`close()` stop every registered consumer whatever `started` says, so neither needs to, and marking it made a later queue `start()` return at once with the other subscriptions a `stop()` stopped left stopped (`a_message_queue_start_after_one_subscription_started_on_its_own_starts_every_subscription`), and a failed start stops only the consumers it started (`startEachOrUndo`), or a queue `start()` failing on one subscription stopped another already consuming (`a_failed_message_queue_start_leaves_a_subscription_started_on_its_own_running`); a `stop()` on the holder's own thread (an observer told of an acquisition) never re-takes the lock, it is owed like an unlocked one (`stopFromInsideTheHolder`). The holder starts nothing more, never sets `started` (`consume()` and `start()` set it under `handOver` only while `Holder.letsNothingStart()` is false. It is true while the holder stops the queue, `stopsTheQueue()`: no stop owed, or `isStarted()` read true after that stop returned, and no owed or plain stop under way, or a start from an observer told of a release inside it started every consumer mid-stop; `a_consume_a_message_queue_stop_gave_up_waiting_for_...`, `a_message_queue_stop_from_another_thread_landing_...` and `a_message_queue_start_called_by_an_observer_while_the_queue_is_being_stopped_...` pin it. It is also true while the holder undoes its own failed start, `UNDOING_A_QUEUE_START`/`UNDOING_A_SUBSCRIPTION_START`, or an observer's `start()` told of a release started the very lanes being stopped; `a_message_queue_start_called_by_an_observer_while_a_failed_subscription_start_is_undone_starts_nothing` pins it), waits for those stops, stops every consumer again and only then lets go (`letGoOfLifecycle`, the last check and `moveHolder(NONE)` in ONE `handOver` block, or an owed stop is lost). On the monitor a `stop()` racing a partitioned start never reached any budget. `ShardOwnedLifecycleIT.a_message_queue_stop_called_while_a_start_is_still_leasing_...` pins it (verified failing on the monitor: 10 s). The adapter's `ShardOwnedDurableQueueConsumer` has five of these `Holder` values around `queue.consume()` (neither undoing value: it undoes no start of its own), NOT the same edges: its stop without the lock stops nothing and leaves all of it to the start, so a stop finding `FINISHING_OWED_STOP` returns owing nothing; here that stop stops every consumer itself (counted in `stopsWithoutLock`), so a stop arriving during `FINISHING_OWED_STOP` is owed again (`STOP_OWED`) and the holder repeats the stopping. Both read `NONE` alike: a waiting start's WARN supplier returns false and asks again one budget later, and a stop parks 10 ms at a time on the lock (`tryLockAfterAHandOver`, both through `shared`'s `Locks.tryLockDeferringPendingInterrupt`). Change one copy's protocol, check the other.
- **A voluntary release is not a lost lease, and saying so was a warning per unit for a normal handover.** `onLeaseLost()` was called both when a unit was TAKEN (renewal refused, or granted under a fence this owner does not hold) and when this instance gave one up — fair share, or an ordered unit that finished draining — and both logged `lease lost under fence N, owner stopping` at WARN. It is now `onLeaseEnded(LeaseEnd.RELEASED | TAKEN)`: per-unit at DEBUG for both, with the *taken* case summarised into one WARN per heartbeat tick at the caller, since that one still means something else believed this instance was gone. `beginShedding()` returns whether THIS call started the shed, so the caller's summary reports only what it began — it re-attempts every tick by design, and would otherwise re-report the same shed until it completed.
- **Ownership moves a unit at a time and is REPORTED a pass at a time.** Per-unit INFO on acquire/release meant one instance taking an ordered lane logged 64 lines, a two-instance rebalance 32 more per side, and six queues multiplied all of it — several hundred lines per rebalance, of which nobody reads a unit id. The loops collect and the caller logs once (`Instance demo-1 acquired 32 ordered unit(s) [32-63] on queue 1; now holding 32 of 64`); the per-unit line stays at DEBUG, where it keeps the **fence**, the part that is genuinely per unit. `ShardOwnedQueue.summarise` renders the runs, and is unit-tested because a summary that is quietly wrong is worse than the noise it replaced — `[32-54]` gives an operator no way to see it should have read `[32-53,55]`.
- **Everything `stop()` does against the database is best-effort, so it must also be BOUNDED.** Leases were released one connection per unit — 64 acquisitions on the ordered lane to perform one logical operation. Against a live database merely wasteful; against an absent one it is the difference between a shutdown and a hang, because a pool with nothing to connect to answers each request only when `connectionTimeout` expires (30s at Hikari's default). Measured: 145.8s to hand back one queue with the timeout cut to 2s, so ~36 minutes at the default, per queue, per lane — reported as "Ctrl-C does nothing". Now one statement over one connection (`ShardOwnedStorage.releaseFencedLeases`), and the whole leg runs under a 2s budget on an abandonable daemon thread. Abandoning is safe precisely because the work is optional: a lease expires and a membership row ages out on their own. `ShardOwnedShutdownBudgetIT` pins it and was verified failing against the old path. **The test must PARTITION, not stop the container** — a refused connection is an answer and returns in microseconds, so the per-unit cost is invisible and the old code passes.
- **`stop()` releases the leases**, after the pumps have flushed. Without it a graceful shutdown left every shard unserved for the rest of the TTL — 30s per rolling restart — while `Subscription`'s javadoc promised the opposite.
- **`leaseTtl` is its own setting**, not `holeExpiry x 3`. The two are bounded by unrelated things; deriving one from the other let a long outbox transaction silently triple failover time.
- **A message's identity is `(lane, shard, seq)`.** Sequences are per (queue, shard), so seq 1 exists in every shard — deduplicating on `seq` alone only works while a batch happens to land on one shard. A test did exactly that and reported 300 duplicates the moment enqueue started spreading properly.
- **`enqueue` round-robins per MESSAGE, not per call.** Hashing once per call puts a 5 000-row batch on one shard and serialises it behind one owner.
- **An observer that throws must not fail the message.** A broken `aroundDelivery` used to get every message retried and dead-lettered. Distinguish by whether the handler itself completed: if it did, log and acknowledge; if an observer threw before calling through, the message really was not handled.
- **A fresh `MessageQueue` is NOT started.** The flag was seeded `true`, so the first `start()` was a no-op. `stop()` keeps consumers registered so `start()` can restart them.
- **`isStarted()` is "marked started", not "anything running", and no binary answer suits a generic `Lifecycle` manager.** After a `stop()`, a `Subscription.start()` or later `consume()` runs lanes with it false, so a manager gating `stop()` on it (`DefaultLifecycleManager`) skips the queue; read as "anything running", a manager gating `start()` on it would skip the stopped subscriptions instead. Documented as a limit (`MessageQueue` class javadoc, README, LLM doc), not fixed; `ShardOwnedLifecycleIT.a_stop_called_only_when_the_message_queue_reports_itself_started_...` pins it — change the docs with it.
- **Only `Subscription.unsubscribe()` takes a subscription out of `PostgresqlMessageQueue.consumers` (`Subscription.close()` calls it, since 0.60.1 — try-with-resources and Spring's inferred destroy method mean "let go for good"); `Subscription.stop()` leaves it registered.** A caller that stopped and consumed anew (the adapter's consumer once did) left a stopped pair per round: COMPETING WARN with a new `-N` id suffix, and a queue `stop()`/`start()` restarting every abandoned handler. `deregister` removes the pair under `lifecycleLock` (waits `SHUTDOWN_BUDGET`, then — or at once on the holder's own thread — hands it to the holder via `toDeregister`, which `letGoOfLifecycle` removes and stops again: a lane the holder started before the retirement is stopped by whichever of that stop and the unsubscribe's gets there first, the other doing nothing; each lane remembers what either stop kept (`ShardOwnedQueue.keptOrderedOwners`), so neither stop's answer is lost). Before that `unsubscribe()` `retire()`s both lanes (`ShardOwnedQueue.retire`: the lane's `start()` then does nothing, read under the lane's own lock, so a lane start already under way is ended by the unsubscribe's stop instead), and `startEachOrUndo` skips retired lanes: the holder going over `consumers` starts neither from the retirement on. It used to restart them after `unsubscribe()` had returned, delivering to a handler let go of until the holder let go of the lock (`ShardOwnedUnsubscribeIT`'s two hand-over tests count the lane starts). Subscription indexes are lowest-free (`subscriptionIndexes`), given back by a failed `consume()` and by `Deregistration` only once every owed stop of its lanes has returned — both through `releaseSubscriptionIndex(index, lanes, ended)`, never a bare clear. A returned stop is not a finished one: its hand-back runs on a budget thread the stop abandons after `SHUTDOWN_BUDGET`, which may still `deregisterInstance` the id, so the index stays held while `ShardOwnedQueue.handBackMayStillDeregister()` (counted until the thread's work returns, not until the budget; only hand-backs of a stop that deregisters and kept nothing — one that kept a unit returns before the deletion). A lane stop that KEPT an ordered unit (key still in a handler past `shedGrace`) holds the index until that handler returns and the lane has handed the unit back, or until the key has been in its handler longer than `stuckHandlerTimeout` — a failed hand-back keeps it held, and `reserveSubscriptionIndex` has the old lanes retry it (`reviewAndHandBackKeptUnits`) before it picks an index; freed on failure, the next `consume()` took the unit unclean (`ShardOwnedQueue.keptOrderedUnitAwaited()`, asked of the old lanes; it was a lease TTL, which outlasted a quick handler and undercut a slow one) — the failed `consume()` too: an observer throwing for the ordered lane's acquisition escapes its start after it dispatched. Both in `heldIndexes`, freed lazily by `reserveSubscriptionIndex`: `acquireLeaseGrant` accepts a row naming its own owner, so a pair re-registering the id would take the kept unit at once and start the key beside its handler, or, after it, take it back as an unclean takeover. `ShardOwnedUnsubscribeIT` pins all six paths (mutation-checked), and `a_subscription_whose_kept_unit_could_not_be_handed_back_...` the retry (mutation-checked).
- **A dead letter's `last_error` names the root cause, not just the wrapper.** Both owners render it through `DeliveryErrorText`: the outermost throwable's `toString()` (`<type>: <message>`, just `<type>` without a message), preceded by a `Root cause: …` summary of the same shape when it is wrapped (several lines when the root cause's message has them, e.g. PostgreSQL `Detail:`). The summary comes from `shared`'s `Exceptions.prependRootCauseSummary`, which `foundation`'s `DeliveryErrorDescription` uses too, so both engines write it identically; change the summary there, never by re-rendering it here. Until 0.60.1 only the outermost throwable was stored, so a handler failing inside the adapter's wrappers left a dead letter naming the wrapper. The adapter's `DeadLetterErrorTextOnShardOwnedIT` pins both lanes.
- **`resurrect` takes a FRESH seq.** Re-inserting at the old value puts the row behind the owner's cursor, where only the head sweep finds it — up to `maxSweepInterval`.

- **The sweep backs off per SWEEP, not per pump iteration.** A pump iterates whenever any shard it serves has work, so doubling per iteration drove an idle shard to `maxSweepInterval` within milliseconds — which silently made delayed delivery and lost-notification recovery 30-second operations.
- **A failing statement is not a failing connection.** The pump asks `connection.isValid()` before treating a `SQLException` as connection loss. Conflating them made a permanently-broken statement look like a database blip: reconnect several times a second, forever, while every shard that pump served stopped delivering. Still paced at 200 ms, or a permanent failure spins — measured at 8 405 stack traces in one run — but per owner (`pumpRetryAtNanos`, checked before `needsAttention()`, folded into `park()`), the unchecked branch too. It was a 200 ms sleep after the pass, which held every other shard on the pump, across every queue it serves, to five passes a second (`ShardPumpDeliveryFailureTest.a_healthy_shard_keeps_delivering_...`). `onTakeover` gets the same treatment (`ShardPump.takeOver`): a takeover failing on a healthy connection is retried 200 ms later and the owner is not pumped until it completes. That wait is per owner too (`takeoverRetryAtNanos`, folded into `park()`): pacing the pass held every other shard on the pump to five passes a second while the takeover failed. `park()` folds in `parkDeadlineMillis()` only for taken-over owners: a never-swept owner's is always 0, which parked the pump 1 ms at a time (`backstopPolls` ~300/s in the IT); it used to reach the reconnect loop and stall every shard on the pump (`ShardOwnedTakeoverExhaustionRetryIT`). That retry has **no bound and keeps the lease**: releasing would hand a data-caused failure (trigger, constraint) to the next instance and bounce the shard between instances. So the shard is held and unserved, which `QueueHealth.unownedShards` cannot see. `TakeoverStalls` makes it visible on the OWNER's metrics: `shardsAwaitingTakeover` (alert on it next to `unownedShards`) and `takeoverFailures`, with at most one ERROR a minute **per subscription** (window on the owner's `ShardOwnerMetrics`, shared by every pump serving it and by both its lanes, so two `consume()`s of one queue get two windows and two counts; reopened when none of its shards is stalled), naming one shard and counting the others, and every failure at DEBUG (no stack trace). Per shard was not enough: a refused dead-letter move or an `onTakeover` bug fails every takeover, so a takeover of 64 units logged ~70 stack traces at once and 70 a minute. Those metrics are reachable only through `ShardOwnedQueue.metrics()` (`PostgresqlMessageQueue` keeps its `ShardOwnerMetrics` private), so the same two transitions also go to `QueueObserver.takeoverStalled` — the MessageQueue users' signal (starter, adapter), published by `MicrometerQueueObserver` as the eagerly registered gauge `essentials.queue.shards.awaiting.takeover`. Unlike every other observer call it is caught and logged (`TakeoverStalls.notifyObserver`): it runs on the pump thread outside the per-owner guard, so a throwing observer would end the pump. Caught as `RuntimeException | Error` then `rethrowIfCriticalError`, like the per-owner guards — a test double's `AssertionError` ended the pump while only `RuntimeException` was caught. `PostgresqlMessageQueue`'s fan-out tells every observer before rethrowing the first throw (same catch), so one bad observer cannot leave the others with a stall that never ends (`TakeoverStalledFanOutTest`). `ShardOwnedMicrometerIT.a_takeover_that_keeps_failing_...` drives it through a real refused takeover. Before that it logged a stack trace per retry, five a second, and counted nothing.
- **A failing `pumpOnce` is counted and rate-limited too (`PumpFailures`).** Both pump catch branches (unchecked, and `SQLException` on a valid connection) go through it: every failure → `pumpFailures` on the OWNER's metrics; ERROR with stack trace at most once a minute per SUBSCRIPTION (`nextPumpFailureErrorNanos` on the owner's metrics, so two `consume()`s of one queue get two windows; same CAS helper `ErrorWindow.take`, its own class so a change to the takeover window cannot reach this one); rest DEBUG, no stack trace; when the pass next succeeds INFO if that run logged the ERROR (`Failing.windowTaken`), DEBUG otherwise — an INFO per run end flooded when a check threw on and off, since each run is then one failure long. Entry dropped when the pass succeeds or the lease ends. A throwing selection check (`leaseHeld`/`deliveryPermitted`/`needsAttention`, also the end-of-pass lease sweep) is counted the same way but in its own run (`selectionFailed`), ended by the next pass whose checks all complete (`selectionSucceeded`), pumped or not: kept until the next successful `pumpOnce`, an idle shard's run stayed open for hours and its next throw read as "2 in a row over N s". Never let the selection close the `pumpOnce` run, or a retry whose checks pass cuts it to 1 every time. No gauge and no observer callback (unlike takeovers), so the window does not reopen on recovery. Before: a stack trace per pass, five a second, nothing counted (`ShardPumpDeliveryFailureTest`). The ordered lane's per-queue batched read (`ShardPump.batchRead`) fails on the same causes on the same passes, so it goes through `PumpFailures` too: `batchedReadFailures`, WARN with stack trace once a minute per SUBSCRIPTION (`nextBatchedReadWarningNanos` on its metrics; batches keyed by `PumpFailures.BatchedRead` = queue id + metrics, so two `consume()`s of one queue get two windows), every line naming the batch's shards so the two can be told apart, DEBUG otherwise, INFO on recovery only after a run that logged the WARN. Throttle only one and a revoked grant still floods from the other.
- **Never subtract a client clock from a server timestamp.** `millisUntilNextVisible` asks the server for the *interval*, not for `min(visible_at)`. `ServerSideTimeTest` catches `System.currentTimeMillis()` in the storage class, and it caught exactly this.
- **`getDouble` + `wasNull`, not `getObject(Double.class)`** — `EXTRACT(EPOCH ...)` returns numeric and pgjdbc refuses that conversion.
- **Bind `shard` and `attempts` with `setInt`, never `setShort` + a cast.** Columns are `smallint`; the Java side is `int` everywhere (`shardCount`, loop vars, `MessageId.shard`). The 36 `(short) shard` narrowings that used to bridge that read to a static analyser as unchecked truncation — safe only via an invariant it cannot see — and an external pipeline scanner flagged every one. `setInt` is better on both axes that matter, not just quieter: PostgreSQL's `integer_ops` btree opfamily carries cross-type `int2 = int4`, so the index is still used (verified on 17 — identical `Index Only Scan` plans), and an out-of-range write now raises `smallint out of range` instead of wrapping the way `(short) 32768` did. `queueId` is a genuine `short`; it keeps `setShort` and is not cast. `ShardRuntime.NO_QUEUE_ID` exists for the same reason — a constant narrows implicitly, a `(short) 0` at the call site does not.
- **Engine internals are package-private** (`ShardOwner`, `OrderedShardOwner`, `ShardPump`, `ShardWakeup`, `HandlerDispatch`, `LeasedOwner`). Their wide constructors are internal wiring; the project's 5-parameter ceiling applies to public and protected constructors, which is the line these sit on the far side of. `ConstructionErgonomicsTest` enforces it over this package, **unfrozen** — the module is compliant, so a frozen store would import other modules' debt and hide new violations here.
- **`ShardRuntime.SHARED` is an `IdentityHashMap`.** A `DataSource` is a resource, not a value, and framework proxies define equality as they like — two pools comparing equal would share one runtime drawing connections from the wrong pool. It also warns when a later borrower asks for a different `pumpThreads`, `readBatchSize`, `pollBackstop` or `maxSweepInterval` than the runtime's pumps were started with (`ShardOwnerSettings.runtimeScoped()`, the only values the runtime reads: it keeps only that record and gives each `ShardPump` only that, and `architecture.RuntimeScopedSettingsTest` fails when either calls another `ShardOwnerSettings` accessor — a value a pump needs goes into `RuntimeScoped`); every other setting is the borrowing queue's own, so comparing the whole record warned that a per-queue `stuckHandlerTimeout` was ignored when it was applied. `ShardRuntimeSharedSettingsTest` pins it.
- **Builders, not constructors, for `ShardOwnedQueue` and `PostgresqlMessageQueue`.** The identifying arguments are a `short`, an `int` and a `String` in a row; transposing `queueId` and `shardCount` compiles and silently addresses the wrong queue.
- **No semantic types, deliberately** — but not for the reason this used to give. `types` declares kotlin-reflect and kotlin-stdlib `<optional>true</optional>`, so neither is transitive and depending on it would add one jar that itself depends only on `shared`. What stands is that the builders already close the transposition hazard, and that this module holds to `shared` alone on purpose. See `docs/durable-queue-shard-owned.md` §15.

- **`shard_count` lives in the registry, with the name, and is now the UNORDERED lane's alone.** It is a property of the queue, not of the process: an unordered producer believing in 8 and a consumer believing in 4 write to shards nobody leases. `ShardOwnedQueueRegistryIT` reproduces that stranding before asserting the protection. Re-registering a name with a different count is refused. The ordered lane does not read it at all — see `ShardOwnedSchema.ORDERED_UNITS`.
- **Interning races are resolved by the DB, not by the caller.** `INSERT ... ON CONFLICT (queue_name) DO NOTHING` then **read back** — on conflict the insert wrote nothing because another process won, and its id is the one that counts. Burned sequence values are harmless; an id is a token.
- **`QueueName` is a local record, not a `CharSequenceType`.** Same decision as the other semantic types above, and the same correction: the Kotlin cost is not transitive, so what the choice rests on is the builders and this module's `shared`-only dependency, not a jar it would have inherited.

- **A handler is given the message's `key_order`, through a `default` overload.** `MessageHandler`/`OrderedPayloadHandler` keep the 4-argument method lambdas implement; the engine calls the 5-argument `handle(messageId, key, keyOrder, payload, payloadType)`, which defaults to it. Free on the hot path — the ordered cursor read already returns `key_order` to order dispatch by. Unordered passes `0`, as `Message.of` stores. `QueuedMessage`/`DeadLetter`/`HandleMessage` carry it too. It was dropped at the owner, so the `DurableQueues` adapter rebuilt every `OrderedMessage` with order 0 and every `EventProcessor` on this engine resolved each forwarded event to the aggregate's first — see the adapter's `CLAUDE.md`
- **`payloadType` is opaque application metadata**, not an interned FQCN and not an index-density measure — it is in no index and nothing interns it. It reaches the handler via `MessageHandler.handle(messageId, key, payload, payloadType)`; it used to be written on every row and returned only on the pull and dead-letter paths, so the push path — how almost everything consumes — never saw the one thing it was for. Both lane reads now `SELECT payload_type`, and `Row`/`OrderedRow` carry it.

- **Interceptor vs observer is a real distinction, not two names for one thing.** Observer is *told*; interceptor is *in the path* and can modify or skip. An observer that throws must not fail its message; an interceptor that throws must. Both are read when a subscription starts, so both must be attached before `consume`.
- **The chain is skipped when empty** — `interceptors.isEmpty()` short-circuits in both `enqueue` and `invoke`, so the common path allocates no operation, chain or lambda. Delivery interception runs once per message; an unconditional chain is exactly the kind of obligation the cost decomposition exists to expose.
- **Interceptors are sorted at registration, not per call.** `@InterceptorOrder` is read reflectively; sorting per delivered message would put reflection on the hot path.
- **Only `EnqueueMessages` and `HandleMessage` are interceptable.** The other SPI members gain no capability from it — an observer already sees them and nothing useful substitutes for their results.
- **Not proceeding on `HandleMessage` acknowledges the message.** A dropped message and a handled one look identical afterwards; say so wherever this is documented.

- **By-id operations do NOT need a claim flag, and the SPI javadoc used to say they did.** `MessageId` is `(lane, shard, seq)` and the primary key is `(queue_id, shard, seq)` — addressing a row is a point lookup. The claim write this design removes is paid per *delivery*; an admin write is paid per *administrator*. Those were priced as if they were the same frequency. Acknowledgement stays session-scoped, because the engine cannot know an arbitrary caller did the work.
- **A by-id write races an in-flight delivery and cannot be fixed.** In-flight lives in the owner's memory. The mismatched ack is already tolerated (`stillOwns` disambiguates it); what is not guaranteed is that the handler did not run. Document it, do not try to close it.
- **The readable views are ergonomics, not storage.** `shard_queue_*_readable` render `bytea` via `shard_queue_readable()`, which falls back to hex on non-UTF-8 — a view that raises on one binary row is worse than one that shows hex. `recreate` must drop the views before the tables.
- **A stopping lane leaves the membership row to the OTHER lane of its subscription while that lane needs it** (`ShardOwnedQueue.shareMembershipWith`, set by `consume()` on both lanes; `needsMembership()`: a run installed, still draining, a stop that kept an ordered unit, or a hand-back of a kept unit running with its row held, the last read live). A `PostgresqlMessageQueue` pair shares one id and the unordered lane stops first: its DELETE made the ordered lane's kept unit (or units it still served) read as gone, taken at once by another id, key started beside its handler. Decided in memory by the lanes, never from lease rows: a lease-row `NOT EXISTS` could not tell a served or kept unit from one whose release failed, so a failed unordered release kept the row and held survivors at a stale fair share for a lease TTL. Not by `PostgresqlMessageQueue` either: only a lane knows when its stop has finished (handed to a start still running, or a hand-back past `SHUTDOWN_BUDGET`). Each lane writes its own need before reading the other's, so of two ending at once at least one deletes (unless a lane kept a unit: then neither does, and the row ages out a lease TTL later). A standalone `ShardOwnedQueue` deletes on every stop that keeps nothing. Paired or not, a lane's hand-back reads its OWN `needsMembership()` first: a stop abandons it after `SHUTDOWN_BUDGET`, and finishing after a restart of the same queue it deleted the row the new run had just registered (units read as ownerless until the next heartbeat). A deletion already past that read is waited for by `start()` before it registers (`deregistrationsRunning`, `awaitDeregistrationsRunning`: up to `SHUTDOWN_BUDGET`; if it has not finished by then, this logs one WARN and goes on); each side writes its own before reading the other's. `ShardOwnedLifecycleIT.a_restart_keeps_its_membership_row_...` and `a_restart_while_the_stop_before_it_is_deleting_...` pin both (mutation-checked). `ShardOwnedUnsubscribeIT.a_subscription_whose_stop_kept_...` (mutation-checked: row gone) and `..._whose_unordered_release_failed_...` (failed on the lease-row version) pin it.
- **`stop()` must DEREGISTER, not only release leases.** `fairShare = ceil(shardCount / liveInstances)`, so a departed instance that still counts holds every survivor at a quota for a cluster that no longer exists — the shards are free and nobody may take them. That made a graceful scale-in worse for the cluster than a crash, which is the autoscaler's normal path.
- **Membership rows were never deleted, only upserted.** With a per-boot instance id — the Spring starter's default, and what any autoscaled deployment produces — that is one row per pod that ever ran, on a table every heartbeat scans. The heartbeat now prunes past 10x `leaseTtl`: garbage collection, deliberately far outside anything `fairShare` reads.
- **Each lane caps horizontal scale by its OWN unit count.** At most N instances can hold anything for a lane with N units: `shardCount` for unordered (size it >= the most instances you will ever run, not just for throughput) and the fixed `ORDERED_UNITS` for ordered, which is 64 and therefore not a limit anyone reaches. The larger of the two is reported as `maxInstances` on `ApiShardOwnedQueueStatus` (derived in its `from(...)` factory), **not** on `QueueHealth` — that record carries `shardCount()` and `orderedUnits()` separately and has no combined accessor.
- **Historic: shard count had a measured knee at 4, with 8 buying 95% of what 16 does.** Ordered lane, 500 keys, 2ms handler: return per shard fell 1155 -> 151 msg/s from one shard to sixteen, one shard being the noisiest arm (74% IQR vs 3% at eight) because everything serialised through one owner. `ShardOwnedShardCountSweepIT` is DELETED — it swept a knob the ordered lane no longer has, so every arm would now measure the same 64 units. The number survives as the justification for `ORDERED_UNITS` being 64: far past the point of return, which is what a fixed space wants.
- **The ordered lane's routing space is FIXED at `ORDERED_UNITS` (64) and nothing configures it.** This was the design defect: ordered `shardCount` was effectively immutable, `growShardCount` refused while the lane held anything, and the only way to satisfy that was stopping producers. Growing now moves nothing and is allowed with ordered traffic in flight (`growing_is_allowed_while_the_ordered_lane_holds_messages`). The constant is frozen for the life of the schema — changing it moves every key.
- **The caller's `maxShards` does NOT apply to the ordered lane, and honouring it strands messages.** It meant "how many of the queue's shards will I serve" and callers passed the shard count, so a caller passing 8 would hold 8 of 64 units and leave 56 owned by nobody — every key hashing to one of them silently undelivered. `startOrdered` pins it to `ORDERED_UNITS`; `fairShare` decides the split.
- **A per-unit counter table on the enqueue path is closed, not open.** Measured: the row lock is held to the CALLER's commit, so an Outbox producer blocks every other producer on that unit for its whole business transaction (211 ms behind a 200 ms tx), and a large ordered batch takes a lock on every unit it touches, so it blocks all of them. No fix from inside a caller-supplied transaction — savepoints do not release locks. `nextval` acquires nothing; keep it.
- **Measure a queue read in the near-idle state, not just under backlog.** A range read whose cursor sits at the end of its range flips off the discovery index onto `*_visible` with an Incremental Sort: 0.62 ms with work to do, **10.16 ms** with none — and near-idle is where the engine spends its polls. Same trap in reverse for a per-unit cursor list joined ordinarily: the planner merge-joins it and scans the whole index (234 ms on a sparse wake-up). `LATERAL` with a per-unit inner `LIMIT` makes the nested loop structural rather than a planner choice, and is stable in all three states.
- **A range read makes round trips O(1) per owner; it does NOT make units free.** Three buffers per unit held per poll, linear, no amortisation — 24 at 8 units, 3 072 at 1024. That is what caps the routing space, independently of anything about sequences.
- **Ordered sequences are ONE per queue; unordered stay per (queue, shard).** Per-shard ordered sequences existed for density, and the watermark does not need it — so the only thing they still cost is relations, which is what makes a large routing space unaffordable across many queues. Consequence: an ordered `seq` is unique within the queue (the "seq 1 exists in every shard" trap is gone for that lane), and an owner's sequence values are sparse within its shard, which is fine for the watermark and would NOT be fine for hole detection. That is why the unordered lane was left alone.
- **`maxWatermarkLagSeq` is a span of sequence values, not a row count.** With one ordered sequence per queue, an owner's span covers other shards' rows: a 500-message batch over 4 shards reads as 500 while each owner re-reads ~125. Size the real re-read cost with `cursorReadsPerMessage`. An assertion written against it as a row count passed until the sequences were collapsed, then failed.
- **Batching the pump's reads is an IDLE-cost mechanism, not a throughput one.** `needsAttention` consumes a per-shard wake-up so a pump reads only the shard that was signalled — which means under load typically one shard is attentive per pass and there is nothing to batch (measured: statements issued equalled owners served). The win is the case where many shards' sweeps come due together. Specify and test it against a quiet queue's queries/s, not against a workload.
- **The ordered routing space is a per-queue, registration-time choice with `ORDERED_UNITS` as its default.** `registerQueue(dataSource, name, shardCount, orderedUnits)`. Safe to fix per queue in a way it was never safe to fix globally, because routing reads the recorded value — upgrading the default changes nothing for an existing queue. Measured, one queue idle: **64 / 256 / 1024 units all cost 1.2-1.3 queries/s**, flat, because reads are batched per queue and units carry no lease to renew. Acquisition is the only per-unit cost left and it is one-off: 144ms at 64, 221ms at 1024. What still grows is per-unit STATE — a lease row and an owner object each — so do not raise the default for a process running hundreds of queues; raise it for the one queue that needs more than 64 consumers.
- **An instance-owned lease carries NO expiry; a pull session's does.** `lease_until` is NULL for a unit held by an instance — liveness is that instance's row in `shard_queue_instance`, which the heartbeat refreshes once per queue. It used to be a real expiry, which meant the heartbeat WROTE one row per owned unit: invisible at a few shards per lane, and the dominant idle cost at 64 ordered units. Measured across 5 idle queues holding 170 units: **17 lease writes/s against 6.8 reads, then 0.0** — total idle queries/s went 23.8 to 7.4. A SHARD-scope session is not an instance and heartbeats nothing, so it keeps an expiry and renews it (`acquireSessionLease`); which rule applies is decided by whether `lease_until` is NULL.
- **An instance MUST register itself before acquiring anything.** Registration used to happen on the first heartbeat, ten seconds in. Once liveness moved to the instance row, that left every instance looking dead for its first ten seconds — so instances stole each other's units on start-up, and the two-instance split tests hung. `startUnordered`/`startOrdered` now call `heartbeatInstance` before the acquire loop.
- **Correctness never rested on the lease expiry — it rests on the FENCE.** An owner whose unit is taken finds its fence bumped and its writes refused, whether the takeover came from a lapsed lease or a stale instance row. That is why removing the expiry is safe; a test asserting liveness via `lease_until > now()` is asserting the mechanism rather than the property, and will report nobody.
- **`ORDERED_UNITS` is the default for a queue being CREATED, never the truth for one that exists.** Routing reads `ordered_units` from the registry per queue (`ShardOwnedStorage.orderedUnits()`, resolved once), so a build with a different default uses it only for new queues and leaves existing ones routing exactly as before. An earlier revision instead REFUSED on a mismatch — correct about the hazard, wrong as an answer, because it turned a version upgrade into "drain this queue and re-create it": the manual, outage-shaped step §1 of the design rejects for `shardCount`. There is no ordered-lane failure left that a human has to heal.
- **Both failure directions of the fixed routing space are measured, not assumed** (`ShardOwnedRoutingSpaceIT`). Too small: 65 instances against 64 units converge to 64 holders of one unit each and one idle — nothing lost, duplicated or reordered, so the ceiling DEGRADES rather than breaks. Changed: refused at registration. A test asserting only "every unit is owned" passes trivially in 2s because the first starter grabs all 64; assert the units are SPREAD or it proves nothing.
- **`registerQueue(dataSource, queueId, shardCount, orderedUnits)` — the id-based overload — writes NO registry row.** It creates the sequences and seeds the lease rows, and that is all; `ShardOwnedStorage.orderedUnits()` then finds no row and returns the default 64. So a test registering two ordered units that way gets two lease rows and an engine that believes the space is 64: the first instance holds both units, `fairShare` is computed as `ceil(64/n)`, and nothing ever rebalances. Use the NAME-based `registerQueue(dataSource, QueueName.of(…), shardCount, orderedUnits)`, which returns the `RegisteredQueue` whose `queueId()` the low-level constructors take.
- **`surplusInstances`, `deliveryPauses` and `keptUnitsInHandler` are on `snapshot()`, deliberately not on `QueueStatistics`.** That record is the admin API's published shape, so adding a field is the three-place sync plus a moving number inside a contract compatibility-checked at `1.0.0`. The first two are logged on transition instead, kept units by a rate-limited WARN. Decision and trigger in `docs/durable-queue-shard-owned.md` §18.3 — do not quietly append to the record.
- **`surplusInstances` is the routing space's own alarm.** `rebalance()` records `max(0, liveInstances - units)` on `ShardOwnerMetrics` and warns once when it becomes non-zero, once when it clears — on transition, because the heartbeat runs every `leaseTtl / 3` and a deployment one instance over would otherwise warn every few seconds forever. It is the only signal that separates a surplus instance from an instance whose queue is quiet, and the ordered lane's space cannot be grown, so it is the evidence `docs/durable-queue-shard-owned.md` §18.3 asks for before that decision is reopened.
- **Asserting the surplus and asserting the spread need different waits.** The count is true from the first heartbeat; the ownership it describes takes a rebalance to converge, because the instance that started first holds everything until then. A test that reads `shardsHeld()` immediately after the metric agrees sees one idle instance too many.
- **The ordered lane REFUSES to start where `backend_xid` is not readable.** Its cursor decides safety from `max(backend_xid)` over `pg_stat_activity`; if that is redacted the query does not fail, it returns a SUBSET of the running transactions — and a subset is not degraded, it is wrong, because the watermark then advances over a live writer. `verifyWatermarkPrerequisites` constructs the condition rather than inspecting the column (which is legitimately null for a backend that has not written): it forces a second connection to take a real xid and asserts the first can see it. Once per `DataSource`. Verified on 17.5 that a plain LOGIN role with no `pg_read_all_stats` can see it, and that revoking the view makes `startConsumingOrdered` fail with the grant named in the cause.
- **A pump is process-wide; anything it does for one queue must be bound to that queue.** `ShardRuntime` hands each pump a `ShardOwnedStorage` bound to **queue id 0** ("only used to open connections") and builds its **own** `ShardOwnerMetrics`. Issuing a batched statement on that handle queries queue 0 and returns nothing, silently; counting on those metrics is invisible to `queue.metrics()`. Both bugs shipped and cost two sessions of probing. `LeasedOwner` exposes `queueId()` and `ownerMetrics()` so the pump groups by queue and counts on the queue.
- **A batched sweep that returns nothing is not the same as no sweep.** The owner sets `lastSweepNanos` and `sweptThisPass` when it applies one, so an empty batched sweep suppressed the real sweep AND doubled the backoff on every pass. That pairing is why a mis-bound query looked like starvation — short parks, few passes, backoff at the 30s ceiling — rather than like an empty result. `null` swept rows mean "not asked"; empty mean "asked, nothing there".
- **A batched read must return a FULL batch per shard, not a share of one.** Dividing `readBatchSize` across the shards in a pass makes the batched read return less than the per-shard read it replaces, so an owner sees a different amount of its own backlog depending on how many siblings happened to be attentive. `ShardOwnedBatchedReadIT` pins the equivalence in both directions.
- **Idle cost is flat in the routing space, and that is load-bearing rather than incidental.** 64 / 256 / 1024 units all cost 1.2-1.3 queries/s on one idle queue, because reads are batched per queue AND an instance-owned unit carries no lease to renew. Break either and it goes linear again: before the reads were batched, raising the space to 64 would have turned 8 queries per poll cycle into 64. `ShardOwnedRoutingSpaceCostIT` (benchmark-gated) is the guard.
- **A snapshot's `xmax` does NOT bound running xids.** `xmax` is `latestCompletedXid + 1`, so a transaction holding an assigned xid sits at or above it and appears in neither the in-progress list nor below `xmax` — one running writer reads as `55486:55486:`, an apparently empty snapshot, and 98% of polls under a concurrent write load look idle. Any "has everything from then finished?" test built on `xmin >= xmax(X)` advances over live writers (measured: 12.6 ms of apparent lag against 64.1 ms of real lag). The bound that works is `max(backend_xid)` over `pg_stat_activity`, 0.086 ms, sampled AFTER the value it is protecting — never before — when it RECORDS a candidate; retiring one uses the probe taken BEFORE the read (next bullet).
- **Retire a watermark candidate against the probe taken BEFORE the read, record one with the probe AFTER it.** A candidate says "values ≤ maxSeen, these writers running". Retiring it on the probe that follows the pass's read let a writer commit between that read and that probe: missing from the probe, its rows invisible to the read, so the cursor stepped over them and the head sweep delivered them late — behind later `key_order`s of the same key. Seen in the trading demo as lost ledger cycles; `ShardOwnedConcurrentProducersOrderIT` (8 producers, disjoint keys, multi-unit transactions) hit it in 4 of 5 runs before the fix; `ShardOwnedOrderedWatermarkIT.a_writer_committing_between_the_read_and_the_probe_is_not_stepped_over` pins it on every run, committing the writer between a read and the pass `applyBatchRead` hands it to. `OrderedShardOwner.runningAtLastProbe` is the pre-read probe; a pass whose read hit its row limit advances no further than the last row it read (`readReachedSeq`; `READ_NOT_CAPPED` when the read returned fewer rows than its limit). That limit is the one the read was ISSUED with: a pump's batched read uses the `ShardRuntime`'s `readBatchSize`, which can be smaller than the queue's, so `applyBatchRead` carries it (`cursorLimit`); judged against the owner's own, a truncated batch looked complete and the cap never fired. `ShardOwnedOrderedWatermarkIT` drives both by hand (limit 5). Cost, measured A/B on 40 000 messages: drain +1.2 % median (inside the spread), read statements unchanged, watermark lag +21 % (one pass later). The stepped-over signal is `sweepRecoveriesBehindCursor` (`snapshot()` only), NOT `sweepRecoveries` (not a defect signal — see the `sweepRecoveries` bullet), which also counts rows committed between a pass's cursor read and its sweep. It too counts delayed messages, retries and requested redeliveries, interrupted handlers reached by the sweep after the cursor passed them, and rows a `watermarkCapped` advance stepped over; with none of those, non-zero means the watermark stepped over a row (`ShardOwnedConcurrentProducersOrderIT` asserts zero).
- **A long READ-ONLY transaction does not hold the xid horizon back**, however long it runs — only a writing one does, because only a writer is assigned an xid. Do not cite `pg_dump` or an analytics query as a hazard for anything keyed on `pg_snapshot_xmin`; a 13 s reader is indistinguishable from no reader.
- **The ordered lane's cursor is a safe watermark, not a high-water mark.** It advances to a value only once every write transaction running when that value was observed has ended — `max(backend_xid)` over `pg_stat_activity`, compared by set identity because `backend_xid` is a wrapping 32-bit `xid` and `pg_snapshot_xmin` is a non-wrapping `xid8` with no cast between them. Record a candidate with the probe taken AFTER the read, never before; retire it against the probe taken BEFORE the read (the retire-before-read bullet above). Skip the probe entirely when caught up or the idle poll pays 0.086 ms for nothing. Hole chasing, `holeExpiry` and `maxHolesPerChase` are gone from THIS lane, and `chaseDelay` only paces how often an owner with an unretired candidate asks for another probe (`OrderedShardOwner.needsAttention`); the unordered lane still uses all of them, so the settings stay.
- **`watermarkCap` is not `holeExpiry` and must stay far larger.** Both say "stop waiting", but `holeExpiry` was held low by a map entry and a chase query per unresolved value, and the watermark costs one deque entry and no query. Set the cap as low as `holeExpiry` and the two mechanisms become behaviourally identical — the watermark force-advances on the same timer that abandoned a hole, and the exactness is thrown away. A test written against the old, reused setting passed against a deliberately broken implementation for exactly this reason.
- **A key NEVER advances past a dead letter, and the messages behind it are dead-lettered rather than left queued** (`docs/durable-queue-shard-owned.md` §9.1). It used to release the key, which was the one ordering difference from `PostgresqlDurableQueues` that changes what a handler sees — its fetch barrier's `NOT EXISTS` filters on key and order alone, so a dead-lettered row has always blocked there. Three things about the implementation are load-bearing and not obvious:
  - **The block is DERIVED, never remembered.** `ShardOwnedStorage.orderedDeadLetterBlocks` groups the DLQ by `msg_key` (both `msg_key` and `key_order` were already copied there by `moveToDeadLetter`). Read in `onTakeover`, before the first `pumpOnce`, and thereafter only while a block stands. A memory-only block clears on every rebalance and restart *silently*, which is the failure the rule exists to prevent, reintroduced by its own enforcement.
  - **Poisoning happens at DISPATCH, never at enqueue.** `PostgresqlDurableQueues` has the enqueue-side variant written (`getQueueMessageSqlOptimized` — dead code, referenced nowhere) and it would put an `EXISTS` inside the producer's transaction. Ours keeps the producer path free, and the placement is also what keeps `readyByKey` from growing per blocked key and the head sweep from spending its `readBatchSize` re-reading rows it can never deliver.
  - **A row arriving at EXACTLY the blocked `key_order` requests a re-derivation, it does not clear the block.** That row can only be the resurrected dead letter — `(key, key_order)` is unique and the original was deleted when parked. Clearing directly would be wrong when several of a key's messages are parked: lifting at 5 while 6-8 are still dead lets 9 through. The refresh runs before dispatch in the same pass, and `poisonBlocked` re-tests every candidate against the blocks as they then stand, dropping (and un-`seen`ing) any whose key was released — otherwise a message queued for the DLQ microseconds before a resurrect is thrown away for nothing. Without the request the block would only lift on the sweep cadence, which has backed off to `maxSweepInterval` precisely because the shard stopped delivering, so a resurrect would appear to do nothing for 30s.
  - **`blocked_by_key_order` is a COLUMN, not a marker in `last_error`.** Null = tried and failed; set = never ran, and the value is the lowest dead-lettered `key_order` for that key that is not itself blocked, resolved per row inside the insert so it names the message recovery actually starts from. `DeadLetter.neverDelivered()` asks it. NOT `attempts` — a takeover bumps attempts on rows that were never delivered. Added by `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` on every boot (the table already shipped), and projected by `shard_queue_dead_letter_readable` with a `never_delivered` boolean. The read mapper reads it into a local **before** constructing `DeadLetter`: `wasNull()` reports on the most recent get, so asking it inside the constructor call answers for `payload_type` and every row comes back claiming it was never delivered. That shipped and the test caught it.
  - `keysBlockedByDeadLetter` and `messagesPoisonedBehindDeadLetter` are on `QueueStatistics`, not just the debug map — but they are running totals and never fall, which read as "still broken" on a console after a resurrect. Current state is `QueueDepth.blockedKeys` / `parkedBehindDeadLetter` (one `FILTER`ed count over the dead-letter table, in `deadLetterSummary`), on the admin status as `blockedKeys` / `parkedBehindDeadLetterDepth`. `blockedKeys` counts distinct ordered keys with ANY dead letter — the owner's block rule, not only keys whose head failed.
  - **Cost, measured** (`ShardOwnedStalledKeyCostIT`, benchmark-gated, `docs/durable-queue-measurements.md` §3.11): a stalled key costs 1.70x WAL per message (801 B vs 471 B) and 75% of throughput — but 241 B per row in `shard_queue_dead_letter`, which is shared by every queue on the database, so an hour stalled at 100 msg/s is ~87 MB everyone else reads past. The suite asserts the lane drains to zero; if the poison path could not keep up, dispatch-side placement would have bought nothing.
  - **Recovery is `resurrectKey(key)`, and ONE TRANSACTION is what makes the replay order right** — not the `ORDER BY key_order` in the insert. The rows become visible together, so the owner holds all of them before dispatching and its per-key `TreeMap` orders them whatever seq they got; the `ORDER BY` only matters when the batch exceeds `readBatchSize`, where it keeps seq ascending with key_order so the prefix is still lowest-first. Per-message resurrect still has to be walked ascending and awaited. Admin surface: `ShardOwnedQueuesApi.resurrectDeadLettersForKey` → `POST /shard-owned-queues/{queueName}/ordered-keys/{key}/resurrect`; the conformance count moved 50 → 51.
  - **`PoisonCandidate` carries its ROW, not just the seq**, so a candidate released by a lifted block goes straight back into `readyByKey` and is dispatched that pass. Dropping it and un-`seen`ing it is also correct and up to a sweep interval slower — which is exactly the wait `resurrectKey` exists to remove.
  - **The blocked-key WARN is once per key AND at most once a minute per consumer** (`BlockedKeyReport`, the `LeaseOverrun` pattern), the next one carrying a count of the keys blocked since; every key stays at DEBUG. Once per key was not enough: a handler failing for everything (the tracing-interceptor bug) blocks every key with traffic, and the trading demo logged a WARN per new key on every queue without end. The line names the queue id: shard numbers repeat across queues, so two Inboxes fed the same trade events read as one key reported twice.
  - `ShardOwnedDeadLetterBlocksKeyIT` pins the behaviour (5 tests) and the block-disabled disconfirming run failed all three that existed then.
- **A delayed ordered message does NOT block its key, and that is left deliberately** (`docs/durable-queue-shard-owned.md` §18.3). Only visible rows are dispatched, so an undelayed later `key_order` overtakes a delayed earlier one; `PostgresqlDurableQueues` blocks the key, because its barrier does not filter `next_delivery_ts`. **The factory cannot be retired** — the adapter reaches it from `queueMessage(queue, orderedMessage, deliveryDelay)`, so it exists to serve `DurableQueues`. Fixing it is not a query tweak: the owner would have to HOLD not-yet-due rows (the cursor read would stop filtering `visible_at`, widening the read that runs ~2x per delivered message; `OrderedRow` would carry `visible_at`; the release would need the interval-not-timestamp treatment the retry schedule already uses), because once the cursor passes a not-yet-due row nothing re-reads it — the head sweep filters `visible_at` too. Trigger to reopen is in §18.3; the warning is on `Message.delayedOrdered` where a caller will actually see it.
- **The watermark does NOT prevent the ordering violation, and it was briefly documented as though it did.** It governs the cursor, not dispatch: a row read from above the gap is still handed to its key, so a late commit under a lower `key_order` still counts an `orderViolation` (measured). Preventing it means gating dispatch on the watermark, which costs every message ~11ms. `ShardOwnedOrderingBoundaryIT` pins the two producer-visible halves of that: a delayed `key_order` is overtaken by a later undelayed one and the violation is counted (a per-key delay is a reordering instruction — only visible rows are dispatched), and reusing a `key_order` for a key is refused by the primary key rather than overwriting the message already queued under it. The README's ordering section enumerates the rest, including the two that look like they should reorder and do not — a retry (the key stays blocked and the message goes back at its head, also across a hand-over: next bullet) and a voluntary hand-over (drain, or abandon the shed and keep the shard).
- **A retry's key block is DERIVED on takeover, not only remembered (N-16, RN-4).** `keysAwaitingRetry` and `retrySchedule` are the owner's memory; every other read a successor makes filters `visible_at <= now()`, so until 0.60.1 a rebalance, graceful stop or crash let a later `key_order` overtake the message in backoff. `onTakeover` now calls `restoreRetriesInBackoff` after `refreshDeadLetterBlocks`: `ShardOwnedStorage.orderedRetriesInBackoff` returns rows with `visible_at > now()` AND `attempts > 0` plus the server-measured remaining backoff, and they go into the schedule with their keys blocked. Two load-bearing details: (1) `attempts > 0` is what separates a retry from a delayed row, so `bumpOrderedAttemptsOnTakeover` must skip rows not yet visible — bumping a delayed row made the next takeover read it as a retry and block its key (`a_delayed_message_still_does_not_block_its_key_after_two_hand_overs`, verified failing with the old bump); (2) `inFlight()` deliberately still counts only keys in a handler — a draining owner never dispatches a retry, so waiting for one would only make `stop()` keep the unit until `leaseTtl`. `ShardOwnedOrderedRetryHandoverIT` (rebalance, graceful stop, crash) and the adapter's `OrderedRetryHandoverOnShardOwnedIT` failed on the old code.
- **An ordered-lane hazard test must keep the shard BUSY.** With nothing else arriving the owner parks and re-examines the gap only when the held transaction's commit wakes it — by which time the value is visible and every mechanism, correct or broken, looks right. The first version of `ShardOwnedOrderedWatermarkIT` made that mistake and passed against a deliberately broken cap.
- **Measure a horizon or staleness claim against a positive control.** Arms A-C of the watermark gate showed no stall, which is only meaningful because arm D — an unrelated 13 s *writing* transaction — stalled 98% of polls for 12.75 s. Without it the result is an uncalibrated negative. Same family as the failure-injection rule above.
- **There is nothing to size for the ordered lane any more.** It has a fixed space and no knob; size `shardCount` for the unordered lane's throughput today and grow it with a single call when that changes. The advice this replaces — "size ORDERED for future peak, pause producers to change it" — described a procedure that did not exist.
- **Idle cost is per QUEUE, not per unit — measured, and gated.** 64 units, 200ms sweep with backoff pinned off: **84 statements over 3s against 2 880 if every unit read for itself**, serving 1 219 owner-passes. `ShardOwnedOrderedIdleCostIT` holds it, and asserts the sweep is still running so "cheap" cannot mean "stopped". `ShardOwnedMultiQueueCostIT` covers both lanes — it builds an unordered and an ordered consumer per queue. Note it gives them distinct instance ids (`cost-u-N`, `cost-o-N`), so each queue sees two instances and fair share hands each consumer half its lane. That does not skew the result, because every figure it reports is normalised **per owned unit** rather than per queue; an absolute threshold would have been the wrong shape anyway.
- **Redeploy and autoscaling never change `shardCount`**, so they never open a two-moduli window — and since the ordered lane no longer reads it, neither does `growShardCount`. The everyday paths are asserted boring by `ShardOwnedAdminSurfaceIT.restarting_and_scaling_instances_never_changes_the_shard_count`.
- **BOTH sides must learn about growth.** The consumer side refreshes on the heartbeat; the producing side refreshes in `route()`, time-guarded at 10s, because a query per enqueue would be a per-message cost. Wiring only the consumer side leaves a producer routing by the old modulus while its own consumers lease the new shards — and a growth test still passes, because the old shards are still owned.
- **A grown `shardCount` is picked up at runtime**, no restart: the heartbeat re-reads the registry and `rebalance()`'s acquire loop iterates to the lane's unit count. `shardCount` is `volatile` — the unordered enqueue path reads it too. Growth only; a smaller registry count is ignored and logged, since dropping shards strands their rows. The one-heartbeat window is harmless: unordered is round-robin, and ordered does not read the number.
- **`shardCount` can grow freely now, and neither lane pins it.** Unordered is round-robin so nothing depends on a message's shard; ordered routes on its own fixed space. `growShardCount` still refuses to SHRINK, because the messages in the removed shards would be addressed by nobody. **No restart** — a running consumer re-reads the registry on its heartbeat, asserted by `a_running_consumer_picks_up_a_grown_shard_count_without_a_restart`. This bullet has been wrong in both directions before; it is now the ordered lane not reading the number that makes it true.

- **`shardsHeld()` is BOTH lanes; `unorderedShardsHeld()`/`orderedUnitsHeld()` are the per-lane ones.** It used to be the unordered count alone, so a sole consumer of a 4-shard queue reported 4 while holding 68 — omitting exactly the lane whose ownership failures are invisible in depth. Anything about `shardCount` (growth, shrink-refusal, a SHARD-scope session excluding consumers) must ask the **unordered** accessor: those are unordered-lane questions, and the merged total buries them under a constant 64. Four existing tests asserted the old semantics, including one whose own description said "unordered shards".
- **`remaining()` is per configured lane.** It iterated `shardCount` and counted the unordered table whichever lane was configured, so on an ordered queue it returned zero unconditionally — wrong bound and wrong table, and a drain assertion written against it would pass before anything was delivered. `ShardOwnedLaneAccountingIT` pins both this and `shardsHeld()`, verified failing against the old implementations.
- **`MessageQueue.messages(offset, limit, ascending)` is an ADMIN listing and says so.** Ordered by `(lane, shard, seq)` across both lanes in one `UNION ALL`, which is the message id — so it answers `DurableQueues`' "sort by getId()" exactly, and makes no chronological claim. It exists because the admin console's message browser is built on `getQueuedMessages`, which the adapter used to refuse: 500 on that page for any app on this engine. A deep offset sorts the queue's rows; that is an administrator's cost, paid once per page viewed, not a message's. Do not reach for it from anything on the delivery path. Note `both` is a PostgreSQL reserved word — the subquery alias is `lanes`.
- **Statistics are per-JVM and reach the console through `MessageQueue.statistics()`, not the raw metrics map.** `ShardOwnerMetrics.snapshot()` stays the full debugging map (every counter; no key count is kept here, since one stated before drifted unnoticed); `statistics()` is the operator subset as a stable record, so renaming an internal counter is not a breaking change to a published contract. The DTO carries `runningInThisInstance` because an instance consuming none of a queue answers zeros, and a console cannot otherwise tell that from "nothing is happening" — `unownedShards` is the cluster-wide answer and it reads the database.
- **A subscription's two lane consumers SHARE one `ShardOwnerMetrics`.** `PostgresqlMessageQueue.consume` hands the same object to both, deliberately, since a subscription is one thing to the caller. So anything aggregating over `consumers` must deduplicate by identity or it doubles every counter — which reported 136 units acquired for an instance holding 68, and would have gone unnoticed on any counter without an independent number to check it against.
- **`shardsAcquired` counts the first acquisition too, not only rebalances.** It used to be incremented in `rebalance()` alone, so a single instance that took every unit at start-up and never rebalanced reported zero. Invisible until the counter was published; compare it against `status`'s owned counts.
- **`unownedShards` is the operational signal this engine lacked.** Depth cannot distinguish "nobody is consuming" from "busy"; every ownership failure here was invisible in the metrics of the day and surfaced as an unattributable backlog. `MessageQueue.health()` + `bindQueueHealth`. It is not the whole signal: a shard that is leased but unserved (a takeover that keeps failing) counts as owned. That one shows as `ShardOwnerMetrics.shardsAwaitingTakeover` through `ShardOwnedQueue.metrics()`, and through `MessageQueue` (the starter and the adapter on it) as `QueueObserver.takeoverStalled`, published as `essentials.queue.shards.awaiting.takeover`; `health()` and `bindQueueHealth` cannot report it. See "A failing statement is not a failing connection".
- **`countLiveInstances` is floored at 1, `countInstances` is not.** The floor exists so `fairShare` cannot divide by zero. Using the floored one for health makes "nobody is consuming" read as "one instance" — the exact state being reported.
- **Micrometer gauges must use the `Supplier` form.** The state-object form is a WEAK reference: a cache created in a bind method is collected once nothing else holds it and the gauge reports `NaN` silently, forever. Retaining it on the observer is not enough — the observer can be collected too. The depth gauge shipped with this and looked fine, because asserting right after binding runs before any GC. `gauges_keep_reporting_after_their_state_could_have_been_collected` forces one.

## Auto-configuration ordering — two classes, and the slot between them

Three beans, three different ordering needs, and every failure here is silent: a `@ConditionalOnBean` that backs off logs nothing and leaves the endpoints 404ing.

| Class | Ordered | Because |
|---|---|---|
| `ShardOwnedQueueAutoConfiguration` | **before** `EssentialsComponentsConfiguration` | its `DurableQueues` bean must displace that starter's `@ConditionalOnMissingBean` default — the whole mechanism behind `durable-queues-enabled` |
| `ShardOwnedQueuesAdminApiAutoConfiguration` | **after** `EssentialsComponentsConfiguration`, **before** `EssentialsAdminApiAutoConfiguration` | it is `@ConditionalOnBean(EssentialsSecurityProvider)`, declared by the former; and the latter registers the controller `@ConditionalOnBean(ShardOwnedQueuesApi)`, declared by it |

- **They cannot be one class.** `EssentialsAdminApiAutoConfiguration` is itself after `EssentialsComponentsConfiguration`, so "before components" and "after admin-api" is a cycle. Merging them broke the admin endpoints once: adding the `beforeName` moved the nested admin config earlier, its `@ConditionalOnBean` found nothing, and every `/shard-owned-queues` path 404'd. Splitting them the wrong way broke it a second time, in the opposite direction.
- **A test using `ApplicationContextRunner` must list BOTH.** `AutoConfigurations.of(...)` is explicit; the imports file is not consulted.

## Admin API gotchas

- **The admin surface is FOUR places, not three: the `*Api` SPI, `EssentialsAdminApiSpec`, the controller — and `admin.js` in `spring-boot-starter-admin-ui`.** The console's "Shard-owned queues" page renders ownership, depth, the `statistics()` tiles and the dead letters, so a counter added to `QueueStatistics` is invisible to an operator until a tile is added for it. `AdminUiContractParityTest` only checks that every path `admin.js` calls is declared (count 57) — it cannot see a *field* nobody renders. Two gates to remember when the surface grows: that path count, and `AdminApiContractConformanceTest`'s operation count (60). There is no JS build; `node --check` on `admin.js` is the only syntax gate, and a break there takes out the whole console rather than one page.
- **`ShardOwnedQueuesController` lives in `spring-boot-starter-admin-api`, with every other admin controller.** That is the convention's third place, and publishing the engine is what made it legal. It matters beyond tidiness: `AdminApiExceptionHandler` is `@RestControllerAdvice(basePackageClasses = AdminApiPaths.class)`, so while the controller sat in the engine's own starter *no* error mapping reached it — a 404 arrived as a 500, and an authorization failure would have been a 500 rather than a 403. Registered `@ConditionalOnBean(ShardOwnedQueuesApi.class)`, the same shape CDC and the event store use, so an application that does not wire the engine never gets it. `AdminApiContractConformanceTest` covers these operations now; its count is 60.
- **`releaseKeptOrderedUnit(instanceId, unit)` (SPI, API, `POST .../ordered-units/{unit}/release-kept?instanceId=…`) answers from the answering process's memory, and only for the instance id asked for.** Kept units are per `ShardOwnedQueue` object (`keptOrderedOwners`); `PostgresqlMessageQueue` asks `consumers` + `beingStarted` + `endingLanes` + `heldIndexes` lanes, read in one `handOver` step: `endingLanes` holds an unsubscribed or failed-`consume()` pair from before it leaves `consumers` (`unsubscribe()`), or from the same step as it leaves `beingStarted` (a failed `consume()`), until `releaseSubscriptionIndex` frees or holds its index - without it a request during the stops (kept-unit WARN already logged) came back empty (`ShardOwnedUnsubscribeIT.a_kept_unit_released_on_request_while_*_still_stopping_*`). A lane under another instance id answers empty before touching anything, its review included (`ShardOwnedQueue.releaseKeptOrderedUnit`): without it, a request for the unit the operator diagnosed under one subscription released a unit of the same number whichever subscription of the answering process had kept it (`a_release_on_request_touches_only_the_subscription_running_under_the_instance_id_asked_for`, mutation-checked). The answer is `KeptUnitReleases(answeredBy, releases)`: `answeredBy` = the PMQ's own id, then each asked lane's that differs, so an empty answer still names the process. Empty `releases` elsewhere = normal answer, not 404. Reviews the kept units first (`reviewStuckKeptUnits`), then through `KeptUnit.claimHandBack` (`BUSY` at `STOP_FLUSHING`/`HANDING_BACK`), flush + fenced `releaseLeaseRows` (now returns the count: 0 = `ALREADY_TAKEN`); tries EVERY kept entry for the unit, never returns on the first `ALREADY_TAKEN`/`BUSY`: a run that took the unit over past `stuckHandlerTimeout` and was stopped again lists its entry after the stale one, which still reads `holdsLeaseRow()` true (answer: `RELEASED` if any, else `BUSY`, else `ALREADY_TAKEN`); one subscription at most runs under an id among the lanes asked (indexes are given back only once out of `endingLanes` and `heldIndexes`), so `PostgresqlMessageQueue` throws its lane's `SQLException` as it is (pin: `ShardOwnedUnsubscribeIT.a_kept_unit_whose_release_on_request_the_database_refuses_...`) - the cross-subscription catch-and-WARN it had before the instance id went with it; ends `FORCE_RELEASED` with a key in handler (its message charged an attempt before the release, dead-lettered at `maxAttempts`: attempt-counts bullet) — `Phase.nothingWaitsForHandler`, read by `keptOrderedUnitAwaited` and `endRun`, so no held id, no stay-registered — else `HANDED_BACK`. SPI and API methods are `default` (empty): implementors outside this repo. Console: **Release kept unit** on the Shard-owned queues page (`admin.js` `shardReleaseKept`; asks for the instance id and the unit, acts on the instance taking the request, answer shown as a notice naming `answeredBy` and each entry's `deadLetteredKeys`). Each `KeptUnitRelease` carries the charge made before the release (`charged`, `deadLetteredKeys`; `ReleaseCharge.NONE` for `BUSY`), through `ApiShardOwnedKeptUnitRelease` and the contract: a key dead-lettered by the release is blocked behind its dead letter, the operator's follow-up. Pins: `ShardOwnedUnsubscribeIT.a_kept_unit_released_on_request_*` (the first also stops again with the handler running: deregisters; mutation-checked against `isGivenUp()` in `endRun`), `..._whose_row_was_taken_meanwhile_...` (`ALREADY_TAKEN`, new owner untouched) and `a_unit_kept_again_after_a_takeover_...` (two entries; mutation-checked against returning on the first `ALREADY_TAKEN`), `KeptUnitPhaseTest`, `ApiShardOwnedKeptUnitReleaseTest`, `ShardOwnedQueuesApiIT`, `AdminApiEndpointsTest`.
- **`MessageQueue` is the engine; `ShardOwnedQueuesApi` is the operator surface.** Same layering as `DurableQueuesApi` over `DurableQueues`. The API authorises, resolves the name, delegates and converts — it must contain no queue logic, or there are two implementations to keep correct and the divergence surfaces first on the path nobody exercises.
- **`MessageId` had no text form**, which is why by-id operations were reachable only from Java. `toString()`/`parse` render `<lane>-<shard>-<seq>` (`u-3-1042`) — one character for the lane so it fits a URL path segment unescaped, and the same triple the tables use so it can be pasted into psql. By-id *lookup* was never missing; naming a message outside Java was.
- **A malformed id must be an `IllegalArgumentException`.** An unguarded `split` throws `ArrayIndexOutOfBoundsException`, which the admin API's exception handler maps to 500 — reporting a caller's typo as a server fault.
- **Every admin operation takes a `QueueName`, and dropping it is a data-loss bug, not an ergonomics one.** Sequences are per `(queue, shard)`, so the first message of every queue has the same id. `an_id_from_one_queue_does_not_address_a_message_in_another` asserts the premise before asserting the protection. There is deliberately no `getQueueNameFor(messageId)`.
- **A withheld payload is `null`, never `""`.** An empty payload is a legal message and has to stay distinguishable from one being redacted.
- **Payload rendering must not lossy-decode.** `new String(bytes, UTF_8)` substitutes U+FFFD and makes a protobuf payload look like text. Decode with `REPORT` and fall back to hex — the same rendering `shard_queue_readable()` applies, so an HTTP response and psql show the same string.
- **The read and write roles must be genuinely different.** An implementation validating `QUEUE_READER` on the write paths passes every functional test in the suite; `a_reader_cannot_write` is the only thing that catches it. Both it and the redaction tests were verified to fail against a deliberately broken implementation.
- **`MessageQueues` exists because `MessageQueue` is single-queue.** Its `queue_id` is resolved once and then bound into every statement, which is what lets one `ShardRuntime` serve hundreds of queues from five connections — so there is nothing to ask "which queues exist?". `findQueue` returns empty rather than throwing: an unknown name from outside the process is a 404, not a bug.
- **`queueNames()` reads the registry, not the built queues.** The two differ by exactly the queues this pod does not consume — which are the ones worth looking at when something is stuck.
